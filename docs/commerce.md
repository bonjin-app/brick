# 쇼핑몰 (brick-shop)

커머스 플러그인입니다. **코어를 수정하지 않고** 플러그인으로만 구현되어 있어,
Brick의 확장 아키텍처가 쇼핑몰 규모의 기능을 담을 수 있음을 보여줍니다.

## 시작하기

관리자 → 플러그인 → **쇼핑몰** 활성화. 그것으로 끝입니다.
활성화하면 마이그레이션이 적용되고 사이드바에 **주문 · 상품 · 상품 분류 · 쿠폰** 메뉴가 나타납니다.

### 상품 진열 페이지 만들기

관리자 → 페이지 → 새 페이지 (주소: `shop`) → 블록 추가:

| 블록 | 용도 |
|---|---|
| 상품 분류 목록 | 분류 필터 내비게이션 |
| 상품 목록 | 상품 그리드 (분류·개수·열 수·정렬 지정) |
| 상품 상세 | 개별 상품 페이지 |
| 장바구니 | 장바구니 화면 |

`/cart` 슬러그로 장바구니 페이지를, `/checkout` 으로 주문서 페이지를 만들면 구매 흐름이 완성됩니다.

## 기능

| 영역 | 내용 |
|---|---|
| 상품 | 분류, 판매가/정가(할인 표시), 재고, 옵션별 추가금·재고, 진열 순서, 무료배송 |
| 상품 이미지 | 대표 + 추가 이미지 최대 20장, 상세에서 썸네일 갤러리 |
| 상품 후기 | **구매 검증** 별점 후기, 사진 첨부, 판매자 답변, 표시/숨김, 별점 분포 |
| 상품 문의 | 공개/비밀 문의, 판매자 답변, 답변 상태 |
| 장바구니 | 회원(계정 귀속) / 비회원(토큰), 같은 상품 수량 합산 |
| 주문 | 주문번호 자동 발급, 주문자·배송지 스냅샷, 상태 이력 |
| 결제 | 무통장입금 기본. PG는 별도 플러그인으로 확장 |
| 배송비 | 기본 배송비 + 무료배송 기준 금액 + 상품별 무료배송 |
| 쿠폰 | 정액/정률, 최소 주문금액, 최대 할인 상한, 사용 한도, 기간 |
| 재고 | 주문 시 원자적 차감, 취소·환불 시 자동 복원, 재고 부족 알림 |
| 통계 | 매출, 이번 달 매출, 입금대기 건수, 재고 부족 상품 |
| SEO | 상품 상세에 JSON-LD(schema.org/Product + AggregateRating) 자동 삽입, 전 화면 서버 렌더 |

## 설계에서 중요한 것

커머스는 틀리면 **돈이 새는** 영역입니다. 다음을 명시적으로 방어합니다.

### 1. 금액은 항상 서버에서 재계산한다

클라이언트가 보낸 가격·할인액을 절대 신뢰하지 않습니다. 주문 시점에 DB 가격으로 다시 계산합니다.
모든 금액은 **원 단위 integer** 입니다 — 부동소수점을 쓰지 않습니다.

### 2. 재고는 원자적으로 차감한다

조회 후 차감(check-then-act)은 동시 주문에서 초과판매를 일으킵니다. 그래서 조건부 UPDATE를 씁니다:

```sql
UPDATE shop_products SET stock = stock - :qty
WHERE id = :id AND stock >= :qty
RETURNING id
```

영향받은 행이 0이면 다른 주문이 먼저 가져간 것이므로 409로 실패시킵니다.
전체가 **하나의 트랜잭션**이라 실패 시 부분 차감이 남지 않습니다.

> 스모크 테스트가 이것을 검증합니다: 재고 3개에 동시 주문 6건 → 정확히 3건 성공.

### 3. 주문 항목은 가격 스냅샷이다

`shop_order_items` 에 주문 시점의 상품명·단가를 복사합니다.
상품 가격을 나중에 바꿔도 과거 주문 내역과 매출 집계가 변하지 않습니다.

### 4. 주문 상태는 상태 머신이다

```
pending ──→ paid ──→ preparing ──→ shipped ──→ delivered
   │          │           │            │           │
   └──────────┴───────────┴────────────┴───────────┘
              cancelled / refunded
```

허용된 전이만 가능합니다. `pending → delivered` 같은 건너뛰기는 400으로 거부됩니다.
**취소·환불로 전이하면 재고가 자동 복원**되고, 종료 상태에서는 더 이상 전이할 수 없어
재고가 두 번 복원되는 일이 없습니다.

### 5. 장바구니는 관대하게, 주문은 엄격하게

다른 사람이 먼저 구매해 재고가 부족해지는 것은 정상 상황입니다.
이때 장바구니 조회가 실패하면 사용자는 화면을 볼 수도, 수량을 줄일 수도 없게 됩니다.

- **장바구니 조회**: 문제 항목을 `available: false` + `issue` 로 표시하고 합계에서 제외
- **주문 생성**: 409/400으로 확실히 차단

### 6. 후기는 구매한 사람만 쓴다

평점은 그 자체가 상품 정보입니다. 사지 않은 사람이 별점을 남기면 평점이 정보로서
가치를 잃습니다. 그래서 후기 작성 요청마다 **주문을 되짚어 확인**합니다.

```
후기 작성 → 이 회원의 주문 중
            해당 상품이 담겨 있고
            상태가 paid / preparing / shipped / delivered 인 것이 있는가?
          → 없으면 403
```

- **입금대기(pending)는 인정하지 않습니다.** 주문만 걸어두고 후기를 쓰는 것을 막습니다.
- **취소·환불된 주문도 인정하지 않습니다.**
- 근거가 된 주문번호를 후기 행에 남기지만, **공개 응답에서는 지웁니다.**
  고객에게는 `verified: true` 배지만 보입니다 — 주문번호는 개인정보입니다.
- 상품당 1인 1후기입니다 (`shop_reviews_once_idx` 부분 유니크 인덱스).
  두 번째 시도는 409로 막고, 화면은 "기존 후기를 수정" 으로 안내합니다.

숨긴 후기는 목록에서 빠지고 **평점 집계에서도 제외**됩니다. 삭제 대신 숨김을 기본으로
둔 이유는 되돌릴 수 있기 때문입니다. 집계는 증감 누적이 아니라 매번 다시 셉니다 —
숨김·복구·수정이 섞여도 평점이 어긋나지 않습니다.

`brick-point`가 설치되어 있으면 후기 작성에 포인트가 적립됩니다
(기본 100P, 후기 1건당 1회). 구매 검증을 이미 통과했으므로 어뷰징 여지가 작습니다.

### 7. 비밀 문의는 서버에서 가린다

문의에는 연락처·주소가 자주 들어갑니다. 그래서 비밀 문의는 **응답 자체에서**
제목을 "비밀 문의입니다"로 바꾸고 본문과 답변을 `null`로 지웁니다.
화면에서 감추는 방식이 아니라 데이터가 나가지 않습니다.

후기·문의 목록은 페이지 렌더 캐시에 담지 않고 클라이언트가 따로 불러옵니다
(ADR-30). "내 비밀 문의"나 "내 후기 삭제 버튼"이 캐시된 HTML에 섞이면
다른 사람에게 새어 나가기 때문입니다.

### 8. 옵션은 텍스트로 편집하고 이름으로 동기화한다

옵션은 상품에 종속된 목록입니다. 선언적 관리 화면(ADR-12)은 부모에 종속된 목록을
편집할 수 없으므로, 상품 폼에 **한 줄에 하나씩** 적습니다:

```
색상: 빨강|1000|10
색상: 파랑|0|5
무광 마감||3
```

`이름|추가금|재고` 이고 뒤쪽은 생략할 수 있습니다(재고를 비우면 무한).
저장할 때 전부 지우고 다시 넣지 않습니다 — 그러면 장바구니에 담긴 옵션의 id가
사라져 고객의 장바구니가 조용히 망가집니다. **이름으로 짝지어 갱신**하고,
목록에서 사라진 것만 삭제합니다. 이름을 바꾸지 않는 한 장바구니는 그대로 유지됩니다.

추가 이미지도 같은 방식입니다(한 줄에 주소 하나, 최대 20장).
`javascript:` 같은 스킴은 저장 단계에서 거부합니다.

### 관리자 (admin/manager)

`/admin/products`, `/admin/categories`, `/admin/orders`, `/admin/coupons`,
`/admin/reviews`, `/admin/inquiries` (각 CRUD), `/admin/stats`, `/admin/settings`.

후기 관리는 답변과 표시 여부를 같은 요청에서 저장합니다.
문의 관리는 답변을 저장하면 상태가 자동으로 `answered` 가 됩니다.

## PG 결제 연동하기

기본은 무통장입금입니다. 카드/간편결제는 **별도 플러그인**으로 붙이는 것을 권장합니다:

1. `shop.order.created` 훅을 구독해 결제 요청을 만든다
2. PG 콜백을 받을 라우트를 `registerRoute` 로 등록한다
3. 검증 후 주문을 `paid` 로 전이시킨다

PG사 인증 정보(가맹점 ID, 시크릿)는 `ctx.settings` 에 저장하세요.
코어나 brick-shop을 수정할 필요가 없습니다.

## 취소 · 반품 · 교환

편의 기능이 아니라 **법적 요건**입니다. 전자상거래법 제17조는 소비자가 상품을 받은
날부터 **7일** 안에 청약철회를 할 수 있다고 정하고, 사업자는 이를 거부할 수 없습니다.

### 상품 단위로 처리합니다

세 개 중 하나만 반품하고 색상만 교환하는 것이 실제입니다. 주문 상태를 통째로
바꾸면 나머지 두 개의 배송 정보가 사라집니다. 그래서 요청은 **상품 단위**이고,
주문 상태는 전량이 빠졌을 때만 바뀝니다.

### 금액은 안분합니다

10,000원짜리 두 개에 2,000원 쿠폰을 쓴 주문에서 하나를 반품하면 **9,000원**입니다.
실제로 받은 돈이 18,000원이기 때문입니다. 10,000원을 돌려주면 반품할수록
사업자가 손해를 봅니다.

전체 취소일 때는 배송비도 돌려줍니다. 부분 취소는 남은 상품이 배송되므로
배송비를 유지합니다.

### 누가 반송비를 내는가

| 사유 | 부담 |
|---|---|
| 단순 변심 · 사이즈/색상 변경 · 기타 | **고객** (제18조 제9항) |
| 상품 불량 · 오배송 · 배송 중 파손 · 배송 지연 | **사업자** |

사유가 자유 입력이 아닌 이유: **불량의 반송비를 고객에게 청구하는 것은 위법**이라
사업자가 임의로 "고객 부담"이라고 적을 수 없어야 합니다. 사유 코드에 부담자가
고정되어 있고, 화면은 신청 **전에** 누가 내는지 알려줍니다 — 나중에 환불액이
깎여 있으면 분쟁이 됩니다.

고객 부담이면 반송비를 환불액에서 차감합니다. 별도로 청구하는 것보다 분쟁이 적습니다.
금액은 **관리자 → 쇼핑몰 설정 → 반품 배송비**에서 정합니다(기본 3,000원).

### 처리 흐름

```
접수 → 승인 → 수거중 → 입고완료 → 처리완료
                                    └─ 여기서 재고 복원 + 환불이 실행됩니다
     └─ 거부 (사유 필수)
```

**물건을 받기 전에 완료로 바꾸지 마세요.** 재고가 복원되고 환불이 나갑니다.
`접수 → 입고완료` 처럼 건너뛰는 전이는 막혀 있습니다.

취소(배송 전)는 수거가 없으므로 `승인 → 처리완료` 로 바로 갑니다.

**거부에는 사유가 필수입니다.** 고객에게 그대로 전달되어야 왜 거부됐는지 알 수
있습니다.

### 신청 가능 범위

| 주문 상태 | 신청 가능 |
|---|---|
| 입금대기 · 결제완료 · 상품준비중 | 취소 |
| 배송중 | 반품 · 교환 (이미 물건이 나갔으므로) |
| 배송완료 | 반품 · 교환 |
| 취소 · 환불 | 없음 |

배송완료 후 **7일이 지나면 단순 변심 반품은 막히지만 불량은 언제든 받습니다.**
하자에 대한 책임은 청약철회와 다른 근거에서 나옵니다.

### 교환

같은 상품의 **다른 옵션**으로만 됩니다. 다른 상품으로 바꾸는 것은 취소 + 재주문이고,
금액이 달라져 결제를 다시 해야 합니다.

완료 시 반품 옵션의 재고는 늘고 교환 옵션의 재고는 줄며, 주문 항목의 옵션이
바뀝니다 — 나중에 "무엇을 받았는가"가 맞아야 합니다.

### API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `.../returns/reasons` | 사유 목록 + 배송비 부담자 |
| GET | `.../orders/:orderNo/returnable` | 신청 가능 수량 · 종류 · 청약철회 기한 |
| POST | `.../orders/:orderNo/returns` | 신청 |
| GET | `.../my/returns` | 내 요청 목록 |
| GET | `.../returns/:id` | 요청 상세 |
| POST | `.../returns/:id/cancel` | 요청 철회 (처리 시작 전에만) |
| GET | `.../admin/returns` | 전체 목록 (운영자) |
| PUT | `.../admin/returns/:id` | 상태 변경 · 운송장 · 거부 사유 (운영자) |

### 훅

| 훅 | 시점 |
|---|---|
| `shop.return.requested` | 신청 접수 (운영자 알림을 붙이는 지점) |
| `shop.return.resolved` | 완료 또는 거부 |

### 검증

```bash
DATABASE_URL=postgresql://... bash scripts/smoke-returns.sh
```

99개 항목. 돈이 걸린 계산을 특히 촘촘히 확인합니다 — 할인 안분, 재고가 정확히
그만큼만 복원되는가(이중 복원 없는가), 물건을 받기 전에 환불되지 않는가,
불량의 반송비를 고객에게 청구하지 않는가.


## 회원 등급

구매 실적에 따라 등급이 자동 배정되고, 등급별 상시 할인이 적용됩니다.
관리자 → 쇼핑몰 → 회원 등급.

- **산정**: 최근 3개월 순구매액 (결제 금액 − 반품 환불액). 반품하면 실적에서
  빠집니다 — 사서 반품하기로 등급을 올릴 수 없습니다.
- **재계산**: 6시간마다 자동. 등급을 만들거나 바꾼 직후에는 `지금 재계산`
  (`POST /admin/grades/recompute`)을 부르세요.
- **할인**: 상품 금액의 %. 쿠폰과 함께 쓸 수 있고 합쳐서 상품 금액을 넘지
  않습니다. 주문 내역에는 등급 이름과 할인액이 그대로 남습니다.
- **기본 등급**: 기준 금액 0원인 등급입니다. 구매가 없는 회원도 여기 배정됩니다.
- 손님은 `GET /me/grade` 로 자기 등급과 **다음 등급까지 남은 금액**을 봅니다.

등급은 역할(권한)과 별개입니다 — 등급이 높아도 관리 권한은 없습니다.
