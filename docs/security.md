# 보안

## 구현된 방어

| 영역 | 조치 |
|---|---|
| 비밀번호 | argon2id 해시 (memory-hard, GPU 공격에 강함) |
| 세션 | 랜덤 256bit 토큰. **DB에는 sha256 해시만 저장** — DB 유출로 세션을 탈취할 수 없음 |
| 쿠키 | `httpOnly` · `sameSite=lax` · 프로덕션에서 `secure` |
| CSRF | `sameSite=lax` 로 크로스사이트 POST에 쿠키가 실리지 않음 |
| 브루트포스 | 계정별 5회/15분, IP별 50회/15분 (NAT 환경 오탐 방지). **DB 에 세므로 서버 수·재시작과 무관하다.** 로그인에 성공하면 그 계정의 기록만 지우고 IP 기록은 **그 시도 한 번만** 되돌린다 — 전에는 IP 기록까지 비워서, 자기 계정으로 가끔 로그인하면 여러 계정에 비밀번호를 뿌려도 IP 한도가 영영 차지 않았다 |
| 가입 스팸 | **캡차** + 같은 이메일 3회/시간 · 같은 IP 20회/시간 (축을 나눈다 — IP 하나에 좁게 걸면 NAT 뒤 사무실·학교에서 여섯 번째 사람이 막힌다) |
| 캡차 | 자체 SVG. HMAC 서명 토큰(상태 없음) · **1회용** · 5분 만료 · 상수시간 비교 |
| 비회원 글쓰기 스팸 | 캡차 필수 (회원은 면제 — 도배 방지·계정 정지로 대응) |
| 비회원 비밀번호 대입 | 비회원 문의·비회원 글·댓글·비밀글은 비밀번호 하나로 열린다(네 자리부터, 문의번호는 순번). **대상별 5회 · IP별 20회 / 15분**, 실패만 센다. 잠긴 동안은 맞는 비밀번호도 시험하지 않는다(시험해 주면 응답이 답을 알려 준다). 동시에 쏟아져도 검증 **전에** 세므로 한도만큼만 시험한다 |
| 비회원 비밀번호 검증 부하 | scrypt 를 **비동기**로 돈다 — 동기(scryptSync)는 한 번에 약 70ms 동안 서버 전체를 멈춰, 틀린 비밀번호를 쏟아부으면 사이트가 섰다(대입 20건 동안 상태 확인이 1.6초) |
| 권한 상승 | 관리자가 자기 권한/활성 상태를 변경할 수 없음 (관리자 전멸 방지) |
| 비밀번호 변경 | 현재 비밀번호 확인 필수 + 성공 시 **모든 세션 무효화** |
| 계정 정지 | 즉시 전 세션 무효화 |
| 파일 업로드 | 확장자 **화이트리스트** + MIME 일치 검사. 저장 키는 서버 생성 |
| 경로 조작 | 정적 서빙과 ZIP 전개 모두 정규화 후 base 디렉터리 검증 (zip-slip 방어) |
| SQL 주입 | Drizzle 파라미터 바인딩. 플러그인도 `sql` 템플릿 사용 |
| XSS (콘텐츠) | 테마 템플릿 `{{ }}` 는 이스케이프, 블록 렌더는 사용자 입력 이스케이프 |
| 설정 조작 | 관리자 설정 API가 화이트리스트 방식 (`install.state` 등 변경 불가) |
| 메뉴 링크 | `javascript:` 등 위험한 스킴 차단 |
| 열린 리다이렉트 | 로그인·카드 등록 뒤 돌아갈 주소(`?next=`)는 **브라우저의 URL 해석으로 풀어 본 결과가 같은 출처일 때만** 따른다. "//" 만 막는 문자열 규칙은 `/\evil.example`(브라우저는 역슬래시를 슬래시로 읽는다)·`/<탭>/evil.example` 에 뚫렸다. `check-safe-next` 가 스크립트 안의 검사 함수를 실제로 돌려 우회 여섯 가지를 넣어 본다. 서버 쪽(OAuth)은 역슬래시·제어 문자를 거부한다 |
| 컨테이너 | 비-root 사용자(uid 1001)로 실행, tini로 PID 1 시그널 처리 |
| 보안 헤더 | `X-Content-Type-Options` · `X-Frame-Options` · `Referrer-Policy` |
| 설정 검증 | 프로덕션에서 약한 `BRICK_SECRET` 이면 부팅 거부 |
| 비밀번호 재설정 | 토큰 sha256 해시 저장 · 30분 만료 · **단회성** · 이메일 열거 방지 · 성공 시 전 세션 무효화 |
| 결제 금액 위조 | PG가 확인한 실제 금액 ≠ 주문 총액이면 거부 + PG 취소 ([결제](payments.md)) |
| 결제 중복 승인 | `(provider, provider_tid)` unique로 DB가 차단 — 재고·매출 이중 계상 방지 |
| 주문 중복 | `idempotencyKey` 로 네트워크 재시도 시 재고 이중 차감 방지 |
| 환불 한도 | 누적 환불액 ≤ 결제액 (코드 + DB CHECK 이중 방어) |
| 감사 로그 | 권한 변경·계정 정지·확장 설치 등 관리 동작을 행위자·IP와 함께 기록 (180일 보관) |
| PG 시크릿 | 공개 API로 반환하지 않음 (설정 여부만). PG 응답은 화이트리스트 필터 후 저장 |

## 신뢰 모델 — 반드시 이해할 것

Brick은 **관리자를 신뢰합니다.** 워드프레스와 같은 모델입니다.

- `core/rich-text` 블록은 raw HTML을 그대로 출력합니다
- 테마 템플릿은 `{{{ }}}` 로 raw HTML을 삽입할 수 있습니다
- 플러그인은 서버 프로세스 안에서 **제약 없이** 실행됩니다 — 파일 시스템과 DB에 접근할 수 있습니다

따라서:

> **관리자 권한은 서버 권한과 사실상 동등합니다.**

그래서 **관리 경로는 규칙으로 닫혀 있습니다.** 플러그인이 `/admin/...` 으로 등록한
라우트는 디스패처가 운영자(manager) 이상을 요구합니다 — 플러그인이 자기 핸들러에서
권한 확인을 잊어도 열리지 않습니다. 그보다 좁혀야 하는 일(상품·쿠폰·환불처럼
`admin` 전용)은 핸들러가 자기 줄에서 다시 막고, CI 가 그 명시를 확인합니다.
> 신뢰하지 않는 사람에게 관리자 권한을 주지 마세요.
> 출처가 불분명한 플러그인을 설치하지 마세요.

일반 회원(`member`)은 이런 권한이 없습니다 — 글쓰기와 댓글만 가능합니다.

## 배포 시 체크리스트

- [ ] `BRICK_SECRET` 을 `openssl rand -base64 32` 로 생성해 설정
- [ ] `NODE_ENV=production` 설정
- [ ] `POSTGRES_PASSWORD` 를 기본값(`brick`)에서 변경
- [ ] HTTPS 적용 (Let's Encrypt / Cloudflare)
- [ ] 프록시 뒤라면 `BRICK_TRUST_PROXY=true` — **설정하지 않으면 요청 제한이 무력화됩니다**
      (빠뜨리면 관리자 대시보드가 알려줍니다 — 프록시 헤더가 달린 요청이 오는데 신뢰하지 않는 상태를 감지합니다)
- [ ] `BRICK_SITE_URL` 을 사이트의 공개 주소로 설정 — **기본값이면 메일 안의 모든 링크가 `localhost` 를 가리킵니다**
      (빠뜨리면 부팅 로그와 관리자 대시보드가 알려줍니다)
- [ ] 내부 API 포트(3001)를 외부에 노출하지 않음 (Docker는 기본적으로 노출하지 않음)
- [ ] PostgreSQL 포트를 외부에 노출하지 않음
- [ ] 관리자 계정에 강한 비밀번호
- [ ] 자동 백업 설정 ([운영 가이드](operations.md#백업))
- [ ] 불필요하면 회원가입 닫기 (관리자 → 설정)
- [ ] **SMTP 설정** — 없으면 재설정 링크가 로그로 노출됩니다
- [ ] `BRICK_SITE_URL` 을 실제 도메인(https)으로 설정 — 메일 링크에 사용됩니다
- [ ] 쇼핑몰 사용 시: PG 라이브 키 적용, 테스트 키 제거 ([결제](payments.md))
- [ ] `BRICK_CAPTCHA` 를 끄지 않았는지 확인 (비회원 글쓰기·문의·재입고 알림을 허용한다면 필수)

## 캡차

비회원 글쓰기·댓글·회원가입은 스팸의 주 표적입니다. 도배 방지(작성 간격)만으로는
분산된 봇을 막을 수 없습니다.

기본 구현은 **자체 SVG 캡차**입니다. reCAPTCHA/Turnstile을 기본으로 쓰지 않는 이유는
API 키 발급이 필요해 "설치가 쉬워야 한다"가 깨지기 때문입니다.

| 특성 | 내용 |
|---|---|
| 상태 | **없음.** 정답을 HMAC 서명 토큰에 담아 클라이언트에 넘깁니다 (DB 테이블 불필요) |
| 1회용 | 통과한 토큰을 캐시에 기록 — 봇이 한 번 풀고 재사용하는 것을 막습니다 |
| 만료 | 5분 |
| 토큰 내용 | 정답이 아니라 `HMAC(secret, nonce:정답)`. 서명은 위조를 막을 뿐 열람을 막지 않으므로, 담지 않는 것이 유일한 방법입니다 |
| 그리는 법 | 내장 스트로크 글꼴로 `<path>` 를 그립니다. `<text>` 로 그리면 정답이 마크업에 평문으로 남습니다 |
| 비교 | 정답·서명 모두 상수시간 비교 (타이밍으로 한 글자씩 맞추는 것 방지) |
| 대상 | 비회원만. 회원에게 매번 요구하면 정상 사용자가 떠납니다 |
| 요구하는 곳 | 회원가입 · 게시판 글·댓글 · 1:1 문의 · 재입고 알림. 메일을 유발하는 비회원 경로는 모두 포함합니다 |
| 문자 | 혼동되는 글자 제외(0/O, 1/I, 2/Z, 5/S, 8/B), 대소문자 무시 |

**한계를 정확히 알아두세요:** 글자 모양을 알아보는 공격(OCR)에는 강하지 않습니다.
대량 스팸봇 대부분을 막지만, 표적 공격에는 Turnstile/reCAPTCHA를 구현하는 플러그인이 필요합니다.
`CaptchaProvider` 인터페이스를 구현해 교체할 수 있습니다.

개발 중에는 `BRICK_CAPTCHA=off` 로 끌 수 있습니다. **프로덕션에서는 끄지 마세요.**
자동화 테스트에서 캡차를 **켜 둔 채** 통과시켜야 한다면 `BRICK_CAPTCHA=test` 를 쓰세요 —
같은 암호·같은 그림에 정답만 응답에 얹어 줍니다. `NODE_ENV=production` 에서는 거부합니다.

## 이메일 열거 방지

비밀번호 재설정은 **계정이 존재하는지 알려주지 않습니다.** 등록되지 않은 주소여도
동일한 성공 응답을 주고, 없는 계정에도 같은 시간을 소비합니다(타이밍 공격 방지).
요청 제한에 걸려도 같은 응답을 유지합니다 — 응답 차이가 곧 회원 목록 유출입니다.

## 알려진 제약

- **이메일 인증은 의무가 아닙니다** — 가입하면 인증 메일이 자동으로 나가지만, 인증하지
  않아도 서비스를 쓸 수 있습니다. SMTP 가 없는 사이트에서 가입이 실패하면 설치 직후
  아무도 들어올 수 없기 때문입니다. 인증을 요구해야 하는 서비스라면 그 규칙을 직접
  세워야 합니다.
- **2단계 인증은 회원이 켭니다** — 운영자(admin·manager)에게는
  `security.require_2fa_for_staff` 로 강제할 수 있지만, 일반 회원에게 강제하는 설정은
  없습니다.
  등록은 **내 정보 화면의 2단계 인증**에서 합니다(인증 앱에 키를 넣고 6자리 코드를
  확인하면 켜집니다). 강제 설정은 **켜는 관리자 본인이 먼저 등록해야** 저장됩니다 —
  그러지 않으면 저장하는 순간 스스로 관리 화면에서 잠깁니다.
- **QR 코드는 없습니다** — 인증 앱에 키를 직접 넣거나(화면이 4자씩 끊어 보여줍니다)
  폰에서 `otpauth://` 링크를 누릅니다. 인증 경로에 외부 패키지를 들이지 않기 위한
  선택입니다.
- ~~요청 제한이 인메모리~~ — 이제 DB 에 셉니다. 서버가 여러 대여도 한도는 하나이고,
  배포로 재시작해도 잠금이 풀리지 않습니다.
- **감사 로그에 변경 전/후 전체 값은 없음** — 무엇이 바뀌었는지 요약만 남습니다.
- **SMTP 미설정 시** 비밀번호 재설정 링크가 서버 로그에 출력됩니다. 개발 편의를 위한
  동작이며, **프로덕션에서는 SMTP를 반드시 설정하세요** (로그 접근자가 계정을 탈취할 수 있습니다).
