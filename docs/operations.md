# 운영 가이드

## 백업

Brick의 상태는 두 곳에 있습니다: **PostgreSQL**(콘텐츠·설정)과 **볼륨**(업로드 파일·설치된 확장).
둘 다 백업해야 완전합니다.

### DB

```bash
# 백업 (custom 포맷 — 압축 + 선택 복원 가능)
docker compose exec brick node /app/api/dist/backup.js dump /app/uploads/db-$(date +%F).dump

# 복원 (기존 데이터를 덮어씁니다)
docker compose exec brick node /app/api/dist/backup.js restore /app/uploads/db-2026-08-25.dump
```

덤프를 뜨면 **그 파일을 실제로 읽어 확인합니다** — `pg_dump` 가 성공했다는 것은
"명령이 끝났다" 일 뿐이고, 디스크가 찼거나 도중에 끊긴 덤프도 파일은 남습니다.
크기와 담긴 테이블 수를 함께 알려 주고, 복원할 수 없는 파일이면 **0 이 아닌
종료 코드로 끝냅니다** — 매일 도는 cron 이 그제야 실패를 알립니다.

```
[backup] 백업 완료: /app/uploads/db-2026-09-22.dump (48.2MB · 테이블 63개)
```

백업 파일을 업로드 폴더 안에 두면 경고합니다. 그 볼륨은 업로드 파일 백업의
대상이기도 해서, 백업이 백업을 품고 부풀다가 볼륨을 채웁니다.

복원은 **덤프를 뜬 그 시점으로 되돌립니다** — 그 뒤에 들어온 주문·가입·글은 사라집니다.
복원하는 동안 손님이 사이트에 글을 쓰고 있으면 그 글도 대상입니다.
**관리자 → 설정 → 점검 모드**를 켜고 하세요 — 손님에게는 점검 안내(503)만 나가고
댓글·주문 같은 쓰기가 막힙니다. 운영자는 그대로 들어올 수 있어 점검 중에도 고칠 수
있고, 켜 두면 대시보드가 계속 알려 줍니다(끄는 것을 잊기 쉬운 자리입니다). (앱을 켠 채로 복원해도 동작하는 것은 스모크가
`smoke-backup.sh` 에서 매번 확인합니다 — 문서가 시키는 방식 그대로 시험합니다.)

`pg_dump: server version mismatch` 가 나오면 컨테이너 안의 클라이언트가 DB 서버보다
낮은 것입니다. 이미지에는 PostgreSQL 17 클라이언트가 들어 있으니, 더 높은 버전의
PostgreSQL 을 쓰고 있다면 이미지를 올리거나 DB 서버 쪽에서 직접 덤프를 뜨세요.

### 파일

```bash
# 업로드
docker run --rm -v brick_uploads:/d -v "$PWD":/b alpine \
  tar czf /b/uploads-$(date +%F).tgz -C /d .

# 플러그인 · 테마
docker run --rm -v brick_plugins:/d -v "$PWD":/b alpine tar czf /b/plugins.tgz -C /d .
docker run --rm -v brick_themes:/d  -v "$PWD":/b alpine tar czf /b/themes.tgz  -C /d .
```

### 자동 백업 (cron)

```bash
# 매일 새벽 4시
0 4 * * * cd /srv/brick && docker compose exec -T brick \
  node /app/api/dist/backup.js dump /app/uploads/db-$(date +\%F).dump
```

오래된 백업 정리도 함께 걸어두세요 — 업로드 볼륨이 백업으로 가득 차는 것이 흔한 사고입니다.

## 점검 모드

복원·판올림·대규모 이전처럼 **지금 들어오면 그 글이 사라지는** 동안 켭니다.
관리자 → 설정 → 점검 모드.

| | 점검 중 |
|---|---|
| 손님의 화면 | 점검 안내 **503** + `Retry-After: 1800` (검색엔진은 색인을 건드리지 않습니다) |
| 손님의 쓰기 | 막힙니다 — 열어 둔 탭에서 들어오는 댓글·주문이 없습니다 |
| 운영자(관리자·운영자) | 사이트도 관리 화면도 평소와 같습니다 |
| 로그인 화면 | 열려 있습니다 — 그래야 고치러 들어옵니다 |

안내 문구는 직접 적을 수 있습니다. 언제쯤 끝나는지 적어 두면 손님이 다시 올 때를 압니다.

**끄는 것을 잊기 쉽습니다.** 운영자는 관리 화면으로 들어오므로 점검 화면을 보지
못하고, 손님만 며칠째 503 을 봅니다 — 그래서 켜져 있는 동안 대시보드가 계속 알립니다.

## 모니터링

| 엔드포인트 | 용도 | 특징 |
|---|---|---|
| `GET /healthz` | liveness | DB를 건드리지 않음. 프로세스 생존만 확인 |
| `GET /readyz` | readiness | DB 연결 확인. 실패 시 503 |

Docker 이미지에 `HEALTHCHECK` 가 내장되어 있어 `docker compose ps` 에 상태가 표시됩니다.

k8s 예시:

```yaml
livenessProbe:
  httpGet: { path: /healthz, port: 3001 }
  initialDelaySeconds: 20
readinessProbe:
  httpGet: { path: /readyz, port: 3001 }
  periodSeconds: 10
```

## 성능

### 캐시

렌더 결과는 PostgreSQL 기반 태그 캐시에 저장됩니다 (기본 TTL 300초).
페이지·테마·플러그인·설정이 변경되면 자동 무효화됩니다.

트래픽이 커지면 Redis로 전환하세요:

```yaml
environment:
  REDIS_URL: redis://redis:6379
```

### 정리 작업

만료된 세션과 캐시 레코드는 **1시간 주기로 자동 정리**됩니다 (`MaintenanceService`).
Redis 없이 동작하는 설계의 대가이므로 코어가 책임집니다 — 별도 cron이 필요 없습니다.

함께 정리되는 것과 보관 기간입니다. 보관 기간은 **각 서비스**가 갖고 일정만 여기
있습니다 — 두 곳에 적으면 한쪽만 고쳐지고 그 어긋남을 아무도 모릅니다.

| 무엇 | 얼마나 |
|---|---|
| 세션 · 캐시 | 만료 즉시 |
| 비밀번호 재설정 토큰 · 이메일 인증 토큰 | 만료 후 |
| 감사 로그 | 180일 |
| 검색 로그 | 180일 |
| **알림** | 읽은 것 30일 · 안 읽은 것도 180일 |

알림은 댓글·주문·재입고마다 한 줄씩 쌓입니다. 치우지 않으면 이 테이블이 본문보다
커지는데, 반년이 지나도록 열어 보지 않은 알림을 붙들고 있어서 좋아지는 사람은
없습니다. 더 오래 보관해야 한다면 그건 백업의 몫입니다.

### 인덱스

주요 인덱스는 마이그레이션에 포함되어 있습니다. 게시글이 수십만 건을 넘어가면
`EXPLAIN ANALYZE` 로 실제 쿼리를 확인하고 필요한 복합 인덱스를 추가하세요.

실측(알림 20만 1천 건, 한 회원의 알림함 1천 건): 머리의 안 읽은 개수 46ms,
목록 첫 쪽 45ms, 이어 읽기 45ms, 로그인 상태 홈 렌더 58ms. DB 시간은 그중
0.1ms 미만이고(부분 인덱스 · 인덱스 스캔) 나머지는 세션 확인과 HTTP 입니다.

## 한국어 검색

**현재 제약**: 코어 검색은 `ILIKE` 기반입니다. 정확하지만 데이터가 많아지면 느려집니다.

PostgreSQL의 기본 전문 검색(`to_tsvector('simple', ...)`)은 한국어에서 두 가지 문제가 있습니다:

1. DB 로케일이 `C` 이면 한글을 토큰으로 인식하지 못합니다 (공식 postgres 이미지는 UTF-8이라 괜찮습니다)
2. 조사·어미가 붙는 교착어 특성상 `simple` 사전으로는 "수정된" ↔ "수정" 이 매칭되지 않습니다

### 권장: pg_trgm

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX pages_title_trgm_idx ON pages USING gin (title gin_trgm_ops);
CREATE INDEX pages_text_trgm_idx  ON pages USING gin (plain_text gin_trgm_ops);
CREATE INDEX board_posts_trgm_idx ON board_posts USING gin (title gin_trgm_ops);
```

trigram 인덱스는 `ILIKE '%검색어%'` 를 가속하므로 코드 변경 없이 즉시 효과가 있습니다.

### 대안

한국어 형태소 분석이 필요하면 `pg_bigm` 이나 외부 검색엔진(Meilisearch, Typesense)을
플러그인으로 연동하는 방향을 검토하세요.

## 부팅이 멈출 때

마이그레이션은 HTTP 리스닝 **전에** 실행되므로, 이 단계에서 막히면 서비스가 뜨지 않습니다.
Brick은 두 경우를 타임아웃과 함께 명확히 알립니다.

### "데이터베이스에 연결할 수 없습니다"

접속 정보나 네트워크 문제입니다. 15초 후 실패합니다.
`DATABASE_URL` 또는 `data/brick.config.json` 을 확인하세요.

### "마이그레이션 락을 60초 안에 얻지 못했습니다"

다른 인스턴스가 마이그레이션 중이거나, **이전 프로세스가 락을 쥔 채 남아 있습니다.**

```sql
-- 누가 붙어 있는지 확인
SELECT pid, state, query, state_change
FROM pg_stat_activity
WHERE datname = current_database();

-- 남은 세션 정리 (pid를 확인한 뒤)
SELECT pg_terminate_backend(12345);
```

여러 인스턴스를 동시에 배포하는 경우에는 정상 동작입니다 —
락을 먼저 얻은 인스턴스가 마이그레이션을 끝내면 나머지가 이어서 뜹니다.

## 켜 둔 확장이 안 보일 때

서버는 멀쩡히 뜨는데 상품·게시판이 **손님 쪽에서만** 통째로 사라졌다면, 확장이
켜져 있는데 돌지 않는 상태입니다. 로그에 이렇게 남습니다.

```
plugin "brick-shop" files are missing — 켜 둔 상태는 그대로 둡니다. 경로·볼륨을 확인하세요.
```

흔한 원인은 셋입니다.

- 컨테이너의 **볼륨이 아직 안 붙은 채** 서버가 먼저 떴다
- `BRICK_PLUGINS_DIR` 이 실제 설치 경로와 다르다 (기본값은 실행 디렉터리의 `plugins`)
- 배포 중 파일을 교체하는 순간에 재시작이 겹쳤다

**켜 둔 상태는 DB 에 그대로 있습니다.** 원인을 고치고 다시 시작하면 저절로
돌아옵니다 — 관리 화면에서 다시 켤 필요가 없습니다. 예전에는 이 상황에서
`is_active` 를 내려 버려서, 경로를 고쳐도 쇼핑몰이 꺼진 채였고 운영자가
알아채기 전까지 손님은 빈 사이트를 봤습니다.

관리자 대시보드가 같은 내용을 한 줄로 알려 주고(**켜 둔 확장이 지금 돌지
않습니다**), 확장 목록에도 이름과 이유가 남습니다 — 목록에서 통째로 사라지면
운영자는 자기가 지웠나 의심하게 됩니다.

## 사이트가 허전해졌을 때 (테마)

디자인이 사라진 것처럼 밋밋한 화면이 나오거나, 적용해 둔 테마가 관리 화면의
목록에서 없어졌다면 **테마 파일을 읽지 못하는 상태**입니다. 로그에 이렇게 남습니다.

```
테마 "editorial" 를 그릴 수 없습니다: … — "default" 테마로 대신 그립니다.
테마 "default" 를 그릴 수 없습니다: … — 내장 레이아웃으로 대신 그립니다.
```

원인은 확장이 안 보일 때와 같은 집안입니다.

- 컨테이너의 **볼륨이 아직 안 붙은 채** 서버가 먼저 떴다
- `BRICK_THEMES_DIR` 이 실제 설치 경로와 다르다 (기본값은 실행 디렉터리의 `themes`)
- 테마 파일을 직접 고치다 `brick.theme.json` 의 쉼표·괄호가 어긋났다
  (빌드 없이 파일을 고치는 것이 이 테마 체계의 목적이므로, 이건 사고가 아니라 일상입니다)

**사이트는 내려가지 않습니다.** 고른 테마 → 기본 테마 → 내장 레이아웃 순으로
물러납니다. 마지막 단계는 디자인이 없는 대신 제목·본문·메뉴가 그대로 나가고
링크가 살아 있어, 손님은 수수한 사이트를 볼 뿐 주문도 글쓰기도 계속됩니다.
예전에는 이 상황에서 **모든 공개 페이지가 500** 이었습니다 — 글도 상품도 DB 에
멀쩡히 있는데 사이트가 통째로 사라진 것처럼 보였습니다.

**되돌리면 저절로 돌아옵니다.** 파일을 고치거나 볼륨을 붙이면 다음 렌더부터
원래 테마로 그립니다 — 다시 적용할 필요가 없습니다. 어느 테마가 왜 안 되는지는
관리자 대시보드(**적용해 둔 테마로 그리지 못하고 있습니다**)와 테마 목록 화면에
이유가 그대로 적힙니다. 올린 테마가 미리보기에서 실패한다면 그 화면이 알려 주는
메시지가 곧 고쳐야 할 곳입니다 — 미리보기는 대체 테마로 물러나지 않습니다.

## 로그

```bash
docker compose logs -f brick          # 전체
docker compose logs --since 1h brick  # 최근 1시간
```

프로덕션에서는 로그 드라이버를 설정해 디스크가 차지 않게 하세요:

```yaml
logging:
  driver: json-file
  options: { max-size: "10m", max-file: "3" }
```

## 스케일링

Brick은 **단일 인스턴스**를 전제로 설계되었습니다 (ADR-1). 여러 인스턴스로 늘리려면:

| 항목 | 필요한 조치 |
|---|---|
| 요청 제한 | 현재 인메모리 → `CacheProvider` 기반 구현으로 교체 필요 |
| 캐시 | `REDIS_URL` 설정 (PostgreSQL 캐시도 공유되지만 Redis가 빠름) |
| 업로드 파일 | `STORAGE_DRIVER=s3` 로 전환 (로컬 디스크는 공유되지 않음) |
| 확장 파일 | 공유 볼륨(NFS) 또는 이미지에 포함 |
| 마이그레이션 | advisory lock이 이미 처리 — 코어와 플러그인 **둘 다**. 추가 조치 불필요 |

대부분의 설치형 사이트는 단일 인스턴스로 충분합니다. 수직 확장을 먼저 검토하세요.
