# 결제

Brick은 특정 PG에 묶이지 않습니다. **결제수단은 플러그인으로 추가**하며,
코어나 brick-shop을 수정하지 않습니다.

## 기본 제공

| 결제수단 | 플러그인 | 상태 |
|---|---|---|
| 무통장입금 | brick-shop 내장 | 사용 가능 |
| 카드·계좌이체·간편결제 | brick-pay-toss | 키 입력 후 사용 가능 |
| **이니시스·KCP·NICE·토스·카카오페이·네이버페이 등** | **brick-pay-portone** | 포트원 콘솔에서 채널 등록 후 사용 가능 |

## 토스페이먼츠 설정

1. [토스페이먼츠 개발자센터](https://developers.tosspayments.com/)에서 키 발급
2. 관리자 → 플러그인 → **토스페이먼츠 결제** 활성화
3. 관리자 → **토스페이먼츠** 메뉴에서 키 입력

| 항목 | 설명 |
|---|---|
| 클라이언트 키 | `test_ck_` / `live_ck_`. 프론트엔드에 노출되는 값 |
| 시크릿 키 | `test_sk_` / `live_sk_`. **절대 노출 금지.** 저장 후 다시 표시되지 않음 |
| 결제 사용 | 켜면 주문서에 카드 결제가 나타남 |

시크릿 키는 저장 후 조회할 수 없습니다. 비워두고 저장하면 기존 값이 유지되므로
클라이언트 키만 바꿀 때 실수로 지워지지 않습니다.

## 포트원 설정 — 이미 계약한 PG 를 그대로

한국 판매자는 대개 이미 특정 PG 와 계약되어 있습니다. 포트원(PortOne) V2 를 쓰면 그 PG 를
**포트원 콘솔의 채널로 등록**하기만 하면 됩니다 — 이니시스·KCP·NICE·토스·카카오페이·
네이버페이·페이코 등 포트원이 붙인 PG 가 같은 코드로 돕니다.

1. [포트원 콘솔](https://admin.portone.io)에서 계약한 PG 를 **채널**로 추가
2. 관리자 → 플러그인 → **포트원 결제** 활성화
3. 관리자 → **포트원** 메뉴에서 입력

| 항목 | 설명 |
|---|---|
| 상점 ID | `store-…`. 콘솔 → 연동 정보. 공개되어도 되는 값 |
| 채널 키 | `channel-key-…`. **어느 PG 로 결제할지** 정한다. 공개되어도 되는 값 |
| V2 API 시크릿 | 콘솔 → 연동 정보 → V2 API. **절대 노출 금지.** 저장 후 다시 표시되지 않음 |
| 결제 수단 | 카드 · 간편결제 · 계좌이체 · 휴대폰 · **가상계좌** (채널이 지원해야 한다) |
| 가상계좌 입금 기한 | 1~720시간(기본 72). 지나면 계좌가 닫히고 주문이 자동 취소된다 |

토스 플러그인과 다른 점:

- **서버 승인 단계가 없다.** 결제는 포트원 결제창에서 끝나고, 서버는 결제 건을 **조회**해
  상태(`PAID`)와 금액을 확인한다. 조회는 몇 번을 해도 같으므로 승인 재시도가 이중 승인이
  되는 문제가 구조적으로 없다.
- **결제 ID 는 주문번호로 시작한다.** 서버는 조회 전에 그 접두사를 확인한다 — 확인하지
  않으면 다른 주문의 같은 금액 결제를 들고 와 이 주문을 결제 완료로 만들 수 있다(금액
  대조만으로는 못 막는다. 스모크가 그 경로를 실제로 시험한다).
- **부분환불에 취소 전 잔액을 싣는다**(`currentCancellableAmount`). 포트원은 이 값이 실제
  잔액과 다르면 거절한다 — 커밋되지 않은 재시도로 같은 환불이 두 번 나가지 않는다.

### 가상계좌와 웹훅

**포트원 콘솔 → 웹훅**에 `https://<사이트 주소>/api/plugins/brick-pay-portone/webhook` 을 등록하세요.

- 결제창에서 계좌가 발급되면 주문은 **결제대기**로 남고, 손님은 완료 화면·주문 조회·안내(알림함·
  메일·문자 — "주문 — 가상계좌 입금 안내")에서 계좌와 기한을 봅니다. 입금 대기 주문에는 "다시 결제"
  버튼을 내지 않습니다(계좌가 하나 더 생긴다).
- 입금되면 포트원이 웹훅을 보내고, Brick 은 **웹훅 내용을 믿지 않고** 포트원에 다시 조회해 입금이
  확인될 때만 결제 완료로 만듭니다. 위조된 통지는 "다시 확인" 을 한 번 부를 뿐입니다(주소마다 한도).
- 결제 미완료 자동 취소(분)는 입금 대기 주문을 건드리지 않습니다. **계좌 기한이 지나면** 취소합니다.
- 운영자가 입금 대기 주문을 취소한 뒤 입금이 들어오면 "취소된 뒤 들어온 결제" 로 환불을 요청하고
  기록을 남깁니다.
- 카드로 결제하고 창을 닫아 사이트로 돌아오지 않은 손님도 웹훅이 결제를 확정합니다.

- **입금된 가상계좌의 환불**은 손님 계좌로 보내야 합니다. 관리 화면의 주문 폼(또는 환불 API)에
  "환불 받을 은행·계좌번호·예금주" 를 적으면 포트원에 실어 보냅니다. 계좌 없이 환불하려 하면 PG 에
  보내기 전에 무엇이 필요한지 알려 줍니다. 취소된 뒤 들어온 입금은 자동 환불이 거절되어 "수동 환불
  필요" 로 기록되고, 계좌를 받아 같은 방식으로 돌려줍니다.

- 손님은 **취소·반품 신청서에 환불 받을 계좌**를 적습니다(가상계좌로 결제한 주문에만 칸이 열리고, 없으면
  신청을 받지 않습니다). 운영자가 완료하면 그 계좌로 환불하고, **돌려준 뒤에는 계좌를 지웁니다**. 환불
  전에 탈퇴해도 지웁니다.

### 정기결제 (빌링키)

포트원 콘솔에 **빌링키(정기결제) 채널**을 따로 추가하고, 관리자 → 포트원 에서 **정기결제 사용** 과
**정기결제 채널 키**를 넣으면 회원이 결제 카드(`/shop/cards`)를 등록하고 정기배송을 신청할 수 있습니다.
일반 결제와 따로 켭니다 — 일반 결제는 다른 PG 로 받고 정기결제만 포트원으로 해도 됩니다.

- **카드는 이 회원의 것만 붙습니다.** 포트원 빌링키는 한 번 쓰고 끝나는 값이 아니고, 카드 등록 뒤
  돌아오는 주소에 그대로 실립니다. 그래서 Brick 은 회원마다 **고객 식별자**를 하나 만들어 기억하고,
  등록할 때 (1) 요청의 고객 식별자가 이 회원의 것인지, (2) 포트원에 조회한 빌링키가 **그 고객
  식별자로 발급**됐는지, 이 상점의 것인지, 발급 상태인지를 확인합니다. 남의 등록 결과를 들고 와도
  내 계정에 붙일 수 없습니다.
- **회차 결제 ID 는 정해진 값입니다**(`<회차 주문번호>-<시도 해시>`). 포트원에는 멱등키가 없고 **이미
  결제된 결제 ID 를 거절**하는 것이 그 역할을 합니다 — 같은 시도를 다시 보내면 "이미 결제됨" 이 오고,
  Brick 은 조회로 확인해 그것을 성공으로 읽습니다. 카드사가 거절한 뒤의 다음 시도는 새 결제 ID 입니다.
- **응답을 잃어도**(청구는 됐는데 끊김) 먼저 조회로 확인합니다. 조회도 안 되면 실패로 단정하지 않고
  "처리 중" 으로 두어 **회차 주문을 취소하지 않습니다** — 실패로 처리하면 카드는 긁혔는데 주문이
  취소되고, 다음 시도가 이중 청구가 됩니다. 다음 청구가 같은 결제 ID 로 다시 묻습니다(웹훅이 먼저
  오면 웹훅이 그 주문을 확정합니다).
- **웹훅이 청구 응답보다 먼저 와도** 한 거래로 셉니다. 포트원은 웹훅과 API 응답의 순서를 보장하지 않아서,
  청구 응답을 기다리는 사이 웹훅이 그 회차 주문을 먼저 결제 완료로 만들 수 있습니다. 그때 청구 쪽은 자기 시도
  기록을 치우고 먼저 적힌 결제를 따릅니다 — 전에는 그 회차가 "실패" 로 세어지고 끝나지 않은 기록이 남았으며,
  **가입 첫 결제에서는 카드가 긁혔는데 손님이 오류(500)를 받았습니다.**
- **가입 첫 결제의 결과를 모르면**(응답도 조회도 잃었다) 가입 응답은 "처리 중" 이고, 스윕이 5분 뒤부터 같은
  결제 ID 로 다시 물어 결제됐으면 구독을 열고, 거절되면 가입을 거둡니다(첫 회차 주문 취소·재고 복원, 구독은
  이유와 함께 해지로 남는다). 전에는 그런 구독을 아무도 끝내지 않았습니다.
- 카드사가 거절한 이유(한도 초과·정지 카드)는 손님이 고칠 수 있으므로 내 정기배송 화면·알림에 그대로
  보여 줍니다. 그 밖의 서버 사정은 기록에만 남깁니다.

같은 포트원 계정으로 **본인인증**(성인 상품·한 사람 한 계정)도 켤 수 있습니다 — [본인인증](identity.md).

## 관리자가 결제된 주문을 취소·환불로 바꾸면

관리 화면의 주문 상태에서 결제된 주문을 **취소** 또는 **환불**로 바꾸면 결제를 먼저 전액 환불합니다
(PG 에 취소를 보내고 결제 기록을 환불로). 환불이 실패하면 상태를 바꾸지 않고, 허용되지 않은 전이
(예: 배송중 → 취소)는 환불을 보내기 **전에** 거절합니다 — 돈이 나간 뒤 상태 전이가 막히면 돈과 기록이
어긋나기 때문입니다. 전에는 상태만 바뀌어서, 카드 결제를 취소해도 돈이 돌아가지 않은 채 손님에게
취소·환불 안내가 나갔습니다.

## 결제 흐름

```
1. 고객이 주문 생성        POST /orders  (idempotencyKey 권장)
        │  → 주문번호, 총액
        ▼
2. 프론트엔드가 PG 위젯 호출 (클라이언트 키 사용)
        │  → PG가 paymentKey 발급
        ▼
3. 승인 요청               POST /payments/confirm
        │     { orderNo, provider, providerTid, amount }
        ▼
4. brick-shop이 검증
        ├─ PG에 승인 요청 → PG가 확인한 실제 금액 수신
        ├─ 주문 총액과 대조 ─── 불일치 → PG 취소 + 실패 기록
        ├─ 중복 거래 확인 ───── 중복 → 409
        └─ 상태 머신으로 paid 전이 (재고는 주문 시점에 이미 차감됨)
```

## 왜 이렇게 방어하는가

커머스에서 결제는 틀리면 **바로 돈이 새는** 경로입니다. 다음을 명시적으로 막습니다.

### 1. 금액 위조

클라이언트가 보낸 금액을 절대 신뢰하지 않습니다.
**PG가 확인한 실제 승인 금액**과 **DB의 주문 총액**이 정확히 일치할 때만 승인합니다.
불일치하면 즉시 PG 취소를 시도하고 실패로 기록합니다 — 공격이거나 심각한 버그이므로
조용히 넘기지 않습니다.

### 2. 중복 승인

`shop_payments (provider, provider_tid)` 에 unique 인덱스가 있습니다.
같은 PG 거래로 두 번 승인 처리하는 것을 **DB가** 막습니다.

- 같은 거래 재전송(웹훅 재시도) → 멱등하게 성공 반환
- 다른 거래로 같은 주문 재결제 → 409 + PG 취소 시도

### 3. 주문 중복 (네트워크 재시도)

주문 생성에 `idempotencyKey` 를 넣으면 같은 키로는 주문이 한 번만 만들어집니다.
결제 직전 재시도로 주문이 두 번 생기면 **재고가 이중 차감**되므로 중요합니다.

```json
POST /api/plugins/brick-shop/orders
{ "items": [...], "orderer": {...}, "idempotencyKey": "<UUID>" }
```

### 4. 무통장입금 권한

입금 확인은 **관리자만** 할 수 있습니다. 고객이 스스로 결제완료로 바꿀 수 없습니다.

### 5. 민감정보

- 시크릿 키는 공개 API로 나가지 않습니다 (설정 여부만 반환)
- PG 응답은 화이트리스트로 걸러 저장합니다 — 카드번호·영수증 URL 등은 남기지 않습니다
- **실패 이유는 손님에게 그대로 가지 않습니다.** PG 가 돌려준 문장은 기록
  (`shop_payments.failure_reason`)과 로그에 남고, 손님에게는 게이트웨이가
  "보여도 된다"고 표시한 것(`customerReason`)만 보여줍니다. 없으면 일반 안내가
  나갑니다 — PG 서버가 닿지 않을 때 `TypeError: fetch failed` 가 결제 화면에
  뜨던 자리입니다. 손님은 무엇을 해야 할지 알 수 없고, 서버 사정이 밖으로 샙니다.

  게이트웨이는 **손님이 고칠 수 있는 사유일 때만** `customerReason` 을 채웁니다
  (카드 한도·잔액·비밀번호처럼 PG 가 코드와 함께 준 거절 사유). 전송 실패·
  타임아웃·PG 장애(5xx)·인증 실패(401/403)는 비워 둡니다.

## 환불

```
POST /api/plugins/brick-shop/admin/payments/refund
{ "orderNo": "20260825-000001", "amount": 10000, "reason": "일부 품절" }
```

- `amount` 를 생략하면 잔액 전액 환불
- 누적 환불액이 결제액을 넘을 수 없습니다 (코드 + DB CHECK 이중 방어)
- **전액 환불되면 주문이 `refunded` 로 전이되고 재고가 복원됩니다**
- 부분 환불은 주문 상태를 바꾸지 않고 이력만 남깁니다

## 새 PG 붙이기

플러그인 하나로 끝납니다. brick-shop을 수정하지 않습니다.

```ts
import { definePlugin } from "@brick/plugin-sdk";

export default definePlugin(async (ctx) => {
  const gateway = {
    provider: "mypg",
    displayName: "마이PG",

    async confirm({ orderNo, providerTid, claimedAmount }) {
      const res = await callMyPg(providerTid, claimedAmount);
      if (!res.ok) {
        return {
          // 기록·운영자용 — 그대로 저장되고 로그에 남는다
          failureReason: res.message,
          // 손님에게 보여도 되는 이유만 (카드 한도·잔액처럼 PG 의 거절 사유).
          // 네트워크·타임아웃·PG 장애는 비워 둔다 — 일반 안내가 나간다.
          customerReason: res.declineCode ? res.message : undefined,
          ok: false,
        };
      }
      return {
        ok: true,
        // 반드시 PG가 확인한 실제 금액을 반환해야 한다.
        // brick-shop이 이 값을 주문 총액과 대조한다.
        approvedAmount: res.amount,
        method: res.method,
        raw: res.safeFields,
      };
    },

    async cancel({ providerTid, amount, reason }) {
      const res = await cancelMyPg(providerTid, amount, reason);
      return res.ok ? { ok: true } : { ok: false, failureReason: res.message };
    },
  };

  await ctx.hooks.doAction("shop.payment.register", { gateway });
  return {};
});
```

**게이트웨이 구현자의 책임**: `approvedAmount` 는 반드시 PG가 실제로 승인한 금액이어야
합니다. 여기서 요청 금액을 그대로 되돌려주면 금액 검증이 무의미해집니다.

PG 인증 정보는 `ctx.settings` 에 저장하고, 공개 API로 시크릿을 반환하지 마세요.

## PG 호출 시 주의

- **타임아웃 필수** — 없으면 요청이 무한히 매달립니다 (토스 플러그인은 15초)
- **멱등키 전달** — PG가 지원하면 함께 보내 이중 승인을 PG 쪽에서도 막습니다
- **응답 필터링** — 민감 필드를 그대로 DB에 남기지 마세요
