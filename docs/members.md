# 회원 생애주기 — 약관 · 이메일 인증 · 탈퇴 · 휴면

이 문서가 다루는 것은 기능이 아니라 **사이트를 합법적으로 운영하기 위한 전제**입니다.
회원 탈퇴가 없는 사이트는 한국에서 운영할 수 없습니다.

> 이 문서와 Brick이 심어두는 기본 약관은 **법률 자문이 아닙니다.**
> 실제 서비스에 맞게 반드시 고쳐 쓰고, 필요하면 전문가의 검토를 받으세요.

---

## 약관과 동의

### 설치 직후 상태

Brick은 이용약관 · 개인정보 수집·이용 동의 · 광고성 정보 수신 동의(선택) 초안을
심어둡니다. 비워두면 가입이 막히기 때문입니다. 본문 첫 줄에 "초안입니다"라고
적혀 있으니 **관리자 → 약관**에서 고쳐 쓰세요.

### 필수와 선택

| 종류 | 필수 여부 | 비고 |
|---|---|---|
| `terms` 이용약관 | 항상 필수 | 선택으로 바꿀 수 없습니다 |
| `privacy` 개인정보 수집·이용 | 항상 필수 | 선택으로 바꿀 수 없습니다 |
| `marketing` 광고성 정보 수신 | 선택 | 거부해도 가입됩니다 |
| `third_party` 제3자 제공 | 선택/필수 | 서비스에 따라 다릅니다 |

**선택 항목을 필수로 강제하는 것은 위법입니다.** Brick은 선택 항목을 거부한
가입을 정상 처리하고, 거부했다는 사실도 이력에 남깁니다 — "물어봤고 거부했다"가
남아야 나중에 발송 여부를 판단하고 증명할 수 있습니다.

반대로 `terms`·`privacy`는 관리자가 선택으로 바꿀 수 없게 막았습니다.
필수 동의 없이 개인정보를 수집하는 설정을 실수로 만들 수 없어야 합니다.

### 개정하면 다시 동의받는다

약관을 고치면 **새 버전**이 만들어지고 이전 버전은 남습니다. 지우지 않는 이유는
"그 사람이 동의한 시점의 문서"를 보여줄 수 있어야 분쟁에서 쓸 수 있기 때문입니다.

개정 후 기존 회원은 `GET /api/agreements/pending` 에 항목이 잡히고,
`POST /api/agreements/accept` 로 재동의합니다. 필수 항목만 대상입니다 —
선택 항목의 개정으로 로그인을 막을 수는 없습니다.

`effective_at` 을 미래로 두면 그 시점부터 자동으로 바뀝니다(예약 개정).

### 동의 이력

`user_agreements` 에 종류 · 버전 · 동의 여부 · 시점 · IP 해시가 남습니다.
IP는 **원문을 저장하지 않습니다**(해시만) — 방문자 집계와 같은 원칙입니다(ADR-35).
"이 IP가 맞는지"는 대조로 답할 수 있고, 목록으로 뽑아볼 필요는 없습니다.

**탈퇴해도 이력은 남습니다.** "동의 없이 개인정보를 처리했다"는 주장에 답할 근거가
사라지면 이력이 아무것도 증명하지 못합니다. 남는 것은 동의 사실뿐이고,
개인정보는 파기됩니다.

### 만 14세 미만

가입 시 `ageConfirmed: false` 를 보내면 거부하고 법정대리인 동의 안내를 보냅니다.
**생년월일 전체를 받지 않습니다** — 확인에 필요한 최소는 "14세 이상인가"뿐이고,
필요 없는 개인정보는 받지 않는 것이 원칙입니다.

법정대리인 동의 절차 자체는 Brick이 제공하지 않습니다. 필요한 사이트는
운영자가 별도 절차(서면·본인인증)를 만들어야 합니다.

## 이메일 인증

가입하면 인증 메일이 나갑니다. **인증 실패가 가입을 막지는 않습니다** —
SMTP 설정이 없는 사이트에서 가입이 실패하면 설치 직후 아무도 들어올 수 없습니다.
계정은 만들어지고, 나중에 재발송할 수 있습니다.

- 토큰은 24시간 유효, 단회성
- 원문은 메일 링크에만 있고 DB에는 sha256 해시만 저장
- 재발송은 60초 간격 — 남의 주소를 넣어 메일 폭탄을 보내는 데 쓰이지 않게

### 이메일 변경

`POST /api/me/email/verify/send` 에 새 주소를 넣으면 그 주소로 인증 메일이 갑니다.
**인증이 끝난 뒤에** `users.email` 이 바뀝니다 — 먼저 바꾸면 잘못 입력한 주소로
계정이 넘어갑니다. 인증 대기 중에 다른 사람이 그 주소로 가입했다면 인증이 거부됩니다.

## 회원 탈퇴

### 무엇이 사라지고 무엇이 남는가

두 법이 반대 방향을 가리킵니다. 개인정보보호법은 지체 없는 파기를,
전자상거래법은 거래 기록 5년 보존을 요구합니다. Brick은 **개인을 지우고 거래를
남깁니다.**

| | 처리 |
|---|---|
| 이메일 · 이름 · 비밀번호 | **즉시 파기** (익명값으로 덮음) |
| 로그인 세션 · 소셜 연결 | 즉시 삭제 |
| 쪽지 | 삭제 (사적 대화, 보존 의무 없음) |
| 장바구니 | 삭제 (구매 전 데이터) |
| 게시글 · 댓글 | 기본은 **유지 + 작성자 익명화**. 회원이 삭제를 선택할 수 있음 |
| 상품 후기 | 유지 + 작성자 익명화 (다른 구매자에게 유용한 정보) |
| 비밀 문의 | **삭제** (배송지·연락처가 들어 있는 경우가 많음) |
| 주문 · 결제 | **유지**, 회원 연결만 해제 (전자상거래법 5년) |
| 포인트 잔액 | **소멸** (승계 제도 없음). 원장 기록은 정산을 위해 유지 |
| 동의 이력 | 유지 (증명 근거) |

게시글을 기본으로 남기는 이유: 토론이 통째로 사라지면 남은 사람들의 글이
읽을 수 없게 됩니다. 남길 때도 작성자는 "탈퇴한 회원"으로 바뀝니다.

### 탈퇴 전 안내

`GET /api/me/withdraw/preview` 가 무엇이 사라지는지 알려줍니다.
"정말 탈퇴하시겠습니까?"만 묻는 것은 불충분합니다 — 특히 포인트 소멸과
진행 중인 주문은 미리 알리지 않으면 나중에 항의가 들어옵니다.

각 플러그인이 자기 손실을 설명합니다(ADR-38). 포인트 플러그인이 없는 사이트에서는
포인트 안내가 나오지 않습니다.

### 확인 절차

비밀번호를 다시 확인합니다 — 세션이 탈취된 상태에서 계정을 지워버리는 경로를
닫습니다. 소셜 전용 계정은 비밀번호가 없으므로 **"탈퇴합니다"** 를 정확히
입력받습니다.

### 마지막 관리자는 탈퇴할 수 없다

허용하면 사이트에 들어갈 방법이 사라지고, DB를 직접 만지지 않으면 복구할 수
없습니다. 다른 관리자를 먼저 지정해야 합니다.

### 재가입

원래 이메일로 다시 가입할 수 있습니다. 탈퇴한 계정의 이메일은
`withdrawn-<랜덤>@withdrawn.invalid` 로 바뀌어 있으므로 충돌하지 않습니다.
과거 데이터는 승계되지 않습니다 — 연결할 방법이 없기 때문입니다(그게 파기의 의미입니다).

## 휴면 계정

장기 미접속 계정을 표시합니다.

**자동 전환하지 않습니다.** 개인정보보호법은 파기·분리 전 **사전 통지**를
요구하므로, 통지 없이 자동 전환하면 그 자체가 위반입니다. Brick은 대상 목록만
제공하고(`GET /api/admin/users/dormant-candidates?months=12`), 전환은 관리자가
통지 후에 실행합니다.

**휴면 계정은 로그인하면 풀립니다.** 비밀번호가 맞으면 본인 확인의 기준이 평소
로그인과 같으므로 더 높은 문턱을 둘 이유가 없고, 해제 경로가 없으면 휴면은
되돌릴 수 없는 함정이 됩니다(사용자는 관리자에게 연락할 방법도 모릅니다).

## API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/agreements` | 가입 화면이 보여줄 약관 (비로그인) |
| GET | `/api/agreements/pending` | 재동의가 필요한 약관 |
| POST | `/api/agreements/accept` | 개정 약관 재동의 |
| GET | `/api/me/agreements` | 내 동의 이력 |
| GET | `/api/me/profile` | 내 정보 (인증 여부 · 수신 동의 포함) |
| PUT | `/api/me/marketing` | 광고 수신 동의 변경 |
| POST | `/api/me/email/verify/send` | 인증 메일 발송 (주소 변경 포함) |
| POST | `/api/email/verify` | 토큰으로 인증 완료 (비로그인 가능) |
| GET | `/api/me/withdraw/preview` | 탈퇴 전 안내 |
| POST | `/api/me/withdraw` | 탈퇴 실행 |
| GET | `/api/admin/agreements` | 약관 목록 (관리자) |
| POST | `/api/admin/agreements` | 개정 발행 (관리자) |
| POST | `/api/admin/users/:id/withdraw` | 대행 탈퇴 (관리자) |
| GET | `/api/admin/users/dormant-candidates` | 휴면 대상 (관리자) |
| POST | `/api/admin/users/:id/dormant` | 휴면 전환 (관리자) |

### 가입 요청 형식

`POST /api/register` 에 동의가 포함됩니다.

```json
{
  "email": "user@example.com",
  "password": "password123",
  "displayName": "홍길동",
  "agreements": { "terms": true, "privacy": true, "marketing": false },
  "ageConfirmed": true
}
```

필수 항목을 빠뜨리면 400과 함께 무엇에 동의해야 하는지 알려줍니다.

## 플러그인을 만든다면

개인정보를 저장하는 플러그인은 **삭제 방법을 등록해야 합니다.** 등록하지 않으면
탈퇴 후에도 그 데이터가 남아 위법 상태가 됩니다.

```ts
ctx.registerDataEraser({
  label: "내 플러그인",
  order: 50,
  async erase({ tx, userId, deletePosts }) {
    const { rows } = await tx.execute(sql`
      DELETE FROM my_table WHERE user_id = ${userId}::uuid RETURNING id
    `);
    return rows.length ? [`기록 ${rows.length}건 삭제`] : [];
  },
  // 되돌릴 수 없는 손실은 반드시 미리 알린다
  describe: async ({ userId }) => [{ label: "...", detail: "..." }],
});
```

반드시 넘어온 `tx` 를 쓰세요. `ctx.db` 를 쓰면 트랜잭션 밖으로 나가고,
"개인정보는 지웠는데 계정 익명화가 실패해 되돌아간" 상태가 가능해집니다.

예외를 삼키지 마세요. 실패하면 탈퇴 전체가 되돌아가는 것이 맞습니다 —
지우지 못한 것을 지웠다고 말하지 않기 위해서입니다.

## 검증

```bash
DATABASE_URL=postgresql://brick:brick@localhost:5432/brick bash scripts/smoke-member.sh
```

93개 항목이 실제 PostgreSQL로 확인합니다. "파기했다"는 응답을 믿지 않고
**DB의 실제 행**을 들여다봅니다 — 이메일 원문이 남아 있지 않은지, 주문은 남았는지,
감사 로그에 원래 이메일이 새지 않았는지.
