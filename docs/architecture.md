# Brick 아키텍처 결정 기록 (ADR)

이 문서는 Brick의 뼈대를 결정한 이유를 기록한다. 코드를 고치기 전에 이 문서와 충돌하는지 먼저 확인할 것.

## ADR-1. 배포 단위는 "하나의 앱 컨테이너 + PostgreSQL"

- 사용자에게 Brick은 단일 제품이다. 내부가 Next.js/NestJS 두 프로세스여도 사용자가 관리하지 않는다.
- `docker compose up -d` = 설치. `docker compose pull && up -d` = 업데이트.
- PHP 호스팅(FTP-only) 지원은 하지 않는다. Node 런타임이 없는 환경을 억지로 지원하면 아키텍처가 망가진다.

## ADR-2. Next.js(3000, 공개) → rewrite → NestJS(3001, 내부)

- Next.js를 custom server로 감싸지 않는다 — ISR/정적 최적화/스트리밍을 잃는다. SEO가 1급 목표이므로 손해.
- NestJS는 외부에 노출하지 않는다. 공개 포트는 3000 하나.
- 같은 컨테이너 안에서 두 프로세스를 entrypoint가 함께 띄운다.

## ADR-3. Brick Core는 PostgreSQL만으로 완전히 동작한다

- Cache/Queue/Lock/Storage는 전부 Provider 인터페이스(@brick/core) 뒤에 있다.
- 기본 구현: UNLOGGED 테이블 캐시, SKIP LOCKED 큐, advisory lock, 로컬 디스크 스토리지.
- REDIS_URL / STORAGE_DRIVER 설정 시에만 Redis/S3 구현으로 교체. docker-compose 기본 구성에 Redis/MinIO를 넣지 않는다.

## ADR-4. ORM은 Drizzle

- Prisma는 단일 schema.prisma를 강제한다 → 플러그인이 자기 테이블을 들고 올 수 없다.
- Drizzle은 스키마가 분산 가능한 평범한 TS 코드고, 플러그인은 순수 SQL 마이그레이션(migrations/*.sql)을 동봉한다.
- 플러그인 테이블은 `<plugin>_` 접두사, 이력은 plugin_migrations 테이블로 멱등 관리.

## ADR-5. 플러그인은 단일 프로세스 안에서 실행된다

- 플러그인마다 프로세스/포트를 주는 방식은 설치형 CMS에서 지옥이 된다. 금지.
- PluginLoader가 dynamic import로 사전 빌드된 dist/index.js를 로드한다. **서버는 절대 빌드하지 않는다.**
- 플러그인은 PluginContext를 통해서만 Brick과 상호작용한다 (hooks, routes, blocks, settings, db, cache, queue, storage).
- 비활성화 시 HookBus 등록/라우트/블록이 모두 회수된다.

## ADR-6. Theme = 빌드 없는 런타임 템플릿, React는 Block에만

가장 중요한 결정. "theme.zip 업로드 = 즉시 적용"이 성립하려면 테마가 빌드 파이프라인을 타면 안 된다.

- Theme: `templates/*.html`(최소 템플릿 문법) + 디자인 토큰 + 정적 자산. 레이아웃/스킨 담당.
- Block: React/서버 렌더 컴포넌트. Core와 Plugin이 공급하며, 빌드 대상은 이쪽뿐.
- 페이지 = 테마 레이아웃 + 블록 트리(JSONB). 블록의 render()는 항상 HTML을 반환할 수 있어야 한다(SEO).
- 템플릿 문법은 의도적으로 최소({{var}}, {{{raw}}}, #if, #each). 로직이 필요하면 Block으로 만든다.

## ADR-7. 확장 설치 UX는 WordPress와 동일하게

- 관리자 → 업로드 → plugin.zip/theme.zip → 압축 해제 → manifest 검증 → 활성화.
- 확장 디렉터리(plugins/, themes/, uploads/)는 Docker 볼륨 — 이미지 업데이트에도 유지된다.
- 활성화 상태는 DB(installed_plugins/installed_themes)에 기록되어 부팅 시 복원된다.

## ADR-8. 설치 마법사는 최소 입력

- DB 접속 정보를 묻지 않는다 — DATABASE_URL은 compose가 이미 주입했다.
- 사이트명 + 관리자 이메일/비밀번호만 입력. install.state가 installed가 되기 전에는 전 라우트가 /install로 리다이렉트.

## 로드맵 (초안)

1. **M1 — 코어 부팅**: 인증(세션), 관리자 셸, 페이지 CRUD, 테마 렌더 파이프라인 완성
2. **M2 — 확장 시스템**: ZIP 설치 API(yauzl), 플러그인/테마 관리 UI, brick-board 완성(글쓰기/댓글/첨부)
3. **M3 — 페이지 빌더**: 블록 편집 UI, 블록 캐시(태그 무효화), 메뉴 편집
4. **M4 — 운영 품질**: 백업/복원, 업데이트 마이그레이션 검증, 권한 세분화, i18n
5. **M5 — 생태계**: 플러그인 레지스트리, `create-brick-plugin` 템플릿, 문서 사이트

## ADR-9. 공개 사이트는 Next.js Route Handler가 완성 HTML을 그대로 응답한다

- catch-all을 React 페이지로 만들면 테마 HTML(완전한 문서)이 React 문서 안에 중첩되어
  `<title>`/`<meta>`가 `<body>`에 갇힌다 — SEO 1급 목표와 정면 충돌.
- 그래서 `app/[[...slug]]/route.ts`가 API의 렌더 파이프라인(`GET /api/render/page`)을 호출해
  완성 HTML을 상태코드와 함께 그대로 응답한다. 테마가 문서 전체를 소유한다(WordPress 모델).
- React는 관리자(/admin)와 설치 마법사(/install)에만 쓴다. 정적 라우트가 catch-all보다 우선한다.
- 공개 페이지 캐시는 Next(ISR)가 아니라 API 쪽 태그 캐시가 담당한다
  ("pages" / "page:<slug>" 태그, 페이지·테마·플러그인 변경 시 무효화).

## ADR-10. 마이그레이션은 부팅 시 자동 적용된다

- 설치형 CMS의 업데이트 경험은 "파일 교체 후 관리자에서 클릭" 수준이어야 한다.
  별도 마이그레이션 명령을 외우게 하면 `docker compose pull && up -d` 라는 약속이 깨진다.
- 그래서 API 프로세스가 HTTP 리스닝 **전에** 마이그레이션을 실행한다.
  advisory lock으로 다중 인스턴스 동시 부팅에도 한 번만 적용된다.
- 실패하면 프로세스를 종료한다(exit 1). 깨진 스키마로 서비스하는 것보다 안전하고,
  컨테이너 재시작 루프로 운영자가 즉시 인지한다.
- **락과 연결에는 반드시 타임아웃을 둔다.** 초기 구현은 `pg_advisory_lock` 을 그대로 썼는데,
  이 함수는 다른 세션이 락을 쥐고 있으면 **무한 대기**한다. 이전 인스턴스가 마이그레이션 중
  비정상 종료해 커넥션이 남으면 부팅이 아무 로그도 없이 멈춘다 — 운영자가 원인을 찾을 수 없다.
  (실제로 테스트 중 발견) 그래서 `pg_try_advisory_lock` 을 폴링하고 제한 시간을 넘기면
  `pg_stat_activity` 조회 방법까지 담은 에러로 실패시킨다. 연결에도 타임아웃을 둬
  닿지 않는 DB에서 즉시 원인을 알린다.
- down 마이그레이션은 제공하지 않는다 — 롤백은 백업 복원이 유일하게 안전한 경로다.
- 플러그인 마이그레이션은 활성화 시점에 적용되고, ZIP 재업로드 시 자동 재적재로 새 버전이 반영된다.
- `BRICK_AUTO_MIGRATE=false` 로 끌 수 있다(대규모 운영에서 수동 제어가 필요한 경우).

## ADR-11. 배포 산출물은 pnpm deploy로 만든다

- pnpm 워크스페이스의 `node_modules`는 전역 스토어를 가리키는 심볼릭 링크라
  Docker 이미지에 그대로 복사하면 런타임에 모듈을 찾지 못한다.
- `pnpm deploy --filter=@brick/api --prod` 가 자기완결적 번들을 만든다. Dockerfile은 이것을 복사한다.
- Next.js는 `output: "standalone"` + `outputFileTracingRoot`(모노레포 루트)로 별도 번들을 만든다.
- CI가 이 두 경로를 매번 검증한다 — 로컬에서 되는데 이미지에서 깨지는 사고를 막는다.

## 알려진 제약

- **한국어 전문 검색**: `to_tsvector('simple', ...)`는 DB 로케일이 C면 한글을 토큰으로 인식하지
  못하고, 교착어 특성상 조사/어미 때문에 `simple` 사전으로는 매칭 품질이 낮다.
  그래서 코어 검색은 `ILIKE` 기반으로 구현했다 — 정확하지만 데이터가 많아지면 느려진다.
  운영 시 `pg_trgm` GIN 인덱스를 추가하면 코드 변경 없이 가속된다([운영 가이드](operations.md#한국어-검색)).
- **단일 인스턴스 전제**: 요청 제한이 인메모리다. 다중 인스턴스로 확장할 때는
  `CacheProvider` 기반 구현으로 교체해야 한다.
- **감사 로그/2FA/이메일 미구현**: [보안 문서](security.md#알려진-제약) 참고.

## ADR-12. 플러그인 관리 화면은 선언적 리소스로 생성한다

문제: 플러그인은 ZIP으로 배포되므로 Next.js 라우트(React 페이지)를 추가할 수 없다.
그런데 쇼핑몰처럼 큰 기능은 관리 화면 없이는 성립하지 않는다.

검토한 선택지:
- (a) 플러그인이 Next.js 소스를 포함 → 설치 시 재빌드 필요. 테마와 같은 이유로 탈락(ADR-6).
- (b) 플러그인이 관리자 HTML을 서버 렌더 → 폼 상태 관리를 매 플러그인이 재구현해야 한다.
- (c) **플러그인이 "무엇을 편집할 수 있는가"만 선언하고 코어가 UI를 생성** ← 선택

`ctx.registerAdminResource({ fields, basePath, ... })` 로 필드 스키마를 등록하면
코어 관리자(`/admin/x/<plugin>/<resource>`)가 목록·폼·검증·페이지네이션을 런타임에 만든다.
플러그인은 REST 규약(GET/POST/PUT/DELETE)만 구현한다.

효과: 워드프레스 플러그인이 각자 관리 화면을 짜서 UI가 파편화되는 문제를 피하고,
빌드 없이 ZIP 설치만으로 일관된 관리 화면을 얻는다. brick-shop이 이 방식으로
관리 화면 4개를 만든다.

한계: 완전히 자유로운 커스텀 화면(대시보드형 차트 등)은 만들 수 없다.
그런 경우 `registerAdminMenu` + 자체 페이지 조합이 필요하며, 향후 과제다.

## ADR-13. 플러그인에 진짜 트랜잭션을 제공한다

초기에 플러그인 DB 표면을 `execute()` 하나로 두고, 트랜잭션은 플러그인이
`execute("BEGIN")` / `execute("COMMIT")` 으로 처리하게 했다. **이것은 조용히 깨진다** —
커넥션 풀에서 매 `execute` 가 다른 커넥션을 받을 수 있어 BEGIN과 후속 문장이
같은 트랜잭션에 있다는 보장이 없다. (쇼핑몰 재고 테스트에서 실제로 발견)

그래서 `PluginDb` 계약에 `transaction(fn)` 을 추가했다. 콜백 전체가 하나의 커넥션에서
실행되고 예외 시 롤백된다. 재고 차감·결제처럼 원자성이 필요한 로직은 이것을 써야 한다.

함께 배운 것: 동시성이 있는 감소 연산은 조회 후 차감이 아니라
`UPDATE ... WHERE stock >= qty RETURNING` 형태의 조건부 원자적 UPDATE로 해야 한다.
주문번호도 `count(*)+1` 로 만들면 동시 주문에서 충돌하므로 시퀀스를 쓴다.

## ADR-14. 결제는 게이트웨이 추상화로 분리하고, 금액은 PG 응답과 대조한다

특정 PG에 커플링되면 국가·사업자마다 코어를 고쳐야 한다. 그래서 `PaymentGateway`
인터페이스만 brick-shop이 알고, PG별 구현은 별도 플러그인이 `shop.payment.register`
훅으로 등록한다(brick-pay-toss가 레퍼런스).

핵심 방어는 **금액 검증 위치**다. 게이트웨이는 "PG가 실제로 승인한 금액"을 반환할
책임만 지고, 주문 총액과의 대조는 brick-shop이 한다. 게이트웨이를 신뢰하지 않는 구조이므로
서드파티 PG 플러그인이 부실해도 금액 위조가 통과하지 않는다.
불일치 시 즉시 PG 취소를 시도하고 실패로 기록한다 — 조용히 넘기면 대조가 무의미해진다.

중복 승인은 코드가 아니라 **DB가** 막는다: `shop_payments (provider, provider_tid)` unique.
같은 웹훅이 재전송되어도 재고·매출이 이중 계상되지 않는다. 주문 자체의 중복은
`idempotency_key` unique로 막는다 — 결제 직전 네트워크 재시도가 재고를 이중 차감하는 것을
방지하는 실전 요구사항이다.

## ADR-15. 메일은 Provider로 두고, 미설정 시 콘솔로 폴백한다

비밀번호 재설정은 프로덕션 필수 기능이지만, SMTP를 요구하면 "설치가 쉬워야 한다"는
전제(ADR-1)가 깨진다. 그래서 `MailProvider`를 두고 SMTP 미설정 시 `LogMailProvider`가
콘솔에 출력한다 — 메일 서버 없이도 재설정 흐름을 개발·테스트할 수 있다.

대가: 프로덕션에서 SMTP를 잊으면 재설정 링크가 로그에 남아 로그 접근자가 계정을 탈취할
수 있다. 그래서 보안 문서와 배포 체크리스트에 명시했다. (부팅을 막지는 않는다 —
메일 없이도 CMS는 정상 동작해야 하기 때문)

메일 발송 실패는 예외를 던지지 않고 `false`를 반환한다. 메일 서버 장애가 회원가입이나
주문을 막아서는 안 된다.

## ADR-16. 감사 로그는 기록 실패가 주 동작을 막지 않는다

권한 변경·계정 정지·확장 설치는 사고 시 추적이 반드시 필요하므로 기록한다.
단, 감사 로그 INSERT가 실패해도 페이지 저장이나 권한 변경은 성공해야 한다 —
로그를 남기지 못했다는 이유로 실제 작업을 되돌리면 가용성이 낮아진다.
그래서 `AuditService.record()` 는 예외를 삼키고 경고만 남긴다.

본문 같은 큰 데이터와 비밀번호·토큰은 담지 않는다. "무엇에 대한 어떤 동작"과 짧은 요약만
남기며, 180일이 지나면 정리 작업이 지운다.

## ADR-17. DB 설정이 없으면 실패하지 않고 설치 모드로 뜬다

초기 설계는 `DATABASE_URL` 을 필수로 요구했다. Docker에서는 compose가 주입하므로 문제없지만,
**FTP로 파일만 올리는 호스팅에서는 사용자가 환경변수를 설정할 수단이 없다.**
그누보드/워드프레스가 웹 화면에서 DB 정보를 받아 설정 파일을 쓰는 이유가 이것이다.

그래서:
- DB 설정이 없으면 부팅을 거부하지 않고 **설치 모드**로 뜬다. 이 모드는 `SetupAppModule` 만
  올리며 DB 연결 풀을 만들지 않는다.
- 설치 화면이 DB 정보를 받아 `data/brick.config.json` 에 쓴다(권한 0600).
  세션 시크릿은 이때 자동 생성한다 — 사용자에게 랜덤 문자열을 만들라고 하면 약한 값을 쓴다.
- 우선순위는 **환경변수 > 설정 파일**. Docker/k8s에서 환경변수가 이기므로 컨테이너를
  다시 만들어도 옛 파일이 방해하지 않는다.
- 설치 모드에서 `/healthz` 는 200, `/readyz` 는 503이다. 오케스트레이터가 설치 전 인스턴스를
  정상으로 오인하지 않게 한다.

설정 파일을 쓴 뒤에는 재시작이 필요하다(연결 풀과 마이그레이션이 부팅 시점에 만들어진다).
무중단 적용을 위해 런타임 재구성을 넣는 것보다, 재시작을 명시적으로 안내하는 쪽이 단순하고
실패 모드가 적다고 판단했다.

## ADR-18. 공개 사이트의 /api 프록시는 rewrites가 아니라 Route Handler로 한다

Next.js `rewrites` 의 destination은 `output: "standalone"` 빌드에서 **빌드 시점에 고정**된다.
즉 빌드할 때의 API 포트가 산출물에 박힌다. cPanel/Plesk는 포트를 임의로 배정하므로
배포본이 다른 포트로 뜨면 `/api/*` 가 전부 깨진다. (실제로 발견한 버그)

그래서 `/api/*`, `/uploads/*`, `/themes/*` 를 Route Handler(`src/lib/proxy.ts`)로 프록시한다.
Route Handler는 매 요청마다 환경변수를 읽으므로 런타임에 결정된다.
파일 업로드는 `body: req.body` + `duplex: "half"` 로 스트리밍해 메모리에 모으지 않고,
`Set-Cookie` 는 여러 개일 수 있으므로 `getSetCookie()` 로 개별 전달한다.

## ADR-19. 배포본은 node_modules를 루트에 둔다

플러그인 `dist/index.js` 는 `drizzle-orm`, `@brick/plugin-sdk` 를 bare import한다.
`pnpm deploy` 산출물은 `api/node_modules` 에 의존성을 두므로, 플러그인이 이를 찾지 못한다.

단순히 `plugins/*/node_modules` 를 만들어 복사하면 **drizzle 사본이 둘이 되어**
`sql` 객체의 identity가 어긋나 쿼리가 인식되지 않는다.

그래서 `node_modules` 를 배포본 **루트**로 옮긴다. Node는 상위로 올라가며 탐색하므로
`api/dist/main.js` 와 `plugins/*/dist/index.js` 가 **같은 사본**을 쓴다.
심볼릭 링크를 쓰지 않으므로 FTP 업로드에서도 안전하다.

## ADR-20. 런처는 시작할 때 고아 자식 프로세스를 정리한다

배포본의 `server.js` 는 api와 web을 자식 프로세스로 띄운다. 런처가 `SIGKILL` 로 죽으면
자식이 살아남아 포트를 계속 점유하고, 다음 시작이 `EADDRINUSE` 로 실패한다.
호스팅 패널의 강제 재시작에서 실제로 일어난다.

그래서 자식 PID를 `data/brick.pid` 에 기록하고, 시작할 때 남아 있는 PID에 SIGTERM을 보낸 뒤
포트가 풀릴 때까지 기다린다. 정상 종료 경로에서는 PID 파일을 지운다.

## ADR-21. 게시판 권한은 4단 역할로, 그누보드의 10단 레벨을 따르지 않는다

그누보드는 회원 레벨 1~10으로 게시판 권한을 정한다. 유연하지만 "레벨 5는 무엇인가"를
관리자가 매번 정의해야 하고, 사이트마다 의미가 달라 플러그인이 해석할 수 없다.

Brick은 코어 역할 모델(guest/member/manager/admin)을 그대로 쓴다. 게시판마다
읽기·쓰기·댓글·다운로드 권한을 이 4단 중에서 고른다. 잃는 것은 세분성이고,
얻는 것은 **플러그인 간 해석 가능성**이다 — 어떤 플러그인이든 "manager 이상"의 의미를 안다.

더 세밀한 권한이 필요하면 훅으로 확장한다. 코어 역할을 10단으로 늘리는 것은
모든 플러그인의 권한 검사를 바꾸는 일이므로 하지 않는다.

## ADR-22. 답변형은 materialized path로 정렬한다

그누보드는 `wr_num`(음수)과 `wr_reply`(문자 코드) 조합으로 계층을 표현한다.
동작하지만 의미를 읽기 어렵고, 답변 깊이가 늘면 문자 코드가 고갈된다.

Brick은 `thread_id` + `thread_path`(예: `0001.0002`) + `depth` 를 쓴다.
목록 정렬은 `ORDER BY thread_created_at DESC, thread_path ASC` 하나로 끝난다 —
스레드가 통째로 묶이고 새 스레드가 위로 온다.

동시 답변이 같은 path를 갖지 않도록 스레드 원글을 `FOR UPDATE` 로 잠근 뒤 형제 수를 센다.
잠그지 않으면 두 답변이 같은 순번을 받아 정렬이 뒤섞인다.

## ADR-23. 플러그인 라우트에 파일·IP·원본 응답을 제공한다

게시판을 만들며 라우트 계약의 공백이 드러났다:

- **파일 업로드** — 플러그인이 multipart를 받을 방법이 없었다. `req.files()` 를 추가했다.
  지연 호출이므로 업로드를 받지 않는 라우트는 본문을 읽지 않는다.
- **클라이언트 IP** — 도배 방지에 필요하다. `req.ip` 를 추가했다(코어가 프록시 헤더를 해석한 값).
- **JSON이 아닌 응답** — RSS·사이트맵을 낼 방법이 없었다. `rawResponse()` 를 추가했다.
  `instanceof` 대신 구조적 표시(`__brickRaw`)를 쓴다 — 모듈 사본이 다를 수 있는 환경에서
  `instanceof` 는 신뢰할 수 없다.

함께 고친 것: multipart 파일 개수 제한이 코어에 1로 박혀 있어 플러그인이 여러 파일을
받을 수 없었다. 개수 정책은 각 기능이 정하고(게시판은 `max_files`), 코어는 상한만 둔다.
그리고 `HEAD` 를 `GET` 라우트로 매칭한다 — 하지 않으면 `curl -I` 가 404를 받는다.

## ADR-24. 블록은 요청 컨텍스트를 받는다 (페이지 하나가 여러 화면을 처리)

게시판 상세(`/board/free/<글id>`)를 만들며 두 가지 공백이 드러났다:

1. **블록이 요청을 몰랐다** — props만 받으므로 URL에 따라 내용을 바꿀 수 없었다.
2. **페이지가 정확한 slug만 매칭했다** — `/board/free/123` 이 `board/free` 페이지를 찾지 못했다.

그래서 `BlockRenderContext { path, pathTail, query, user, children }` 를 도입하고,
페이지 조회를 **상위 경로로 내려가며 시도**하도록 바꿨다. 매칭된 나머지가 `pathTail` 이다.
게시판 블록은 이 값으로 목록/상세/글쓰기/수정을 구분한다 — 글마다 페이지를 만들 필요가 없다.

함께 처리한 것: 렌더 캐시가 **비로그인 요청에만** 적용되도록 바꿨다.
로그인 사용자의 렌더에는 "수정" 버튼이나 비밀글 본문처럼 사용자별 내용이 들어가므로,
캐시하면 다른 사용자에게 새어 나간다. 캐시 키에 쿼리스트링도 포함한다(검색·페이지네이션 분리).

## ADR-25. 사용자 HTML은 저장 시점에 허용 목록으로 새니타이즈한다

게시판 본문은 일반 사용자·비회원이 쓰는 HTML이고 상세 화면에서 그대로 렌더된다.
관리자가 쓰는 페이지 본문(`core/rich-text`)과 신뢰 수준이 다르다 — **걸러야 한다.**

결정:
- **허용 목록** 방식. 차단 목록은 우회가 계속 발견된다.
- **저장 시점**에 정제한다. 렌더할 때마다 비용을 치르지 않고, DB에 위험한 값이 남지 않는다.
- **작성과 수정 양쪽**에 적용한다. 한쪽을 빼먹으면 그것이 우회 통로가 된다.
- **댓글은 서식을 허용하지 않는다.** 평문으로 저장하고 렌더 시 이스케이프한다 —
  표면을 줄이는 것이 안전하고, 댓글에 HTML이 필요한 경우가 드물다.
- 외부 라이브러리를 쓰지 않는다. 플러그인 배포본을 가볍게 유지해야 한다(FTP 배포).

20개 XSS 벡터(이벤트 핸들러·스킴 숨김·엔티티 인코딩·style expression·중첩 태그)로 검증했다.

## ADR-26. 플러그인 간 협력에는 서비스 레지스트리를 쓴다 (훅으로 부족한 경우)

훅(action/filter)으로 표현할 수 없는 협력이 있다:

- **호출자의 트랜잭션에 참여**해야 하는 경우. 주문 생성과 포인트 차감이 분리되면
  하나만 성공했을 때 잔액이 어긋난다. 액션은 fire-and-forget이고 필터는 값만 변형한다.
- 여러 메서드를 가진 **인터페이스**를 노출해야 하는 경우.

그래서 `ctx.provideService(name, impl)` / `ctx.useService<T>(name)` 를 추가했다.
brick-point가 `"points"` 를 공개하고 brick-shop이 주문 트랜잭션 안에서 차감한다.

지켜야 하는 규칙:
- **사용 시점에 조회한다.** 활성화 시점에 조회하면 플러그인 활성화 순서에 의존하게 되어,
  소비자가 먼저 켜진 경우 서비스를 못 찾는다.
- **반드시 null을 처리한다.** 제공 플러그인이 없어도 동작해야 한다
  (포인트가 없어도 쇼핑몰은 팔려야 한다).
- 소비자는 **필요한 메서드만 좁게 선언한다.** brick-shop은 `PointsPort` 를 자기 파일에
  정의해 brick-point에 대한 컴파일 의존을 만들지 않는다.
- 같은 이름을 두 플러그인이 제공하면 경고를 남긴다 — 어느 쪽이 쓰일지 예측할 수 없다.
- 비활성화 시 서비스 등록이 자동 해제된다.

훅으로 충분한 협력(적립 원인 통지 등)은 계속 훅을 쓴다. 서비스는 결합을 만들므로
트랜잭션 참여나 인터페이스 노출이 필요할 때만 쓴다.

## ADR-27. 포인트는 원장 + 잔여량으로 관리한다 (잔액 컬럼을 두지 않는다)

포인트는 돈에 준한다. 단순 잔액 컬럼은 세 가지를 못 한다:
감사 추적, 적립별 만료, FIFO 소비.

그래서 원장(`point_ledger`)에 적립 행마다 `remaining`(아직 쓰지 않은 양)과 `expires_at` 을 둔다.
**잔액 = 만료되지 않은 적립의 remaining 합.** 별도 잔액 컬럼이 없으므로
원장과 잔액이 어긋날 여지가 없다. 사용은 만료 임박한 것부터 깎고(FIFO),
적립 행을 `FOR UPDATE` 로 잠가 동시 사용의 초과 차감을 막는다.

멱등성은 `(user_id, kind, ref_type, ref_id)` unique 인덱스로 **DB가** 보장한다.
훅 재실행이나 결제 웹훅 재전송에서 이중 적립이 생기지 않는다.

`spend()` 는 잔액 부족 시 예외가 아니라 `false` 를 반환한다 —
호출자가 "포인트 없이 계속"을 선택할 수 있어야 한다.

## ADR-28. 캡차는 자체 구현을 기본으로 하고 상태를 두지 않는다

비회원 글쓰기를 허용하면서 스팸 방어가 도배 방지(작성 간격)뿐이면 실제 사이트는 즉시 뚫린다.
분산된 봇은 간격 제한을 우회한다.

reCAPTCHA/Turnstile을 기본으로 쓰지 않은 이유: API 키 발급이 필요하고, 그러면
"설치에 필요한 기술을 사용자에게 노출하지 않는다"(ADR-1)가 깨진다. 키 없이 동작해야 한다.

설계:
- **상태 없음.** 정답을 HMAC 서명 토큰에 담아 클라이언트에 넘긴다. DB 테이블이 없고
  다중 인스턴스에서도 동작한다.
- **1회용.** 통과한 토큰의 nonce를 캐시에 기록한다. 이것이 없으면 봇이 한 번 풀고
  그 토큰으로 무한히 글을 쓴다 — 캡차를 두는 의미가 없어진다.
- **비회원만.** 회원에게 매 글마다 요구하면 정상 사용자가 떠난다. 회원은 계정이 있으므로
  도배 방지와 계정 정지로 대응할 수 있다.
- **회원가입에서는 비밀번호 해싱보다 먼저 검사한다.** argon2는 비싸므로 봇이 그 비용을
  유발하기 전에 걸러야 한다.
- 이미지는 **서버 렌더에 넣지 않는다.** 캐시된 페이지에 같은 문제가 박히면 무의미해진다 —
  클라이언트가 매번 새로 받는다.

한계를 문서에 명시했다: SVG `<text>` 기반이라 OCR에 완전히 강하지 않다.
표적 공격에는 `CaptchaProvider` 를 구현하는 플러그인으로 교체한다.

## ADR-29. 플러그인 라우트는 구체적 경로가 파라미터 경로보다 우선한다

초기 매처는 등록 순서대로 첫 매칭을 반환했다. `/:id` 를 먼저 등록하면
`/cost` 요청이 그쪽으로 빨려 들어가 uuid 파싱 오류가 난다(실제로 발생).

플러그인 개발자가 등록 순서를 신경 쓰게 하는 것은 함정이다. 그래서 매처가
후보를 모두 훑어 **정적 세그먼트가 가장 많이 일치하는 라우트**를 고른다.
`/cost` (정적 1) 가 `/:id` (정적 0) 보다 우선한다.

## ADR-30. 사적 콘텐츠는 서버 렌더에 담지 않는다

쪽지 본문을 서버 렌더 HTML에 넣으면 캐시·프록시·브라우저 이력에 남을 위험이 커진다.
렌더 캐시는 비로그인 요청만 대상이므로(ADR-24) 직접적인 유출은 없지만,
사적 콘텐츠는 표면을 더 줄이는 편이 맞다.

그래서 쪽지 화면은 **껍데기만 서버가 렌더**하고 내용은 인증된 API 요청으로 가져온다.
비로그인 사용자에게는 껍데기조차 주지 않고 로그인 안내만 낸다.

같은 원칙으로 관리자 화면도 쪽지 **내용을 보여주지 않는다.**
스팸 대응에는 "누가 누구에게 언제 얼마나"로 충분하고, 회원 간 사적 대화를
관리자가 읽을 이유가 없다. 수신자 검색은 이메일을 마스킹해 회원 이메일이
검색으로 수집되지 않게 한다.

## ADR-31. 후기 자격은 요청마다 주문으로 되짚어 확인한다

"구매한 사람만 후기를 쓴다"를 지키는 방법은 두 가지다.

1. 주문이 결제될 때 "후기 쓸 수 있음" 표를 만들어 둔다
2. 후기 작성 요청마다 주문을 조회해 확인한다

1번이 빠르지만 상태가 두 곳에 생긴다. 환불·취소·주문 삭제가 일어날 때마다
그 표를 같이 손질해야 하고, 한 번 어긋나면 사지 않은 사람이 후기를 쓸 수 있게 된다.
후기 작성은 초당 수천 건이 오는 요청이 아니므로, 매번 조회하는 쪽을 골랐다.
주문이 진실의 원천이고 파생 상태가 없다.

같은 이유로 평점 집계도 증감 누적이 아니라 **매번 다시 센다**.
숨김·복구·수정·삭제가 섞여도 `review_count` 와 `rating_sum` 이 실제 후기와
어긋날 수 없다. 상품 하나에 달린 후기를 세는 비용은 인덱스 스캔 한 번이다.

## ADR-32. 종속 목록은 텍스트로 편집하고 이름으로 동기화한다

상품 옵션은 상품에 종속된 목록이다. 선언적 관리 화면(ADR-12)의 필드 스키마로는
"부모에 딸린 여러 행"을 편집할 수 없고, 옵션을 독립 리소스로 만들면 상품을 고르는
동적 select가 필요해 스키마가 감당하지 못한다.

그래서 상품 폼의 텍스트 영역에 한 줄씩 적는다 (`이름|추가금|재고`).
한국 쇼핑몰에서 익숙한 방식이고, 옵션이 수십 개여도 붙여넣기로 관리된다.

저장은 **이름으로 짝지어 갱신**한다. 전부 지우고 다시 넣으면 옵션 id가 바뀌어
장바구니에 담긴 옵션이 `ON DELETE SET NULL` 로 조용히 사라진다 — 고객은 자기
장바구니가 왜 망가졌는지 알 수 없고, 관리자는 자기가 그랬다는 것을 모른다.
이름이 그대로면 id가 유지되고, 목록에서 빠진 옵션만 삭제된다.

관리 목록 API는 반대로 배열을 텍스트로 되돌려 준다. 선언적 폼이 편집할 수 있는
형태로 내려보내는 것은 API의 책임이고, 관리자 UI는 그것이 옵션인지 모른 채 다룬다.

## ADR-33. 소셜 로그인은 코어에 둔다

Brick은 웬만하면 플러그인으로 밀어낸다(게시판·쇼핑몰·포인트·쪽지·방문자 집계).
소셜 로그인은 예외다.

로그인은 사이트의 관문이다. 플러그인이 비활성화되거나 업데이트에서 실패해
로그인 수단이 사라지면, 소셜로만 가입한 회원은 계정에 들어갈 방법이 없다.
비밀번호를 만들어 우회할 수도 없다 — 소셜 전용 계정에는 재설정 메일이 가지 않는다.

또한 소셜 로그인은 세션 발급과 회원 테이블을 직접 만져야 한다.
플러그인에게 "세션을 발급하는 권한"을 주면 그것이 플러그인 계약에서 가장 위험한
표면이 된다. 코어에 두는 편이 노출을 줄인다.

대신 **공급자를 늘리는 일은 표 한 줄 추가**가 되도록 만들었다
(`oauth.providers.ts`). 흐름 코드는 하나뿐이고 공급자마다 다른 것은 주소 세 개와
프로필 응답의 모양뿐이다. 사내 SSO(표준 OIDC)는 주소마저 설정에서 받는다.

## ADR-34. 검증되지 않은 이메일로는 기존 계정에 붙이지 않는다

소셜 로그인에서 "같은 이메일이면 같은 사람"으로 다루는 것은 편리하지만,
공급자가 이메일 소유를 확인하지 않았다면 계정 탈취 경로가 된다:
공격자가 피해자의 이메일을 자기 소셜 계정에 적어두고 그 계정으로 로그인하면
피해자의 Brick 계정에 들어온다.

그래서 `email_verified` 가 참일 때만 연결한다. 검증되지 않은 이메일이 기존 계정과
겹치면 **연결도 가입도 하지 않고** "로그인한 뒤 내 정보에서 연결해주세요"로
돌려보낸다. 불편하지만, 이 경로를 열어두면 편리함의 대가가 남의 계정이다.

GitHub의 `/user` 응답은 검증 여부를 알 수 없으므로 항상 미검증으로 다룬다.
카카오는 `is_email_verified` 와 `is_email_valid` 가 **모두** 참일 때만 신뢰한다.

## ADR-35. 방문자 식별은 해시로만 남긴다

그누보드는 접속자 IP를 그대로 저장하고 "접속자 목록" 화면을 제공한다.
Brick은 그 화면을 만들지 않고, IP도 원문으로 두지 않는다.

집계에 필요한 것은 **동일성**이지 주소가 아니다. 설치마다 다른 소금을 섞어
`sha256(소금 | IP | User-Agent)` 만 저장하면:

 - DB가 유출되어도 접속자 IP 목록이 되지 않는다
 - 소금이 설치마다 다르므로 다른 설치본의 기록과 대조할 수 없다
 - 하루 단위 순 방문자 집계는 그대로 된다

대역 통계를 위해 앞 두 옥텟만(`203.0.*`) 따로 남긴다. 유입 경로도 도메인만
남긴다 — 전체 URL에는 검색어와 세션 토큰이 섞여 들어온다.

날짜는 애플리케이션이 아니라 DB의 `current_date` 가 정한다. 해시 키에 날짜를
섞지 않는 이유도 같다 — 서버와 DB의 시간대가 다르면 자정 무렵에 같은 사람이
두 번 세어진다. 날짜 구분은 유니크 인덱스 `(visit_day, visitor_key)` 의 일이다.

## ADR-36. 집계 훅은 응답을 기다리지 않는다

`page.viewed` 는 코어가 `void this.hooks.doAction(...)` 으로 발행한다.
집계는 렌더의 부수효과이고, 집계가 느리다고 페이지가 늦게 뜨면 안 되며,
집계가 실패한다고 페이지가 안 뜨면 더 안 된다.

`void` 로 던져도 안전한 근거는 HookBus의 계약이다 — action은 플러그인별 예외를
삼키므로 처리되지 않은 rejection이 되지 않는다(ADR-6).

렌더 캐시가 적중한 요청에서도 훅은 발행된다. 캐시된 페이지를 본 것도 방문이다.

## ADR-37. 데이터베이스 오류는 문자열이 아니라 코드로 판별한다

**맥락.** 중복 등록을 409로 돌려주기 위해 오류를 문자열로 검사하고 있었다:

```ts
if (String(err).includes("duplicate key")) throw new ConflictException(...)
```

drizzle-orm 0.45 로 올리자 이 검사가 **전부 조용히 실패**했다. drizzle 이
드라이버 오류를 `Error("Failed query: ...")` 로 감싸고 원본을 `cause` 에 넣기
시작했기 때문이다. `String(err)` 에는 더 이상 "duplicate key" 가 없다.

결과는 사용자에게 이렇게 보였다 — "이미 사용 중인 주소입니다"(409) 대신
**500 서버 오류**. 회원가입 · 게시판 생성 · 페이지 생성 · 상품 등록 · 쿠폰 등록 ·
후기 작성, 그리고 **결제 중복 방어**까지 여덟 곳이 같은 방식이었다.

**결정.** 문자열을 버리고 PostgreSQL 오류 코드(SQLSTATE)로 판별한다.
`packages/core/src/db-errors.ts` 가 유일한 구현이고, `@brick/plugin-sdk` 로
재수출해 플러그인도 같은 것을 쓴다.

```ts
if (isUniqueViolation(err, "shop_coupons_code")) {
  throw new ShopError(409, "이미 사용 중인 쿠폰 코드입니다.");
}
```

`cause` 사슬을 따라가며 다섯 글자 `code` 를 가진 객체를 찾는다 — drizzle 이 한 번,
상위 계층이 또 감쌀 수 있다. 깊이는 8로 제한한다(순환 참조 방어).

제약 이름을 함께 받는다. 한 테이블에 유니크 제약이 여럿일 때
"slug 중복"과 "코드 중복"을 구분해야 하고, 이름을 지정하지 않으면 엉뚱한 충돌을
잘못된 메시지로 안내하게 된다.

**왜 코드가 문자열보다 나은가.** SQLSTATE 는 PostgreSQL 표준이다. 드라이버 버전 ·
ORM · 로케일이 바뀌어도 `23505` 는 `23505` 다. 오류 메시지는 그 어느 것에도
보장되지 않는다.

**남은 위험.** 같은 함정이 다시 생기는 것. `String(err).includes(` 로 오류를
판별하는 코드는 리뷰에서 막는다 — 이 패턴이 조용히 깨진다는 것을
PR 템플릿과 CONTRIBUTING 에 적어두었다.

**부수 효과.** 재시도 가능한 오류(교착 상태 `40P01`, 직렬화 실패 `40001`)를
같은 방식으로 판별할 수 있게 됐다. 지금은 쓰는 곳이 없지만, 동시성 재시도가
필요해지면 판별은 이미 있다.

## ADR-38. 개인정보 삭제는 플러그인이 자기 데이터를 책임진다

**맥락.** 회원 탈퇴는 코어 기능이다(법적 요건이므로 플러그인으로 둘 수 없다 —
플러그인을 끄는 순간 요건이 사라진다). 그런데 개인정보는 코어에만 있지 않다.
게시글·쪽지·주문·후기·포인트에 흩어져 있고, 그 테이블은 모두 플러그인 소유다.

처음에는 코어의 WithdrawalService 가 테이블 이름을 직접 알게 만들었다.
`to_regclass` 로 존재를 확인하고 `DELETE FROM shop_cart_items WHERE user_id = ...`
같은 문장을 실행했다. **바로 깨졌다** — `shop_cart_items` 에는 `user_id` 가 없다.
소유자는 `shop_carts` 에 있다. 탈퇴가 500을 냈다.

버그 자체는 한 줄로 고칠 수 있었지만, 구조가 두 가지를 보장하지 못했다:

1. 코어가 플러그인 스키마에 의존한다. 플러그인이 컬럼을 바꾸면 **코어의 법적
   기능**이 깨진다.
2. 어떤 플러그인이 개인정보를 갖고 있는지 코어가 알 방법이 없다. 새 플러그인이
   개인정보를 저장하면 탈퇴는 그것을 조용히 남긴다 — 위법 상태가 눈에 보이지 않는다.

**결정.** `PluginContext.registerDataEraser()` 를 추가한다. 플러그인이 자기
데이터의 처리 방법을 등록하고, 코어는 **탈퇴 트랜잭션 안에서** 등록된 것들을
순서대로 부른다.

```ts
ctx.registerDataEraser({
  label: "쇼핑몰",
  order: 30,
  async erase({ tx, userId, deletePosts }) {
    // 주문은 남기고 회원 연결만 끊는다 (전자상거래법 5년)
    const { rows } = await tx.execute(sql`
      UPDATE shop_orders SET user_id = NULL WHERE user_id = ${userId}::uuid RETURNING id
    `);
    return [`주문 ${rows.length}건은 법정 보존 기간 동안 유지`];
  },
  describe: async ({ userId }) => [...],  // 탈퇴 전 안내
});
```

**왜 훅(action)이 아닌가.** HookBus 의 action 은 **플러그인별 예외를 삼킨다**(ADR-6).
그게 보통은 옳다 — 한 플러그인의 버그가 게시글 저장을 막으면 안 된다. 하지만
탈퇴에서는 반대다. 삭제가 실패했는데 성공했다고 응답하면, **지우지 않은 것을
지웠다고 말하는** 것이 된다. 그래서 eraser 는 예외를 전파하고, 하나라도 실패하면
트랜잭션이 되돌아간다.

**왜 `tx` 를 넘기는가.** 플러그인이 `ctx.db` 를 쓰면 트랜잭션 밖으로 나간다.
그러면 "개인정보는 지웠는데 계정 익명화가 실패해 되돌아간" 상태가 가능해진다.
계약으로 `tx` 를 강제한다 (ADR-13 과 같은 이유).

**부수 효과.** 탈퇴 전 안내(`describe`)도 플러그인이 만든다. 코어는
"포인트 1,000점이 소멸됩니다"를 쓸 수 없다 — 포인트가 무엇인지 모르기 때문이다.
안내 생성 실패는 그 항목만 건너뛴다. 안내를 못 만드는 것이 탈퇴 화면 전체를
막을 이유는 아니다.

**남은 위험.** 개인정보를 저장하면서 eraser 를 등록하지 않는 플러그인.
계약으로 강제할 수 없다 — 플러그인이 무엇을 저장하는지 코어가 알 수 없기 때문이다.
플러그인 개발 문서에 "개인정보를 저장하면 eraser 를 등록해야 한다"를 적었고,
`docs/plugin-development.md` 의 체크리스트에 넣었다.

## ADR-39. 탈퇴는 행 삭제가 아니라 익명화다

**맥락.** 두 법이 반대 방향을 가리킨다.

| | 요구 |
|---|---|
| 개인정보보호법 제21조 | 목적을 달성했으면 **지체 없이 파기** |
| 전자상거래법 제6조 | 계약·결제·배송 기록은 **5년 보존** |

`DELETE FROM users` 는 두 번째를 위반한다. `ON DELETE CASCADE` 로 주문까지
사라지고, 과거 매출 통계도 바뀐다. 반대로 아무것도 지우지 않으면 첫 번째를
위반한다.

**결정.** **개인을 지우고 거래를 남긴다.**

- `users` 행은 남기고 이메일·이름·비밀번호를 파기한다.
  이메일은 `withdrawn-<랜덤>@withdrawn.invalid` 로 덮는다 — 유니크 제약 때문에
  비울 수 없고, 원래 주소로 재가입할 수 있어야 한다.
- 비밀번호 해시는 `withdrawn:<랜덤>` 으로 덮는다. NULL 로 두지 않는다 —
  "비밀번호 없는 계정"이라는 상태를 인증 코드 전체에 퍼뜨리면 한 곳만 검사를
  빠뜨려도 비밀번호 없이 로그인된다 (소셜 전용 계정과 같은 판단).
- 주문 행은 남기고 `user_id` 만 끊는다. **주문 안의 수령인 이름·연락처·주소는
  지우지 않는다** — 보존 의무의 대상이고, 반품·분쟁·세무 조사에 필요하다.
- 동의 이력(`user_agreements`)은 남긴다. "동의 없이 개인정보를 처리했다"는
  주장에 답할 근거가 사라지면 이력이 아무것도 증명하지 못한다.
- 감사 로그에는 **익명화된 식별자만** 남긴다. 원래 이메일을 남기면 파기했다는
  말이 거짓이 된다.

**마지막 관리자는 탈퇴할 수 없다.** 허용하면 사이트에 들어갈 방법이 사라지고,
DB를 직접 만지지 않으면 복구할 수 없다.

**탈퇴 시 비밀번호를 다시 확인한다.** 세션이 탈취된 상태에서 계정을 지워버리는
경로를 닫는다. 소셜 전용 계정은 비밀번호가 없으므로 확인 문구("탈퇴합니다")를
정확히 입력받는다.

## ADR-40. 사이트맵은 플러그인이 자기 URL을 제공한다

**맥락.** SEO를 설계 전제로 내세우면서 `sitemap.xml` 이 없었다. 게시판이 있는
사이트는 색인해야 할 주소가 수만 개이고, 링크를 따라가는 것만으로는 오래된 글에
닿지 못한다.

문제는 **코어가 그 주소를 모른다**는 것이다. 코어는 `pages` 테이블만 안다.
`/board/free/<uuid>` 나 `/shop/<slug>` 는 플러그인이 만든 주소다.

**결정.** `registerSitemapSource()` — 개인정보 삭제(ADR-38)와 같은 레지스트리
방식이다. 다만 계약이 다르다: **페이지 단위로 요구한다.**

```ts
ctx.registerSitemapSource({
  label: "게시글",
  count: async () => /* 전체 개수 */,
  page: async ({ offset, limit }) => /* 그 구간의 URL 목록 */,
});
```

한 번에 다 달라고 하지 않는 이유: 그누보드 사이트는 게시글이 십만 건인 경우가
흔하다. 전부 메모리에 올리면 터진다. 그래서 코어가 `count()` 로 조각 수를 계산해
`/sitemap.xml` 인덱스를 만들고, 각 조각(`/sitemap-<n>.xml`)이 요청될 때 그
구간만 읽는다. 조각 하나는 2,000개다 — 검색엔진 제한(5만)보다 훨씬 작게 잡아
응답을 가볍게 유지한다.

**정렬은 안정적이어야 한다.** `created_at, id` 로 고정한다. 페이지를 나눠 읽는
동안 순서가 바뀌면 어떤 URL은 두 번 나오고 어떤 URL은 빠진다. 계약 주석에
이것을 명시했다.

**공급자 실패는 격리한다.** `count()` 가 던지는 공급자는 건너뛴다.
게시판 하나가 고장 나서 사이트맵 전체가 사라지면, 검색 노출이 통째로 끊긴다.

**무엇을 넣지 않는가.** 비밀글 · 비공개 게시판(`read_role <> 'guest'`) ·
임시/숨김 상품 · 1:1 문의. 검색엔진에 노출되면 안 되는 것이 사이트맵에 들어가면
그 자체가 유출이다. 스모크가 이것을 항목으로 확인한다.

**robots.txt 도 서버가 만든다.** 관리자·API·로그인 경로를 막고 사이트맵 주소를
알린다. `site.seo_noindex` 설정으로 전체를 막을 수 있다 — 개발 중인 사이트가
색인되는 것을 되돌리는 것은 어렵다.

**응답을 `reply` 로 직접 보낸다.** `@Header` 로 content-type 을 바꾸고 문자열을
반환하면 Nest 가 요청마다 "Content-Type doesn't match Reply body" 경고를 낸다.
크롤러가 이 경로를 자주 치므로 로그가 그 경고로 가득 찬다.

## ADR-41. 1:1 문의는 게시판으로 만들지 않는다

**맥락.** 그누보드는 Q&A를 게시판으로 구현하고 비밀글 옵션으로 가린다.
같은 방식을 쓸 수 있었다 — 이미 게시판 플러그인이 있고 비밀글도 된다.

**결정.** 별도 플러그인(`brick-helpdesk`)으로 만든다.

**이유는 기본값이다.** 게시판은 **기본이 공개**이고 비밀글이 예외다. 문의는
반대여야 한다. 게시판으로 하면 체크박스를 놓치는 순간 주문번호·연락처·환불
계좌가 공개된다. 한 번의 실수로 개인정보가 노출되는 구조를 만들지 않는다.
그래서 helpdesk 에는 "공개 문의" 옵션 자체가 없다.

**그리고 문의에는 게시판에 없는 것이 필요하다.** 답변 상태(접수/답변완료/종료),
담당자 지정, 답변 메일 알림, "내 것만 보이는 목록", 문의번호.

### 남의 문의는 404 로 응답한다

403 을 주면 "그 문의가 존재한다"는 사실이 새어 나간다. 문의번호는 순차적이므로
`Q202608-00001` 부터 훑으면 몇 건이 접수됐는지, 언제 활동이 많았는지 알 수 있다.
그래서 권한이 없으면 존재하지 않는 것과 **같은 응답**을 준다.

### 답변 상태는 양방향이다

운영자가 답변하면 `answered`, 작성자가 다시 쓰면 `open` 으로 돌아간다.
한 방향만 있으면 "답변했는데 또 물어본" 문의가 목록에서 사라져 운영자가 놓친다.

### 탈퇴 시 문의는 지운다

게시글은 익명화하고 남기지만(토론의 맥락), 문의는 **삭제**한다. 내용에
주문번호·연락처·환불 계좌가 들어 있고, 익명화만 하면 그 개인정보가 그대로 남는다.
보존 의무가 있는 것은 주문 기록이고 그건 쇼핑몰 쪽에 남는다.

## ADR-42. 그누보드 이전은 덤프 파일로 한다

**맥락.** 그누보드에서 옮겨오는 방법은 두 가지다 — 원격 MySQL 에 접속해 읽거나,
mysqldump 파일을 받아 읽거나.

원격 접속이 더 깔끔해 보인다. 스트리밍이 되고, 큰 사이트에서 메모리를 덜 쓰고,
사용자가 파일을 만들 필요가 없다.

**결정.** 덤프 파일을 주 경로로 한다.

**이유는 접근성이다.** 그누보드는 대부분 공유 호스팅에서 돌고, 그런 호스팅은
MySQL 의 외부 접속을 막는다(`bind-address = 127.0.0.1`). 원격 접속을 전제하면
**"안 되는 사람"이 대부분**이 된다. 사용자가 실제로 손에 넣을 수 있는 것은
phpMyAdmin 내보내기 파일이다.

### 파서를 정규식으로 쓰지 않는다

`INSERT INTO t VALUES (...),(...);` 를 정규식으로 자르고 싶어진다. 하지만
게시글 본문에는 `),(` 도 `\'` 도 흔하다. 실제 데이터에서 조용히 깨지고,
그 깨짐은 "글이 몇 건 빠졌다"로 나타나 눈치채기 어렵다.

그래서 문자 단위로 상태(문자열 안인가 · 괄호 깊이)를 들고 읽는다.
픽스처에 `),(` 와 이스케이프 따옴표와 줄바꿈을 일부러 넣어 검증한다.

### 리허설이 먼저다

`analyze()` 는 **아무것도 쓰지 않고** 무엇이 몇 건 옮겨지는지, 무엇이 안
옮겨지는지, 레벨이 어떤 역할로 접히는지 보고한다.

이전은 되돌리기 어렵다. 특히 레벨 매핑이 어긋나면 "관리자였던 사람이 일반
회원이 되는" 결과가 조용히 만들어진다. 그래서 **조정 가능하게** 만들고,
리허설로 결과를 먼저 보여준다.

**옮기지 않는 것을 명시한다.** 있는데 안 옮기는 것을 알려주지 않으면 사용자는
"없다"고 착각하고 나중에 발견한다. 그게 최악이다.

### 멱등하게 만든다 (트랜잭션으로 감싸지 않는다)

십만 건을 한 트랜잭션에 넣으면 WAL 이 부풀고 실패 시 롤백에 그만큼 걸린다.
대신 이미 있는 회원·게시판·포인트는 건너뛴다. 중간에 실패하면 그대로 다시
실행하면 된다.

## ADR-43. 옮겨온 비밀번호는 보존하고 로그인 시점에 승급한다

**맥락.** 이전 후 회원 전원이 비밀번호를 다시 만들어야 하면 상당수가 돌아오지
않는다. **이전 도구의 성패가 여기 걸려 있다.** 기능을 다 옮겨도 회원이 못
들어오면 이전은 실패한 것이다.

Brick 은 argon2id 를 쓰고 그누보드는 bcrypt(또는 구형 MD5)를 쓴다. 해시는
되돌릴 수 없으므로 형식을 변환할 수 없다.

**결정.** 원본 해시를 `legacy:<종류>:<해시>` 로 저장하고, 로그인 시 그 방식으로
검증한다. **검증에 성공하면 그 순간 argon2 로 다시 해시한다.**

```
저장:   legacy:bcrypt:$2y$10$...
로그인: bcrypt 로 검증 → 성공 → argon2 로 재해시 → users.password_hash 갱신
```

**왜 접두어를 붙이는가.** `argon2.verify` 는 형식이 다른 값에 예외를 던진다.
저장된 값만 보고 어떤 방식으로 검증할지 알아야 한다.

**왜 승급하는가.** 그누보드의 MD5 는 소금도 없어 유출되면 사실상 평문이다.
그대로 두면 이전한 사이트는 영구히 약한 해시를 갖는다. 로그인 시점은 평문
비밀번호가 손에 있는 **유일한 승급 기회**다. 승급 실패는 로그인을 막지 않는다 —
다음 로그인에 다시 시도된다.

**형식을 모르는 해시는 추측하지 않는다.** 여러 방식을 시도해 하나라도 맞으면
통과시키는 구현은, 잘못된 비밀번호를 통과시킬 위험을 만든다. 대신 쓸 수 없는
값(`unusable:<랜덤>`)을 넣어 비밀번호 로그인을 막고, 리허설이 그 인원을 보고한다.
비밀번호 재설정으로 안내하면 된다.

**남은 위험.** `legacy:` 접두어를 가진 값이 평문 비밀번호로 오인될 여지.
`isLegacyHash()` 를 통과한 값만 레거시 경로로 가고, 그 밖의 모든 값은
argon2 검증(실패 시 false)으로 떨어진다. 어느 경로에서도 평문 비교는 하지 않는다.

## ADR-44. 취소·반품은 상품 단위로 처리한다

**맥락.** 지금까지 취소·환불은 주문 상태를 `cancelled`/`refunded` 로 바꾸는
것뿐이었다. 주문 하나를 통째로 다루는 모델이다.

실제 반품은 그렇지 않다. 세 개 중 하나만 반품하고, 색상만 교환한다.
주문 상태를 통째로 바꾸면 **나머지 두 개의 배송 정보가 사라진다.**

그리고 이건 편의 기능이 아니다. 전자상거래법 제17조는 소비자가 상품을 받은 날부터
7일 안에 청약철회를 할 수 있다고 정하고, 사업자는 이를 거부할 수 없다.
반품이 안 되는 쇼핑몰은 실제로 운영할 수 없다 — M15(회원 탈퇴)와 같은 성격이다.

**결정.** 요청(`shop_returns`)과 대상 항목(`shop_return_items`)을 분리하고,
주문 항목에 `cancelled_qty` 를 누적한다.

### 할인을 안분한다

10,000원짜리 두 개에 2,000원 쿠폰을 쓴 주문에서 하나를 반품하면
**10,000원을 돌려주면 안 된다.** 실제로 받은 돈은 18,000원이고 하나에 9,000원이다.
그러지 않으면 반품할수록 사업자가 손해를 본다.

안분에서 발생하는 반올림은 **내림**으로 처리한다. 부분 반품은 여러 번 나뉠 수
있고, 매번 올림하면 오차가 누적되어 총 환불액이 받은 돈을 넘을 수 있다.
오차는 최대 1원이다.

### 물건을 받기 전에 환불하지 않는다

상태 전이를 `requested → approved → collecting → received → completed` 로 두고,
**`completed` 에서만** 재고 복원과 환불이 일어난다. `requested → received` 같은
건너뛰기를 막는다. 물건을 받기 전에 환불하면 돈만 나간다.

취소(`cancel`)는 수거가 없으므로 `approved → completed` 로 바로 간다.

### 사유가 배송비 부담을 결정한다

자유 입력이 아니라 목록이다. 단순 변심은 고객 부담(제18조 제9항), 불량·오배송·
파손은 사업자 부담이다. **불량의 반송비를 고객에게 청구하는 것은 위법**이므로,
사업자가 임의로 "고객 부담"이라고 적을 수 없어야 한다. 그래서 사유 코드에
부담자를 고정해 두고, 화면은 신청 **전에** 누가 내는지 알려준다 —
나중에 환불액이 깎여 있으면 분쟁이 된다.

### 청약철회 기간과 하자 책임은 별개다

7일이 지나면 단순 변심 반품은 막지만 **불량은 언제든 받는다.** 하자에 대한
책임은 청약철회와 다른 근거에서 나온다. 종류(반품/교환)는 열어두고 사유 검증에서
구분한다.

기산점은 `shop_orders.delivered_at` 이다 — `delivered` 로 전이할 때 기록한다.
없으면 "언제까지 반품할 수 있는가"를 계산할 수 없다.

### 트랜잭션 경계

재고 복원·수량 누적은 트랜잭션 안, **PG 환불은 트랜잭션 밖**이다.
외부 호출을 트랜잭션에 넣으면 커넥션을 네트워크 대기 동안 잡고, PG 가 성공했는데
커밋이 실패하면 "돈은 나갔는데 기록이 없는" 상태가 된다. 순서를 뒤집으면
(기록 먼저 → 환불 나중) 실패 시 재시도할 수 있다. 환불 실패는 삼키지 않고
502 로 알린다 — 운영자가 수동 환불해야 한다는 것을 알아야 한다.

### 발견한 버그: 이중 재고 복원

`changeOrderStatus` 가 주문 항목의 **전체 수량**을 복원하고 있었다.
부분 반품으로 1개를 이미 복원한 뒤 주문 전체를 취소하면 3개가 더 복원되어
**판 것보다 많은 재고**가 생긴다. `quantity - cancelled_qty` 만 복원하고
복원한 만큼 `cancelled_qty` 를 채우도록 고쳤다.

### 발견한 버그: 미결제 주문 취소가 502

가장 흔한 경우인 "입금 전 취소"에서 환불을 시도해 실패했다. 결제 기록이 있는지
확인하고 없으면 환불을 건너뛴다.

## ADR-45. 사업자정보는 코어 설정이고 테마는 렌더만 한다

**맥락.** 전자상거래법 제13조는 통신판매업자가 상호 · 대표자 · 주소 · 전화번호 ·
사업자등록번호 · 통신판매업 신고번호를 소비자가 쉽게 알 수 있도록 표시하라고
정한다. 표시하지 않으면 과태료 대상이고, **쇼핑몰을 합법적으로 열 수 없다.**

세 가지 위치를 고려했다.

| | 문제 |
|---|---|
| 테마 설정 | 테마를 바꿀 때마다 다시 입력하게 되고, 빠뜨린다 |
| 쇼핑몰 플러그인 | 플러그인을 끄면 **법적 표시가 사라진다** |
| 코어 사이트 설정 | ✅ |

**결정.** 코어 사이트 설정(`site.business_info`)에 두고, 테마 렌더 컨텍스트의
`site.business` 로 내려보낸다. 테마는 렌더만 한다.

**공개 API 다.** `GET /api/business-info` 는 인증을 요구하지 않는다 —
관리자만 볼 수 있으면 "소비자가 쉽게 알 수 있도록"이 성립하지 않는다.

### 사업자등록번호를 실제로 검증한다

형식(`000-00-00000`)만 보면 오타가 통과한다. **잘못된 번호를 표시하는 것은
표시하지 않는 것과 같은 문제**이므로 국세청 체크섬 규칙을 검증한다.

가중치 `[1,3,7,1,3,7,1,3,5]` 를 앞 9자리에 곱해 더하고, 9번째 자리 곱의 십의
자리를 추가로 더한 뒤 `(10 - 합%10) % 10` 이 마지막 자리와 같아야 한다.
실제 공개 번호로 검증했다.

`000-00-00000` 은 합이 0이라 체크섬을 통과한다. **칸만 채우는 것**을 막기 위해
전부 0을 따로 거부한다.

### 값이 없는 항목은 내려보내지 않는다

테마가 `{{#if}}` 로 감싸지 않아도 "대표자: " 같은 빈 라벨이 남지 않게,
채워진 항목만 컨텍스트에 넣는다. 하나도 없으면 `null` 이라 영역 자체가 사라진다.

### 빠진 항목은 막지 않고 경고한다

설치 직후에는 아무 값도 없고, 쇼핑몰이 아닌 사이트도 있다. 저장을 막으면
아무것도 못 하게 된다. 대신 `commerceReady` 와 빠진 항목 목록을 응답에 담아
관리 화면이 경고할 수 있게 한다.

## ADR-46. 위시리스트는 비회원도 쓴다

**맥락.** 위시리스트(영카트의 "보관함")를 회원 전용으로 만들 수 있다.
소유자가 명확하고 구현이 단순하다.

**결정.** 비회원도 쓴다. 장바구니와 같은 게스트 토큰을 쓴다.

**이유는 사용 시점이다.** 위시리스트는 **로그인하기 전에** 쓰는 기능이다.
"마음에 드는 걸 담아두다가 나중에 가입"이 실제 흐름이고, 로그인을 요구하면
아무도 쓰지 않는다 — 그러면 기능이 있으나 없으나 같다.

**로그인 시 이어받는다.** `POST /wishlist/merge` 가 게스트 토큰의 항목을 회원으로
옮긴다. 이게 없으면 "담아두고 가입했더니 사라졌다"가 되어 비회원 허용의 의미가
없어진다. 최근 본 상품도 함께 옮긴다.

**소유자 정보가 없으면 빈 목록을 반환한다.** 조건 없이 조회하면 남의 위시리스트가
전부 보인다 — `ownerFilter()` 가 둘 다 없을 때 던지고, 라우트는 그 전에 빈 목록으로
빠진다.

### 장바구니와 왜 나누는가

장바구니는 "살 것"이고 위시리스트는 "볼 것"이다. 장바구니에 넣어두면 결제
화면에서 매번 지워야 하고, 재고가 없으면 주문 자체가 막힌다.

### 최근 본 상품은 짧게 보관한다

브라우저 저장만으로 하면 기기를 바꾸면 사라진다. 그래서 서버에 두지만,
개인의 관심사가 담긴 기록이므로 회원당 30개로 제한하고 90일 후 지운다.

정리를 배치 작업으로 두지 않고 **기록할 때마다** 초과분을 지운다. 배치를 두면
그 작업이 실패했을 때 조용히 무한히 쌓인다.

## ADR-47. 지역별 배송비는 우편번호 구간으로 판단한다

**맥락.** 제주·도서산간은 추가 배송비가 붙는다. 주소 문자열로 판단할 수도 있다.

**결정.** 우편번호 구간(`postcode_from` ~ `postcode_to`)으로 판단한다.

주소 문자열은 "제주도청"과 "제주식당"을 구분할 수 없고, 서울에도 "제주로"가
실제로 있다. 우편번호는 행정구역과 1:1로 대응한다.

**구간이 겹치면 가장 비싼 것을 적용한다.** 겹치게 설정한 것은 실수일 가능성이
높고, 그때 덜 받는 쪽으로 기울면 사업자가 손해를 본다.

### 무료배송이어도 지역 추가비는 붙는다

도서산간 운송료는 실제로 발생하는 비용이고, 무료배송 정책이 그것까지 흡수한다고
볼 수 없다. `shippingFee` 가 0이어도 `zoneFee` 는 계산한다.

### 배송비와 따로 표시한다

`shippingFee` 와 `zoneFee` 를 합치지 않는다. 주문서에 "배송비 3,000 + 지역 추가
3,000"으로 나눠 보여줘야 고객이 왜 6,000원인지 안다. 합쳐 두면 항의가 들어온다.

**주문 생성 시 우편번호를 견적에 넘겨야 한다.** 빠뜨리면 주문서에는 6,000원으로
보이고 실제로는 3,000원만 받는다 — 스모크가 주문 행의 `zone_fee` 를 직접 확인한다.

## ADR-48. 설문의 중복 투표 방지와 결과 공개 시점

**맥락.** 설문조사에서 실제로 어려운 것은 UI 가 아니라 두 가지 판단이다.

### 1. 비회원 중복 투표를 어떻게 막는가

회원은 `user_id` 로 쉽다. 비회원은 IP 밖에 없다.

IP 원문을 저장하면 **"누가 무엇에 투표했는가"** 가 되어 민감한 개인정보가 된다.
그래서 sha256 해시로만 남긴다(ADR-35 와 같은 원칙).

**설문 id 를 해시에 섞는다.** 같은 IP 가 여러 설문에서 같은 해시를 갖지 않게 해서,
해시를 모아도 "이 사람이 참여한 설문 목록"을 만들 수 없게 한다.

**완벽하지 않다.** 같은 공유기 아래 여러 사람이 한 표로 묶인다. 완벽한 방지는
본인 인증뿐이고, 설문에 그 비용을 요구할 수는 없다. 정확한 표가 필요하면
투표 자격을 `member` 로 두면 된다 — 문서에 명시했다.

**최종 방어선은 DB 제약이다.** 앱에서 먼저 확인해도 동시 요청은 통과할 수 있어,
`(poll_id, user_id)` 와 `(poll_id, voter_hash)` 부분 유니크 인덱스가 막는다.

### 2. 결과를 언제 보여주는가

투표 전에 결과를 보여주면 표가 쏠린다(밴드왜건). 기본값은 `after_vote` 다.

**숨겨야 할 때는 득표 수를 응답에 넣지 않는다.** 화면에서 가리는 방식이면
개발자 도구로 볼 수 있다 — `showResults` 가 false 면 `voteCount`·`percent`
필드가 아예 없다.

### 참여자 수와 선택 수는 다른 수치다

복수 선택에서 선택 수 합은 참여자 수보다 크다. 그래서 투표를 사람 단위
(`poll_votes`)와 선택 단위(`poll_vote_choices`)로 나눈다. 목록에 보여줄 값은
참여자 수이고, 막대 그래프의 비율은 선택 수 기준이다.

### 선택지 문구를 고쳐도 표는 유지된다

이름으로 짝지어 갱신한다. 전부 지우고 다시 넣으면 진행 중인 설문에서 **오타를
고쳤을 뿐인데 표가 0이 된다.** 목록에서 뺀 선택지의 표는 사라지지만,
참여자 수는 그대로 둔다 — 그 사람들은 실제로 참여했다.

### 탈퇴 시 표는 남기고 사람만 지운다

투표를 지우면 집계가 바뀌어 **이미 발표된 결과가 소급해서 달라진다.**
설문은 그 시점의 여론을 기록한 것이므로 바꾸면 안 된다.

`user_id` 를 NULL 로만 두면 CHECK 제약(`user_id` 또는 `voter_hash` 필요)에 걸린다.
그 제약은 "출처 없는 표"를 막기 위한 것이고 이미 던져진 표를 익명화하는 것과는
다른 상황이므로, 제약을 없애는 대신 **무작위 값**을 넣는다. 표는 여전히 한 사람
몫으로 세어지고, 그 값으로 누구인지 알 수는 없다.

기타 의견은 자유 서술이라 개인을 특정할 내용이 들어 있을 수 있어 지운다.

### 관리자도 작성자를 볼 수 없다

기타 의견 목록에 작성자를 넣지 않는다. 설문은 익명이 전제이고, "누가 무슨 의견을
냈는가"를 운영자가 볼 수 있으면 그 전제가 깨진다.

**부수 발견.** `gen_random_bytes()` 는 pgcrypto 확장이 필요하다. `gen_random_uuid()`
두 개를 이어 64자 hex 를 만들어 확장 의존을 없앴다 — 설치본이 확장 설치 권한을
요구하면 공유 호스팅에서 쓸 수 없다.

## ADR-49. 영카트 이전에서 구조가 다른 지점들

영카트5는 그누보드5 위에 얹힌 쇼핑몰이고 테이블 접두어를 공유한다. 그래서
덤프 하나로 회원·게시판과 상품·주문을 함께 옮긴다. 어려운 것은 컬럼 대응이
아니라 **모델이 다른 지점**이다.

### 분류 계층은 문자열 길이로 표현되어 있다

영카트의 `ca_id` 는 `"10"`(대) → `"1010"`(중) → `"101010"`(소)다.
**부모는 앞자리를 자른 값**이다. 이걸 모르면 계층이 전부 최상위로 평평해진다.

짧은 것부터 처리해 부모가 항상 먼저 만들어지게 한다.

### 조합형 옵션은 단층으로 펼친다

색상+사이즈 조합을 Brick 의 단층 옵션 모델로 표현할 수 없다. 조합을 하나의
이름(`흰색,M`)으로 펼친다. 영카트도 화면에서는 조합을 한 줄로 보여주므로
**고객이 보는 것은 같다.**

### 알 수 없는 주문 상태는 입금대기로 떨어뜨린다

영카트는 `od_status` 에 한글 문자열을 그대로 저장한다. 사이트마다 커스텀 상태가
있을 수 있다.

임의로 '완료'로 보면 **배송하지 않은 주문이 완료 처리되고 매출 통계가
부풀려진다.** 안전한 쪽(입금대기)으로 떨어뜨리고, 리허설이 그런 값을 목록으로
알려준다 — 운영자가 보고 판단해야 한다.

### 금액이 맞지 않으면 총액을 신뢰한다

`od_cart_price + od_send_cost ≠ od_receipt_price` 인 주문이 실제로 있다
(쿠폰·마일리지·수동 조정). **실제로 받은 돈이 총액**이므로 차액을 할인으로
흡수해 `상품금액 - 할인 + 배송비 = 총액` 을 지킨다. 그러지 않으면 Brick 의
금액 불변식이 깨지고 통계가 어긋난다.

### 과거 주문이 재고를 줄이지 않는다

주문을 옮길 때 재고를 차감하면 **지금 재고가 음수가 된다.** 이미 팔린 것은
영카트 재고에 반영되어 있고 우리는 그 최종 값을 그대로 가져온다.

판매수량은 주문 항목에서 다시 센다(취소·반품 제외). 하나씩 올리면 중간에
실패했을 때 어긋난다.

### 상품 slug 에 id 를 붙인다

`it_id` 는 타임스탬프 문자열이라 주소에 쓸 수 없다. 상품명에서 만들되 **id 를
접미사로 붙인다** — 한글 상품명은 slug 규칙에 맞는 문자가 하나도 없는 경우가
많아 상품명만으로는 전부 같은 slug 가 되어 충돌한다.

### 판매 중지는 hidden 이고 draft 가 아니다

`it_use = 0` 은 "팔다가 내린 것"이다. `draft` 는 "아직 안 만든 것"이므로
의미가 다르다. 관리 화면에서 둘을 구분해 보여줘야 운영자가 무엇을 다시
올릴지 판단할 수 있다.

### 재고 0을 품절로 자동 전환하지 않는다

영카트에서 재고를 관리하지 않는 상품(`it_stock_qty = 0` 이지만 계속 파는)이
흔하다. `it_soldout` 이 판단 기준이다.

### 발견한 버그: 주문 항목이 재실행에 중복됐다

주문 자체는 이미 있으면 건너뛰었지만, **항목 루프는 장바구니 테이블을 훑으므로
다시 실행하면 같은 항목이 또 들어갔다**(5개 → 10개). "새로 만든 주문만"으로
판단하지 않고 **이미 항목이 있는 주문**을 건너뛴다 — 이전이 중간에 실패해
주문은 있고 항목은 없는 상태가 남을 수 있고, 그때는 다시 채워야 한다.

## ADR-50. 단체메일은 운영자가 위법을 저지를 수 없게 만든다

단체메일에서 잘못 보낸 메일은 되돌릴 수 없다. 그리고 그 실수는 단순한 사고가
아니라 **위법**이다. 정보통신망법 제50조는 영리목적 광고성 정보에 대해
사전 동의·`(광고)` 표기·수신거부 방법 명시를 요구하고, 위반하면 3천만원 이하
과태료를 매긴다.

문제는 이것이 **운영자가 지키기 쉬운 규칙이 아니라는 것**이다. 급하게 세일
공지를 보내는 사람은 제목에 `(광고)`를 붙이는 것을 잊고, 수신거부 링크를
빼먹고, "동의한 사람만" 체크박스를 끄고 전체 발송을 누른다. 그래서 이 기능은
**설정 가능한 옵션으로 만들지 않았다.**

### 종류를 고르면 나머지가 결정된다

발송은 `notice(공지)`와 `ad(광고)` 둘뿐이다. 종류를 고르는 순간:

| | notice | ad |
|---|---|---|
| 수신자 조건 | 전체 회원 | `marketing_opt_in = true` **만** |
| 제목 | 그대로 | `(광고)` 강제 접두 |
| 본문 | 그대로 | 수신거부 안내 자동 첨부 |

"광고인데 동의 안 받고 보내기"를 **표현할 방법이 UI에 없다.** 광고 수신 동의
필터는 체크박스가 아니라 `recipientFilter()` 안의 무조건 조건이다:

```ts
if (kind === "ad") parts.push(sql`u.marketing_opt_in = true`);  // 옵션으로 두지 않는다
```

제목도 마찬가지다. 운영자가 `(광고)`를 지우고 저장해도 `create()`가 다시
붙인다. 반대로 공지에는 `(광고)`를 붙이지 않는다 — 운영 공지를 광고로
표기하면 회원이 수신거부를 하고, 정작 약관 개정 안내를 못 받는다.

### 수신거부는 로그인 없이 되어야 한다

법은 "수신거부 방법을 명시하라"고만 쓰지만, 로그인해서 마이페이지에서 설정을
바꾸라는 것은 **쉬운 방법이 아니다.** 메일에 담는 링크는 토큰 하나로
동작한다(`GET /api/mail/unsubscribe?token=`). 토큰은 회원별로 하나이고
**만료되지 않는다** — 반년 전 메일의 링크도 눌리면 해제되어야 한다.

### 발송 직전에 동의를 다시 확인한다

대상은 발송 전에 `mail_recipients` 행으로 확정한다(수만 명 발송은 몇 시간이
걸리고, 중간에 조건이 흔들리면 "누구에게 보냈는가"를 재현할 수 없다).
그런데 확정과 실제 발송 사이에 회원이 수신거부를 할 수 있다. 확정된 목록을
그대로 믿으면 **철회한 사람에게 보낸다 — 위법이다.**

그래서 각 수신자를 보내기 바로 전에 동의를 다시 읽고, 철회했으면 `skipped`
로 기록한다. 발송 이력에 "왜 안 보냈는가"가 남는 것도 중요하다.

### 주소를 스냅샷으로 남긴다

`mail_recipients.email` 은 `users` 를 조인하지 않고 발송 시점 주소를 그대로
복사한다. 회원이 주소를 바꾸거나 탈퇴하면 "어디로 보냈는가"가 사라지는데,
발송 이력은 사실의 기록이어야 한다. 탈퇴 시 개인정보를 익명화하면서도
이 행은 남긴다(ADR-39와 같은 이유 — 동의 이력과 발송 이력은 증거다).

### 발송은 큐 워커에서, 20건씩

요청 안에서 다 보내면 타임아웃이 나고 어디까지 보냈는지 알 수 없다.
`mailing.send` 잡으로 넘겨 20건 단위로 처리하고 배치 사이에 1초 쉰다 —
SMTP 서버가 대량 연결을 스팸으로 판단하는 것을 피한다. 서버가 죽어도
`pending` 인 행만 다시 보내면 되므로 **같은 사람에게 두 번 가지 않는다.**

### SMTP 가 없으면 발송을 거부한다

`LogMailProvider` 는 개발용이다. 운영자가 SMTP 를 설정하지 않은 채 발송을
누르면 "보냈다"고 표시되고 아무도 못 받는 것이 최악이다. `start()` 는
`mail.enabled` 가 false 면 거부하고 이유를 알려준다.

### 검증: 대상 선정만 보면 부족하다

이 기능에서 중요한 것은 **실제로 무엇이 발송되는가**다. 수신자 쿼리만
확인하면 제목의 `(광고)`가 빠지거나 수신거부 링크가 없어도 통과한다.

그래서 최소한의 SMTP 서버(`scripts/smtp-sink.mjs`)를 만들어 스모크에서
띄운다. nodemailer 가 실제로 접속해 메일을 보내고, 테스트는 **받은 메일을
디코딩해서 읽는다** — 제목의 `(광고)`, 본문의 수신거부 링크, 공지에는
그 링크가 없는 것, HTML 메일의 텍스트 대안까지 확인한다.

한글 본문은 quoted-printable 로 인코딩되어 오므로 디코딩이 필요했고, 여기서
두 번 틀렸다. 바이트를 `String.fromCharCode` 로 문자화하면 latin1 이 되어
한글이 깨지고, 접힌 헤더의 encoded-word 사이 공백을 남기면 "안내"가
"안 내"로 읽힌다. **디코딩이 틀리면 검증이 조용히 무의미해진다** — `(광고)`
를 찾지 못하는데 그 이유가 인코딩이면, 기능 버그와 구분되지 않는다.

## ADR-51. 판매 리포트: 무엇을 매출로 세는가를 먼저 정한다

리포트는 **조용히 틀린다.** 화면에 숫자가 나오면 운영자는 그것을 믿고,
틀렸다는 사실은 세무 신고나 정산 때 드러난다. 그래서 SQL 을 쓰기 전에
정의를 못박았다.

기존 `/admin/stats` 에 실제로 두 버그가 있었다.

### 부분 환불이 빠지지 않았다

`sum(total)` 로 셌다. 주문 상태가 `cancelled`/`refunded` 로 바뀌는 것은
**전체 취소뿐**이다(부분 반품은 남은 상품이 배송되어야 하므로 주문 상태를
건드리지 않는다 — ADR-44). 그래서 두 개 중 하나를 반품한 주문은 전액이
매출로 남았다. 반품이 많은 사이트일수록 매출이 부풀어 보였다.

순매출을 정의로 고정했다:

```
주문 기준: Σ orders.total − Σ (완료된 반품의 refund_amount)
상품 기준: Σ (line_total − 할인안분) − Σ refunded_amount
```

반품의 `refund_amount` 는 전체 취소 시의 배송비 환불을 포함하고 고객이
부담하는 반송비는 이미 차감된 값이므로, 그대로 빼면 **실제로 나간 현금과
일치한다.**

상품 기준 할인 안분은 **반품 때 쓰는 것과 같은 규칙**(항목 정가 비중, 내림)을
쓴다. 규칙이 다르면 "반품액 + 남은 매출 ≠ 받은 돈" 이 되어 아무도 못 맞춘다.
스모크에서 `상품별 순매출 합 + 배송비 == 주문별 순매출` 을 항목으로 두었다 —
이게 안 맞으면 운영자는 두 리포트를 다 못 믿는다.

### 날짜가 밀렸다

`created_at >= date_trunc('month', now())` — **주문일 기준이고 서버
시간대**였다. 한국에서 1일 오전 9시 이전 결제는 전달로 잡혔다.

두 군데를 고쳤다. 기준 시점을 **결제일(`paid_at`)** 로 바꿨고(무통장 주문을
걸어놓고 입금하지 않는 것이 흔한데 그것을 매출로 세면 숫자를 믿을 수 없다),
날짜 경계를 **사이트 시간대**로 자른다.

시간대를 환경변수(`BRICK_TIMEZONE`, 기본 `Asia/Seoul`)로 둔 이유: 바꾸면
**과거 집계까지 달라진다.** 관리 화면에서 클릭으로 바꿀 성질의 값이 아니다.

### 신청만 한 반품은 빼지 않는다

물건을 받기 전에는 환불되지 않으므로(ADR-44) 아직 나간 돈이 아니다.
`status = 'completed'` 인 것만 뺀다. 반대로 하면 반품 신청이 들어온 순간
매출이 줄어들고, 반품이 거부되면 다시 늘어난다 — 운영자가 매일 보는 숫자가
이유 없이 흔들린다.

### 반품을 조인하지 않고 서브쿼리로 집계한다

주문 하나에 반품이 여러 건 붙을 수 있다. 그냥 조인하면 **주문 금액이 반품
건수만큼 곱해진다** — 매출이 부풀어 보이는 대표적인 실수다.

### CSV 는 BOM 을 붙인다

운영자는 결국 엑셀에서 본다. BOM 이 없으면 엑셀은 UTF-8 로 추정하지 않고
시스템 코드페이지로 읽어서 한글이 깨진다. 필드 escape 도 필요하다 —
상품명에 콤마와 따옴표가 들어간다.

### 발견한 것: 날짜 검증이 헛돌았다

`Date.parse("2026-02-30T00:00:00Z")` 는 NaN 이 아니다. **JS 는 넘치는 날짜를
다음 달로 굴린다** — 3월 2일이 되어 검증을 통과하고, 그 뒤 PostgreSQL 이
던져서 400 이 아니라 500 이 났다. 되돌려 찍어 같은 문자열이 나오는지
확인하는 방식으로 바꿨다.

## ADR-52. 분류 계층은 스키마에만 있었다

판매 리포트를 만들면서 분류별 집계가 계속 `(분류 없음)` 으로 나왔다.
원인은 리포트가 아니었다.

`shop_categories.parent_id` 와 `shop_products.category_id` 는 스키마에 있고
스토어프론트 쿼리와 이전 도구가 쓰고 있었다. 그런데:

- `PRODUCT_RESOURCE` 에 `category_id` 필드가 없었다
- `CATEGORY_RESOURCE` 에 `parent_id` 필드가 없었다
- `POST/PUT /admin/products` 와 `/admin/categories` 가 두 컬럼을 **쓰지
  않았다**

즉 **운영자는 분류를 만들 수는 있어도 상품에 지정할 수 없었고, 2단 분류를
만들 수도 없었다.** 영카트에서 옮겨온 사이트에는 계층이 있는데(M18 이
이전한다) 새로 등록한 상품에는 절대 분류가 붙지 않는 상태였다.

기능이 "있다"고 말할 수 있는 기준이 스키마가 아니라 **운영자가 화면에서 할
수 있는가**라는 것을 다시 확인한 사례다.

### 선택지가 테이블 행일 때 — `optionsFrom`

관리 리소스의 `select` 는 정적 `options` 만 받았다. 분류는 행이므로 표현할
수 없었다. 그래서 필드에 `optionsFrom` 을 더했다 — 플러그인 기준 경로이고,
응답이 `[{ value, label }]` 이면 화면이 그걸로 선택지를 만든다.

레지스트리 패턴(`registerRoute`·`registerBlock`·`registerDataEraser`…)과 같은
방향이다. 코어가 플러그인의 SQL 을 알 필요 없고, 플러그인은 React 를 쓰지
않는다.

계층은 이름을 NBSP 로 들여써서 보여준다. 평면 목록으로 주면 "상의"가 의류
아래인지 잡화 아래인지 알 수 없다. 보통 공백은 HTML `<option>` 안에서 접혀
사라진다.

### 순환을 막아야 했다

`parent_id` 를 화면에 노출하는 순간, 운영자가 **자기 자손을 상위 분류로
지정할 수 있게 된다.** 그러면 분류 트리를 훑는 재귀 쿼리가 끝나지 않고,
선택지 목록과 분류별 리포트가 함께 멈춘다. 저장 시점에 조상을 거슬러 올라가
확인하고 400 으로 거절한다.

### 재귀 CTE 의 컬럼 타입은 비재귀 항에서 결정된다

들여쓰기용 경로를 만들 때 `name AS path` 로 시작하면 `varchar(200)` 이 되고,
재귀 항의 `path || ' > ' || name` 은 `text` 라서
`has type character varying(200) ... but type text overall` 로 실패한다.
`name::text AS path` 로 시작해야 한다. CONTRIBUTING 에 적어 두었다.

## ADR-53. 관련 상품은 수동 지정과 함께 구매를 둘 다 쓴다

둘 중 하나만 두면 각각 실패한다. **새로 연 쇼핑몰에는 주문 이력이 없어서**
자동 추천만 두면 오픈 직후 몇 달간 아무것도 안 보인다. 반대로 수동 지정만
두면 상품이 천 개인 사이트에서 운영자가 다 지정할 수 없다.

수동 지정을 먼저 쓰고, 남는 자리를 함께 구매로 채운다. 이미 나온 상품은
다시 넣지 않는다.

### 추천에서 반드시 빼야 하는 것

추천은 틀리면 손해로 이어진다.

- **`draft`·`hidden` 상품** — 아직 안 파는 것과 이미 내린 것을 노출한다.
  `draft` 노출은 정보 유출이기도 하다. 지정 자체는 허용한다(나중에 판매를
  시작할 수 있다) — 걸러는 것은 **표시할 때**다.
- **미결제 주문** — 장바구니를 만들어 두기만 한 것으로 추천이 생기면,
  아무도 안 산 조합이 "함께 구매"로 뜬다.
- **취소·반품된 항목** — 반품된 상품을 "함께 구매하셨습니다"로 미는 것은
  반품 사유를 반복시키는 짓이다. `quantity > cancelled_qty` 로 산 것만 센다.
- 자기 자신.

### slug 로 지정한다

uuid 는 운영자가 쓸 수 없고, 상품명은 중복될 수 있다. slug 는 유일하고
사람이 읽는다. 상품 옵션·설문 항목과 같은 줄바꿈 텍스트 방식이다.

**없는 slug 는 400 으로 거절한다.** 조용히 버리면 운영자는 지정했다고 믿는데
화면에는 안 나오고, 오타를 영원히 못 찾는다.

### 방향이 있다

A → B 를 지정해도 B 상세에는 A 가 안 나온다. 본품에서 액세서리를 보여주고
싶지만 그 반대는 원하지 않는 경우가 흔하다 — 액세서리 페이지에 본품이 나오면
오히려 이탈한다. 양방향이 필요하면 두 줄을 넣으면 된다.

### 함께 구매는 최근 주문 500건만 본다

많이 팔린 상품은 주문이 수만 건이고, 전부 훑으면 상품 상세가 느려진다.
최근 500건이면 추천 순서는 거의 같다 — 오래된 주문일수록 지금의 경향과
멀다. **정확도보다 상세 페이지 응답 시간이 중요하다**(가장 많이 열리는
화면이다).

### 추천이 없으면 아무것도 내지 않는다

"관련 상품이 없습니다" 를 띄우면 빈 영역이 페이지를 늘리기만 하고, 새
쇼핑몰에서는 모든 상품에 그것이 붙는다.

### 수정 저장이 관련 상품을 지우지 않게

관리 목록 응답에 `related_text` 를 채워 보낸다. 폼이 기존 값을 받지 못하면
상품을 수정할 때마다 빈 값이 전송되어 **관련 상품이 조용히 날아간다.**
옵션·이미지와 같은 문제이고, 같은 방식으로 막는다.

## ADR-54. 세금 증빙: 거짓으로 "발급됨"을 표시하지 않는다

부가가치세법 제32조의2·제46조: 최종소비자가 요청하면 현금영수증을
**발급해야 하고**, 미발급은 미발급액의 20% 가산세다. 여기까지가 "돈을 받을
수 있다"와 "돈을 받아도 된다"의 차이다.

### 카드 결제에는 발급하지 않는다 — 옵션이 아니라 거부한다

카드는 카드사가 국세청에 자동 통보한다. 현금영수증을 또 발급하면 **같은
매출을 두 번 신고**하고 손님도 이중 공제를 받는다. 그래서 무통장·현금
결제에만 허용하고, 카드 주문에는 이유를 붙여 400 으로 거절한다.

### 기본 발급 수단은 "수동"이다

국세청 직접 연동은 사업자 인증서가 필요해서 실무는 PG 사 API 를 경유한다.
PG 마다 달라서 게이트웨이로 추상화했지만(`registerCashReceiptGateway`),
**기본값은 아무것도 자동으로 하지 않는 수동 모드**다 — 운영자가 홈택스에서
발급하고 승인번호를 Brick 에 적는다.

`LogMailProvider`·`bankTransferGateway` 와 같은 판단이다. PG 계약이 없는
사이트에서 "발급됨"이라고 표시되고 실제로는 아무 일도 없는 것이 최악이다.
수동 모드는 상태를 `requested` 로 남겨 **발급되지 않았음을 화면에
드러낸다.** 그리고 **승인번호 없이는 `issued` 로 바꿀 수 없다** — 없으면
나중에 국세청 자료와 대조할 수 없어서, "발급했다"는 기록만 남는다.

### 금액은 셋을 합쳐 총액이 되어야 한다

공급가액 · 부가세 · 면세금액을 각각 반올림하면 1원이 어긋나고 국세청 검증에서
반려된다. 그래서 **공급가액을 먼저 정하고 부가세를 차액으로 구한다.**

```
면세금액 = 항목 스냅샷 기준
과세분   = 총액 − 면세금액
공급가액 = floor(과세분 / 1.1)
부가세   = 과세분 − 공급가액
```

### 면세 상품이 없으면 잘못된 증빙을 발급한다

도서·농수산물 등은 부가세가 없다(부가가치세법 제26조). 서점이 부가세를 붙여
발급하면 잘못된 증빙이고 손님은 환급받을 수 없다. 상품에 `tax_free` 를 두고
영카트의 `it_notax` 를 이전한다 — 안 옮기면 도서 쇼핑몰이 이전 직후부터
틀린 증빙을 낸다.

**주문 항목에도 스냅샷을 남긴다.** 상품의 면세 설정은 바뀔 수 있고(세법
개정, 운영자의 설정 오류 수정), 그때 **이미 신고한 과거 주문의 증빙 금액이
달라지면 사고다.**

### 증빙할 금액은 "실제로 받은 돈"이다

총 결제액에서 완료된 반품의 환불액을 뺀다. 판매 리포트(ADR-51)와 같은
정의다 — 반품한 만큼 증빙하면 세금을 더 낸다.

### 반품이 완료되면 증빙을 취소한다

**환불했는데 증빙이 살아 있으면 세금을 더 낸다.** 반품 완료에 연결했다.
교환은 금액이 변하지 않으므로 건드리지 않는다.

취소 실패는 조용히 넘기지 않는다 — 행에 사유를 남겨 운영자가 홈택스에서
직접 취소하게 한다. 다만 **반품 처리 자체를 막지는 않는다**: 물건은 이미
돌려받고 환불도 나갔으므로, 반품이 안 끝나는 것보다 증빙 취소가 밀리는 게
낫다.

부분 취소는 지원하지 않는다. 국세청 API 가 부분 취소를 지원하지 않는 경우가
많아 **전액 취소 후 잔액으로 재발급**이 실무다. 그래서 중복 방지 인덱스를
`status IN ('requested','issued')` 부분 인덱스로 두어, 취소된 것은 다시
발급할 수 있게 했다.

### 발견한 버그: 증빙 취소를 PG 환불 실행에 걸었다

처음에는 `refunded > 0`(PG 가 실제로 환불한 금액)일 때만 증빙을 취소했다.
**무통장 주문에는 PG 결제 기록이 없어서 그 값이 항상 0이고, 현금영수증이
필요한 주문이 바로 그 무통장 주문이다.** 기능 전체가 무력화되는 조건이었다.
반품 건의 `refund_amount`(돌려줄 금액)로 판단하도록 바꿨다 — 운영자가 계좌로
직접 환불하더라도 증빙은 취소되어야 한다.

### 식별번호는 개인정보다

휴대폰 번호와 사업자등록번호를 저장하지만, 목록·응답에는 뒤 4자리만
내보낸다. 저장 자체는 필요하다 — 취소·재발급에 쓰고 발급 사실의 증거다.

용도와 번호 형태가 맞는지도 검증한다. 사업자가 소득공제용으로 받으면 매입세액을
공제받을 수 없고, 개인이 지출증빙용으로 받으면 연말정산에 안 잡힌다. 국세청이
반려하는데 **반려 사실을 늦게 알면 미발급 가산세를 맞는다.**

### 세금계산서는 "요청을 잃어버리지 않는 것"부터

국세청 전자세금계산서 연동은 사업자 인증서가 필요해서 이 단계에서는 하지
않는다. 대신 요청을 받아 목록으로 남긴다 — 지금까지 요청은 1:1 문의로 들어와
묻히고, 사업자 손님은 매입세액을 공제받지 못했다.

사업자등록번호는 **체크섬을 실제로 검증한다.** 이 함수를 코어로 옮겨
`@brick/plugin-sdk` 에서 내보냈다 — 사업자정보 표시(ADR-45)와 세금계산서
발급이 같은 규칙을 써야 하고, 두 곳에 복제하면 반드시 갈라진다.

### 부가세 신고 자료는 리포트와 같은 정의를 쓴다

**신고 숫자와 화면 숫자가 다르면 운영자는 둘 다 믿지 않는다.** 결제일 기준,
완료된 반품 차감 — 판매 리포트와 동일하다.

증빙 종류로 나눈다(신고서가 그렇게 요구한다): 카드 / 현금영수증 발행분 /
세금계산서 발급분 / **기타**. 마지막 것을 `missingProof` 로 따로 내보낸다 —
증빙 없는 현금 매출은 발급 누락일 수 있고, 그것이 가산세의 원인이다.

과세기간은 코드로 고른다(`1-final` = 제1기 확정, 4~6월). 운영자가 "1기
확정이 언제부터인지"를 매번 찾아보게 하면 틀린 기간으로 신고한다. 말일은
다음 달 0일로 구해 윤년·30/31일을 직접 다루지 않는다.

집계에는 **세무 담당자와 확인하라는 경고를 함께 내보낸다.** 쇼핑몰 주문만
들어 있고 다른 경로의 매출·매입은 없으므로, 이것만으로 신고하면 틀린다.

## ADR-55. 2단계 인증: 잠기지 않게 만드는 것이 절반이다

**관리자 계정이 뚫리면 사이트 전체를 잃는다.** 회원 개인정보, 주문 내역,
결제 정보 접근 권한이 한 계정에 몰려 있고, 유출되면 개인정보보호법상 신고
의무가 생긴다. 재사용된 비밀번호는 다른 사이트 유출로 뚫리고, 그 사실을
우리는 알 수 없다.

그런데 2FA 는 **잘못 만들면 본인을 영구히 배제한다.** 휴면 계정에서 배운
것과 같다(ADR: 휴면 해제 경로) — 되돌릴 수 없는 상태를 만들면 함정이 된다.
그래서 잠기지 않게 하는 데 설계의 절반을 썼다.

### 검증하기 전에는 켜지 않는다

등록(비밀 생성)과 활성화를 분리했다. 코드를 **한 번 성공적으로 검증**한
뒤에만 `is_enabled = true` 가 된다. 이 순서가 아니면 잘못된 비밀이 저장되고
본인은 로그인할 때 그것을 알게 된다 — 그때는 이미 못 들어간다.

### 복구 코드는 선택이 아니다

휴대폰을 잃으면 관리자가 자기 사이트에 들어갈 수 없다. 활성화 시점에 10개를
만들어 **한 번만** 보여준다. 남은 개수를 상태에 넣어, 복구 코드로 로그인할
때마다 몇 개 남았는지 알려준다.

해시는 sha256 을 쓴다. 비밀번호가 아니라 **우리가 만든 고엔트로피 난수**
(50비트)라 사전 공격이 불가능하고, argon2 를 쓰면 로그인 한 번에 최대 10회
검증이 필요해 수 초가 걸린다 — 그 느림 자체가 서비스 거부 수단이 된다.

소비는 `used_at IS NULL` 조건의 UPDATE 로 한다. 읽고 나서 쓰면 그 사이에
다른 요청이 끼어들어 **같은 코드가 두 번 쓰일 수 있다.**

### 강제 설정에서도 등록 경로는 열려 있다

`security.require_2fa_for_staff` 를 켜면 2FA 없는 관리자의 **관리 작업**을
막는다. 로그인 자체를 막지 않는다 — 설정을 켠 순간 아무도 못 들어오면
등록할 방법이 없어 사이트가 영구히 잠긴다.

`AdminGuard` 에서 막고, 등록 경로(`/api/me/security/*`)는 `AuthGuard` 만
쓰므로 열려 있다. 거절할 때 **무엇을 해야 하는지 문구로 알려준다.**

그 대신 강제가 켜진 상태에서는 관리자·운영자가 **스스로 끌 수 없다** —
끌 수 있으면 강제가 아니다.

### 비밀번호만으로 세션을 주지 않는다

2FA 가 켜진 계정은 비밀번호가 맞아도 세션 쿠키를 심지 않는다. 대신 5분 사는
**도전 토큰**을 준다. 이것으로는 아무것도 할 수 없다(세션 쿠키로도 Bearer
로도 통하지 않는다).

이를 위해 `AuthService.login()` 에서 비밀번호 검증부를 `authenticate()` 로
떼어냈다. 두 단계를 한 메서드에 두면 **"비밀번호만으로 세션이 나가는" 경로가
실수로 되살아나기 쉽다.**

### 같은 코드를 두 번 쓸 수 없다

`last_step` 에 사용한 타임스텝을 기록하고 그보다 작거나 같은 스텝을 거절한다.
30초 안에 코드를 본 사람(어깨 너머, 중간자)이 그것을 재사용하는 것을 검증
로직만으로는 막을 수 없다.

허용 창은 **±1스텝(±30초)**이다. 휴대폰 시계 오차와 입력 시간을 흡수하되
넓히지 않는다 — 창을 넓히는 만큼 가로챈 코드의 유효 시간이 늘어난다.

### 시도 횟수: 도전당 5회

6자리는 100만분의 1이다. 다섯 번이면 실수를 흡수하고 무차별 시도는 막는다.
넘기면 도전을 폐기해서 **비밀번호부터 다시 입력하게** 한다. IP 별 제한도
따로 둔다 — 도전을 계속 새로 만드는 것도 막아야 한다.

### 외부 패키지를 쓰지 않았다

필요한 것은 HMAC-SHA1 뿐이고 `node:crypto` 에 있다. 자체 호스팅 CMS 에서
**의존성 하나는 공급망 위험 하나**이고, 인증 경로에 들어가는 패키지라면
더 그렇다(이 프로젝트는 Dependabot 경고 61건을 정리한 이력이 있다).

대신 **RFC 6238 부록 B 의 표준 테스트 벡터 6개를 스모크에 넣었다.** 구현이
표준과 어긋나면 인증 앱이 만든 코드를 거절하고 **아무도 로그인할 수 없다** —
직접 구현했다면 이 검증이 없으면 안 된다.

### 비밀을 암호화하지 않는다

암호화하려면 키가 필요하고 그 키는 같은 서버의 환경변수에 있다. DB 를 읽을
수 있는 공격자는 키도 읽으므로 **방어가 되지 않는데** 복잡도만 늘고 키
분실 시 전원이 잠긴다. 실질적 방어는 DB 접근 자체를 막는 것이다.

## ADR-56. 세션 목록은 계정 침해를 알아채는 유일한 방법이다

"지금 내 계정에 누가 접속해 있나"를 볼 수 없으면, 계정이 뚫린 것을
피해가 드러날 때까지 모른다.

`sessions` 에 토큰 해시와 만료 시각만 있어서 목록을 만들 수 없었다.
접속 정보를 더했다.

**IP 는 해시로만 저장한다** (ADR-35 와 같은 원칙). 원본을 남기면 접속 위치
이력이 되고, 그것은 우리가 보관할 이유가 없는 개인정보다. 같은 IP 인지
비교하는 데는 해시로 충분하다.

**User-Agent 는 사람이 읽는 이름으로 바꿔 보여준다** ("Mac · Chrome").
원문을 그대로 보여주면 아무도 읽지 않는다. 완벽한 판별이 목적이 아니라
**"내가 쓰는 기기인가"를 알아보게** 하는 것이 목적이다.

판별 순서가 중요하다 — Chrome 의 UA 는 Safari 를 포함하고 Edge 는 Chrome 을
포함하므로, 좁은 것부터 본다.

### "다른 기기 모두 끊기"는 지금 세션을 남긴다

계정이 뚫렸다고 의심할 때 누르는 버튼이다. 자기까지 끊기면 다시 로그인해야
하고, **그 사이 공격자가 먼저 들어올 수 있다.**

## ADR-57. 감사 로그는 사람과 기간으로 좁힐 수 있어야 한다

화면은 있었지만 **동작별 필터뿐이었다.** "누가 무엇을 했나"를 조사하는 것이
감사 로그의 용도인데, 그것으로는 사람을 따라갈 수 없다 — 사고가 났을 때
수만 건을 넘겨보게 된다.

행위자(이메일 부분 일치)와 기간을 더했다.

- **부분 일치**로 찾는다. 정확한 주소를 모를 수 있다. `%` 와 `_` 는
  이스케이프해 **와일드카드 주입**을 막는다(`actor=%` 로 전체를 긁는 것).
- **기간은 사이트 시간대로 자른다.** 판매 리포트와 같은 값을 쓴다(ADR-51) —
  UTC 로 자르면 한국에서 오전 9시 이전 기록이 전날로 밀려서, "어제 무슨
  일이 있었나"를 볼 때 엉뚱한 범위를 본다.
- `to` 는 **그날 끝까지** 포함한다. 오늘까지 조회했는데 오늘이 빠지면
  조용히 놓친다.
- 잘못된 날짜 형식은 **무시한다** (500 을 내지 않는다). 조사 중에 화면이
  깨지는 것이 최악이다.

`/api/audit/actions` 로 기록된 동작 목록을 준다 — 무엇이 기록되는지는
플러그인에 따라 달라지므로 화면이 미리 알 수 없다.

### 발견한 버그 둘

**복구 코드가 TOTP 로 오인됐다.** 처음에는 "숫자만 남겼을 때 6자리면 TOTP" 로
판단했다. base32 알파벳에는 숫자 2~7 이 있어서 **10자 복구 코드에 숫자가 정확히
6개 들어가는 경우가 0.4% 확률로 생긴다** — 사용자 10명 중 4명은 못 쓰는 코드를
하나 갖는다. 그리고 그 사실은 **휴대폰을 잃어 복구 코드를 쓰는 순간에만**
드러난다. 구분자를 떼면 TOTP 는 6자, 복구 코드는 10자이므로 **길이로 구분한다.**

**스모크가 전부 통과했는데 CI 가 실패했다.** 정리 트랩에서 kill 한 프로세스를
`wait` 하면 그 종료 코드(143 = SIGTERM)가 스크립트의 종료 코드가 되고, 뒤에서
`exit 0` 을 해도 덮이지 않는다. `|| true` 로 흡수해야 한다.

앞서 고친 "스모크가 자기 실패를 숨겼다"와 **짝을 이루는 반대 방향의 버그**다.
하네스는 양쪽 다 정확해야 하고, 고칠 때는 **일부러 실패시켜 종료 코드가 1이
되는지도** 확인해야 한다.

## ADR-58. 돈이 나가는 경로는 스텁 PG 로 검증한다

부분 환불 금액이 PG 로 전달되는 코드는 있었다. **검증이 없었다.**

무통장 게이트웨이의 `cancel()` 은 인자를 무시하고 성공을 반환하고, 모든
스모크가 무통장만 썼다. 그래서 "10,000원 반품에 22,000원을 환불 요청" 같은
버그가 있어도 전부 통과했을 것이다.

돈이 걸린 경로는 **실제로 무엇이 나가는지 봐야 한다.** SMTP 싱크(ADR-50)와
같은 판단이다. `scripts/pg-stub.mjs` 는 토스페이먼츠 API 모양의 최소 서버로,
받은 요청을 기록하고 실제 PG 처럼 초과 취소를 거절한다.

이를 위해 게이트웨이의 API 주소를 `BRICK_TOSS_API_BASE` 로 바꿀 수 있게
했다. 운영에서 잘못 설정되어 카드 정보가 평문으로 나가는 것을 막기 위해
**https 가 아닌 주소는 localhost 일 때만** 허용한다.

### 발견한 버그 1: 승인 멱등키가 주문번호뿐이었다

`confirm-${orderNo}` 였다. 토스는 같은 멱등키에 **저장된 응답을 그대로
돌려주므로**, 금액이나 결제키가 잘못된 첫 시도의 실패 응답이 재생된다.

결과: **손님이 그 주문을 영구히 결제할 수 없다.** 위젯이 만료되어 결제키가
낡았거나 금액을 잘못 보낸 한 번의 시도가 그 주문을 막아버린다.

멱등성의 목적은 **같은 요청의 재시도**를 안전하게 하는 것이다. 요청을
유일하게 만드는 값(결제키·금액)을 모두 키에 넣었다.

### 발견한 버그 2: 취소 멱등키가 금액별이었다

`cancel-${providerTid}-${amount}` 였다. **같은 금액의 서로 다른 취소가 하나로
합쳐진다** — 같은 가격 상품 두 개를 따로 반품하면 두 번째 환불 요청이 PG 에서
재생되고, 우리는 `refunded_amount` 를 올려 환불했다고 기록한다.

**돌려줘야 할 돈이 사업자에게 남는다.** 손님은 두 번 반품했는데 한 번만
환불받고, 장부는 두 번 환불한 것으로 보인다.

취소 동작을 유일하게 아는 것은 **누적 환불액을 가진 호출자**다. 게이트웨이
계약에 `idempotencyKey` 를 추가하고 `refundPayment` 가
`cancel-${paymentId}-${already}-${amount}` 로 만들어 넘긴다. 커밋되지 않은
재시도는 `already` 가 그대로이므로 같은 키가 되어 PG 가 한 번만 처리한다 —
정확히 의도한 동작이다.

### 발견한 버그 3: 키를 넣지 않은 PG 가 결제수단으로 떴다

`payment-methods` 가 등록된 게이트웨이를 전부 나열했다. 플러그인을 설치하고
키를 넣지 않은 사이트에서 **손님이 그것을 고르면 "설정되지 않았습니다"로
실패한다.** 사이트가 고장난 것처럼 보이고, 그 손님은 다시 오지 않는다.

게이트웨이 계약에 `isReady?()` 를 더했다. 없으면 준비된 것으로 보므로
무통장입금과 기존 게이트웨이는 영향이 없다.

### 환불 응답에 `refundedNow` 를 분리했다

`refunded` 하나만 주면 운영자가 "이번에 얼마가 나갔는가"와 "지금까지 얼마가
나갔는가"를 구분할 수 없다. 부분 환불을 여러 번 하는 상황에서 이 구분이
없으면 장부를 맞출 수 없다.

## ADR-59. 개인결제는 그림자 주문을 만든다

전화·상담·SNS 로 주문받고 **금액만 청구**하는 방식. 그누보드 쇼핑몰이 실제로
많이 쓴다 — 맞춤 제작, 견적 후 결제, 추가 배송비 청구, 오프라인 주문의
온라인 수납.

### 결제만 따로 만들면 매출이 샌다

판매 리포트(ADR-51)와 부가세 신고 자료(ADR-54)는 `shop_orders` 를 기준으로
센다. 주문 없는 결제는 거기에 안 잡히므로 **세금 신고에서 빠지는 매출**이
생긴다. 그것은 사고다.

그래서 청구서를 결제할 때 주문을 만든다. 청구 제목을 상품명으로 하는 항목
하나를 넣으면 상품별 리포트와 증빙 금액 분해가 그대로 동작한다.
`product_id` 는 NULL 이므로 재고를 건드리지 않는다.

`is_direct_payment` 로 표시하는 이유: 주문 목록에서 **배송할 상품이 없는
주문**임을 운영자가 알아야 한다. 배송 준비로 넘기려다 혼란이 생긴다.

### 결제는 일반 주문과 같은 경로를 쓴다

청구서로 주문을 만들고, 그 뒤 결제는 기존 `/payments/confirm` 이다.
개인결제 전용 결제 경로를 만들면 **금액 위조 방어를 두 번 구현**해야 하고,
한쪽이 뒤처지면 그쪽으로 우회된다.

### 링크 토큰은 추측 불가능해야 한다

비회원도 결제해야 한다(전화 주문 손님이 회원일 이유가 없다). 청구번호를
링크에 쓰면 순차적이라 **남의 청구서를 열어볼 수 있다** — 거래 내용과 금액,
받는 사람 이름이 새어 나간다. 32바이트 난수를 쓴다.

### 기한을 둔다

금액을 고쳐 다시 청구하는 일이 흔하다. 옛 링크가 살아 있으면 손님이 그것으로
결제해 **금액이 틀린 결제**가 생긴다. 기본 7일.

만료는 **조회 시점에 계산한다.** 배치로 상태를 바꾸면 배치가 안 돌 때 만료된
링크가 살아 있게 된다.

### 금액 수정을 두지 않았다

링크를 이미 보낸 뒤 금액이 바뀌면 손님이 어느 금액을 본 것인지 알 수 없고,
그것이 분쟁이 된다. 취소하고 새로 청구해야 한다.

**결제된 청구서는 취소할 수 없다** — 환불은 결제 관리에서 해야 한다. 여기서
"취소"로 바꿔주면 운영자가 환불했다고 착각한다.

### 결제 완료 반영은 훅을 쓰지 않는다

`markRequestPaid` 를 직접 부른다. HookBus 의 `doAction` 은 플러그인별 예외를
삼키므로(설계 의도다) 실패해도 아무도 모르고, **손님은 결제했는데 청구서는
"대기"로 남는다.** 같은 플러그인 안의 일이니 훅을 거칠 이유도 없다.

## ADR-60. 통합검색은 공급자 레지스트리로 모은다

기존 `/api/search` 는 **페이지만** 찾았다. 게시글도 상품도 검색되지 않았다 —
그누보드에서 검색은 게시판 통합검색이 기본인데, 이쪽은 검색창에 무엇을 넣어도
정적 페이지만 나왔다.

코어가 게시글·상품 테이블을 알면 안 되므로 `registerSearchSource` 로 받는다.
사이트맵(ADR-40)·개인정보 삭제(ADR-38)와 같은 방향이다.

### 발견한 버그: total 이 페이지의 행 수였다

`total: rows.length` 였다. 500건이 맞아도 20을 돌려주므로 **페이지네이션이
동작하지 않았다** — 화면은 항상 1페이지뿐이라고 판단하고, 나머지 480건은
아무도 볼 수 없었다.

그래서 공급자 계약에 `count` 와 `search` 를 나눠 두고, **같은 조건을 쓰도록**
조건을 한 곳에 두라고 명시했다. 다르면 "37건" 이라 표시하고 20건만 보여주거나
마지막 페이지가 비어 나온다.

### 정렬을 고정해야 한다

정렬이 없으면 PostgreSQL 이 매번 다른 순서를 줄 수 있고, 페이지를 넘길 때
**같은 항목이 두 번 나오고 어떤 항목은 빠진다.** 사이트맵에서 배운 것과 같은
문제다. 스모크에서 1·2페이지의 교집합이 0이고 합집합이 전체인 것을 확인한다.

### 권한이 가장 중요하다

**검색은 권한 검사를 우회하는 가장 흔한 경로다.** 목록에 제목만 나와도 내용이
새어 나가는 경우가 있다 — 비밀글 제목, 비공개 게시판의 존재, 미공개 상품의
이름과 가격.

그래서 공급자에게 `viewer` 를 넘기고, 각 공급자가 거른다:

- 게시글 — 읽기 권한을 **등급으로 비교**한다(문자열 비교로는 순서를 알 수
  없다). 모르는 값은 admin 으로 봐서 **막는 쪽으로 실패한다** — 오타 하나로
  비공개 게시판이 열리면 안 된다.
- 비밀글 — **관리자에게도 보여주지 않는다.** 작성자에게만 보여주는 것도
  가능하지만, 검색 결과에 자기 비밀글이 섞이면 화면을 공유할 때 새어 나간다.
- 상품 — `draft`·`hidden` 제외. 품절은 **포함한다**(재입고를 기다리는 손님이
  있고, 그것도 정보다).

### ILIKE 이스케이프

`%` `_` `\` 를 이스케이프하지 않으면 손님이 `%` 를 검색하면 전체가 나온다.
그것은 검색이 아니라 **전체 목록 유출**이다.

### 한 공급자가 죽어도 나머지는 보여준다

플러그인 하나의 SQL 오류로 검색 전체가 죽으면 사이트가 고장난 것처럼 보인다.
실패는 경고 로그로 남기고 그 그룹만 빠진다.

## ADR-61. 검색 로그: 못 찾고 나간 것이 가장 값진 데이터다

**무엇을 찾다가 못 찾고 나갔는지가 운영자에게 가장 값지다.** 쇼핑몰이면
결과 0건은 팔 수 있었는데 못 판 것이고, 사이트면 안내가 없어서 문의로
이어지는 것이다. 그런데 아무 기록도 없었다.

### 정규화가 없으면 집계가 흩어진다

`"  아이폰  케이스 "` 와 `"아이폰 케이스"` 가 다른 검색어로 세어지면 인기
검색어가 조각나 아무 의미가 없다. 앞뒤 공백을 떼고, 연속 공백을 하나로 줄이고,
소문자로 바꿔 저장한다. 원문도 함께 남긴다 — 정규화가 무엇을 지웠는지 확인해야
할 때가 있다.

### 한 사람의 반복이 1위가 되면 안 된다

인기 집계에서 **(검색어, 사람, 날짜)** 를 중복 제거한다. 하지 않으면 한 사람이
열다섯 번 검색한 것이 인기 1위가 되고, 그 목록은 화면에 노출된다.

사람을 식별하는 값은 `user_id → ip_hash → 로그 id` 순으로 떨어진다. 마지막
단계는 "식별할 수 없으면 각각 다른 사람으로 본다"는 뜻이다 — 묶어서 과소
집계하는 것보다 낫다.

### 빈손 비율을 함께 준다

인기 검색어에 `emptyRatio` 를 붙인다. **인기 있는데 결과가 없는 것이 가장
먼저 손봐야 할 것**인데, 두 목록을 따로 보면 그 교집합이 눈에 안 들어온다.

### IP 는 해시로만

검색어는 그 자체로 민감할 수 있다 — 질병, 법률, 재정 문의. 접속 위치와 함께
보관할 이유가 없다 (ADR-35 와 같은 원칙). 같은 사람의 연속 입력을 묶는 데만
쓰므로 해시로 충분하다.

보관 기간도 둔다(기본 180일). 집계 목적이 끝나면 남길 이유가 없다.

### 치환과 차단

- **치환** — "아이폰15" 로 찾는데 상품명이 "iPhone 15" 면 결과가 0건이다.
  로그를 보고 운영자가 연결해줄 수 있어야 한다. 치환했으면 **원래 검색어를
  응답에 담아** 화면이 "'우비'로 검색한 결과를 '우산'으로 찾았습니다"를 보여줄
  수 있게 한다.
- **차단** — 인기 검색어 집계에서만 제외한다. **검색 자체는 막지 않는다** —
  경쟁사명을 검색하는 손님을 막을 이유가 없고, 막으면 사이트가 이상해진다.
  차단의 목적은 화면에 노출되는 목록을 관리하는 것이다.

관리 화면은 **0건 목록에서 바로 치환 규칙 폼으로 이어진다**. 두 화면이 떨어져
있으면 운영자가 목록을 보고 아무것도 하지 않는다.

## ADR-62. escapeHtml 이 undefined 에서 터졌다

페이지 렌더러는 모르는 블록을 `<!-- unknown block: ... -->` 주석으로 넘기도록
쓰여 있었다. 그런데 그 안의 `escapeHtml(node.block)` 이 `s.replace` 를 바로
불러서 **`node.block` 이 없으면 그 자리에서 터졌다** — 잘못된 블록 하나로
페이지 저장이 500 이 났다.

이스케이프는 화면을 안전하게 만드는 함수다. **그것이 요청을 죽이면 안 된다.**

구현이 API 에 두 벌 있었으므로 코어로 옮기고 `String(value ?? "")` 로 감쌌다.
`stripHtml` 도 마찬가지로 세 번째 복제를 만들지 않고 코어로 올렸다 — 검색
발췌와 메일 텍스트 대안이 같은 규칙을 써야 하고, 플러그인도 써야 한다
(게시글·상품 본문은 HTML 이다).

같은 판단을 사업자등록번호 체크섬(ADR-54)에서 이미 했다. **여러 곳에서 쓰는
순수 함수는 코어에 두고 SDK 로 내보낸다.**

## ADR-63. 재입고 알림: 스팸 도구가 되지 않게, 광고가 되지 않게

품절 상품을 찾아온 손님에게 지금은 할 수 있는 것이 없었다. 그 손님은 다시
오지 않고, **팔 수 있었던 것을 못 판다.** 통합검색에서 품절 상품을 결과에
포함시킨 것(ADR-60)과 이어지는 판단이다 — 찾아오게 했으면 할 것을 줘야 한다.

### 이메일만 받는 기능은 스팸 도구가 될 수 있다

남의 주소를 넣고 알림을 보내게 만들 수 있다. 이메일 확인 절차를 요구하면
실제 손님의 신청률이 크게 떨어지므로, 다른 방향으로 막았다:

- 같은 (상품, 옵션, 주소) 조합에 신청은 **하나뿐**이다
- 알림은 재입고 시 **한 번만** 가고 그 자리에서 소진된다
- 발송의 방아쇠는 **운영자의 재입고 행위**다 — 신청자가 시점을 못 정한다
- 메일에 "신청하지 않으셨다면" 안내와 **로그인 없는 해지 링크**를 넣는다
- 신청 응답에 **주소를 가려서** 돌려준다(`gu****@rs.test`) — 원본을 그대로
  주면 "이 주소가 신청되어 있는가"를 확인하는 수단이 된다

공격자가 얻는 것은 "타인에게 재입고 메일 1통"이고 그 시점조차 통제할 수
없다. 이 정도가 맞는 균형이다.

### 광고가 아니어야 한다

재입고 알림은 **손님이 요청한 정보**이므로 정보통신망법 제50조의 광고성
정보가 아니다(수신 동의 불필요, `(광고)` 표기 불필요).

단, 그 메일에 **다른 상품을 끼워 넣으면 광고가 된다.** 그래서 본문은 신청한
상품 정보만 담고, **운영자가 문구를 넣을 자리를 두지 않았다.** 자유 입력을
허용하면 언젠가 "이 상품도 보세요"가 들어가고, 그 순간 위법이 된다
(ADR-50 과 같은 판단 — 운영자가 위법을 저지를 수 없게 만든다).

### 옵션 단위로 받는다

옵션이 있는 상품은 **옵션 단위로 품절된다** — "M 사이즈만 품절"이 대부분이다.
상품 단위로만 받으면 L 이 들어왔을 때 M 을 기다린 손님에게 잘못된 알림이 간다.

그리고 옵션 하나만 품절이면 상품 상태는 여전히 `selling` 이라 **품절 화면이
뜨지 않는다.** 가장 흔한 경우인데 폼이 안 보이면 기능이 없는 것과 같으므로,
살 수 있는 상품에도 품절 옵션이 있으면 신청 폼을 보여준다.

### 재입고 감지는 스윕으로 한다

재고가 오르는 지점이 여러 곳이다: 주문 취소, 반품 완료, 관리자의 상품·옵션
수정, 영카트 이전 도구, 그리고 앞으로 생길 것들.

**각 지점에 알림 호출을 붙이면 반드시 하나를 빠뜨린다** — 그리고 빠뜨린
경로로 재입고된 상품의 대기자는 영원히 알림을 못 받는데, 아무도 그것을
눈치채지 못한다.

주기적으로 "대기자가 있는데 재고가 있는 조합"을 찾으면 **경로와 무관하게**
잡힌다. 직접 SQL 로 재고를 넣어도 잡힌다. 재입고 알림에 몇 분의 지연은 아무
문제가 없으므로 이 교환은 명백히 유리하다.

`soldout` 상태는 존중한다 — 재고가 있어도 운영자가 일부러 내린 것이므로
알림을 보내지 않는다. `draft`·`hidden` 도 마찬가지다(눌러도 살 수 없다).

### 발송 전에 소진 표시를 한다

`UPDATE ... RETURNING` 으로 `notified` 로 바꾸면서 가져온다. 반대로 하면
발송 중 서버가 죽었을 때 **같은 사람에게 두 번 간다.**

두 번 가는 것이 안 가는 것보다 나쁘다 — 스팸으로 신고되고, 그것은 도메인
평판에 남는다. 그래서 "보냈는데 기록을 못 남기는" 쪽보다 "기록했는데 못
보내는" 쪽을 택했다.

소진된 신청은 다시 만들 수 있다(또 품절될 수 있다). 중복 방지 인덱스를
`status = 'pending'` 부분 인덱스로 둔 이유다.

### option_id 가 NULL 이면 유니크 인덱스가 중복을 못 막는다

PostgreSQL 에서 NULL 은 서로 다르게 취급되므로, `(product_id, option_id,
email)` 유니크 인덱스는 **옵션 없는 상품에 무한히 신청할 수 있게** 한다.
`coalesce(option_id, '00000000-...'::uuid)` 로 고정값을 넣어 막았다.

## ADR-64. 플러그인 계약에 로그·사이트 정보를 더했다

### 플러그인이 로그를 남길 방법이 없었다

요청 처리 중 오류는 코어가 잡아 응답으로 만들지만, **백그라운드 작업(큐
워커·스윕)의 실패는 아무도 모른다.** 조용히 실패하는 배경 작업은 없는 기능과
같다 — 그리고 그것이 없다는 사실조차 드러나지 않는다.

`ctx.logger` 에 플러그인 이름을 자동으로 붙인다. 여러 플러그인이 도는
사이트에서 어느 플러그인이 낸 로그인지 모르면 추적할 수 없다.

### 사이트 주소·이름도 계약으로

메일에 링크를 넣는 플러그인이 여럿이다. 각자 `process.env.BRICK_SITE_URL` 을
읽으면 코어의 검증(형식 확인·후행 슬래시 정리)을 우회하고 플러그인마다 다르게
처리한다.

사이트 이름은 **매번 읽는다** — 운영자가 이름을 바꾸면 다음 메일부터 반영되어야
한다. 활성화 시점에 캐시하면 재시작할 때까지 옛 이름으로 나간다.

### 반복 작업은 큐 잡이 스스로 다시 예약한다

큐에는 반복 실행 기능이 없다. `setInterval` 을 쓰면 (1) 플러그인을
비활성화해도 계속 돌고, (2) 서버가 여러 대면 모두가 돌아 같은 일을 중복한다.

잡 핸들러 끝에서 `delaySeconds` 로 다음 실행을 예약하면 **한 워커에서만**
실행되고, 실패해도 큐가 재시도하므로 사슬이 끊기지 않는다.

## ADR-65. 연결 대상 레지스트리 — 주소를 타이핑하게 하면 연결되지 않는다

메뉴 편집이 `이름 + 주소 직접 입력`이었다. 운영자는 만든 게시판의 slug 를
외워 `/board/free` 를 손으로 적어야 했고, **오타가 나도 저장은 되고 눌러야
404 를 본다.** "페이지를 만들었는데 메뉴에 어떻게 붙이나"가 가장 흔한
막힘이었다 — 기능이 있어도 연결하는 법을 모르면 없는 것과 같다.

`registerLinkTarget` 으로 각 플러그인이 자기가 아는 주소(게시판, 상품 분류,
쇼핑몰 고정 화면)를 내놓고, 관리 화면의 선택기가 그것을 모아 보여준다.
고르면 **주소와 이름이 함께** 채워진다. 사이트맵(ADR-40)·검색(ADR-60)과 같은
방향이다 — 코어는 페이지만 알고, 나머지는 등록으로 모은다.

### 설계 판단들

- **직접 입력을 없애지 않았다.** 외부 링크와 앵커는 목록에 있을 수 없다.
- **`home` 은 `/` 로 준다.** slug 그대로 `/home` 을 링크하면 404 다 —
  선택기가 있으면 이런 변환 규칙을 운영자가 알 필요가 없어진다.
- **임시 저장 페이지도 보여주되 표시한다.** 곧 공개할 페이지를 미리 메뉴에
  넣는 것이 실제 작업 순서다. 숨기면 "왜 목록에 없나"로 헤맨다.
- **비공개 게시판은 경고만 한다.** 메뉴에 넣으면 손님이 권한 오류를 보지만,
  운영진 전용 메뉴를 두는 사이트가 있으므로 막지 않는다.
- **목록은 관리자 전용이다.** 임시 페이지의 존재와 주소, 비공개 게시판
  이름이 새어 나간다.
- **상한과 검색을 계약에 넣었다.** 분류 200개인 사이트에서 전부 내보내면
  선택기가 멈춘다. 화면이 아니라 공급자가 거른다.

### 표면 문구에서 특정 제품명을 뺐다

README·랜딩·관리 화면·문서 첫 문장이 전부 "그누보드처럼/영카트에 대응"
이었다. 참조가 없으면 설명이 안 되던 시기는 지났고, 이제는 Brick 을 그
제품의 클론으로 읽히게 만들 뿐이다. **이전 도구의 사실 설명(무엇을 어디서
옮기는가)에는 이름을 남겼다** — 지우면 필요한 사람이 기능을 못 찾는다.

## ADR-66. 사이트 스타터 — 설치가 끝나면 이미 돌아가는 사이트가 있어야 한다

설치는 관리자 계정과 사이트 이름만 만들었다. **설치 직후 사이트를 열면
아무것도 없다.** 운영자는 빈 화면 앞에서 페이지·게시판·메뉴를 전부 손으로
만들어야 하고, 대부분은 거기서 멈춘다 — 무엇부터 해야 하는지 모른다.

설치할 때 사이트 유형(커뮤니티 / 쇼핑몰 / 회사 홈페이지 / 빈 사이트)을
고르면 그 유형의 기본 구성이 통째로 만들어진다: 홈 + 하위 페이지 + 게시판 +
헤더 메뉴 + 필요한 플러그인 활성화. 설치가 끝나면 **이미 돌아가는 사이트**가
있고, 할 일은 내용을 자기 것으로 바꾸는 것뿐이다.

### 스타터 전용 개념을 만들지 않았다

만들어지는 것은 전부 **일반 페이지·게시판·메뉴**다. 페이지 빌더와 메뉴
편집에서 똑같이 수정·삭제할 수 있다. "기본 구성"이 특별 취급되면 수정하는
법을 따로 배워야 하고, 그 순간 스타터는 도움이 아니라 짐이 된다.

같은 이유로 유형은 넷뿐이다. 선택지가 많을수록 고르다 지친다 — 설치 화면에서
필요한 것은 "대충 이 방향"이고 세부는 나중에 바꾼다.

### 스타터 실패가 설치를 실패시키지 않는다

플러그인 활성화는 마이그레이션을 돌리므로 실패할 수 있다. 스타터는 설치
성공 **뒤에** 적용하고, 각 단계는 실패해도 다음으로 넘어간다. 반쯤 만들어진
기본 구성은 고칠 수 있지만, 설치가 실패하면 처음부터다.

블록 이름이 잘못돼도 사이트는 깨지지 않는다 — 렌더러가 "unknown block"
주석으로 넘긴다(ADR-62 에서 그렇게 만들었다). 대신 스모크가 **렌더 결과에
그 주석이 없는지** 확인한다: 조용히 빈 곳이 되는 것이 이 방식의 함정이므로
테스트가 잡아야 한다.

### 자리표시 문구는 실제로 쓸 법한 예문으로

"여기를 수정하세요"만 있는 페이지는 버려진 사이트처럼 보인다. 사이트 이름을
섞은 예문("달빛마을에 오신 것을 환영합니다")을 넣고, **어디서 수정하는지**를
문구에 담는다. 쇼핑몰 스타터의 이용 안내에는 교환·반품의 뼈대를 넣었다 —
전자상거래법 표시 의무의 출발점이 된다.

### 모르는 유형은 거부한다

오타(`comunity`)를 조용히 빈 사이트로 만들면, 운영자는 스타터가 고장났다고
생각한다. 400 으로 알려준다. `starter` 를 아예 안 주면 빈 사이트다 — 기존
API 호출(테스트 수트 전부)과의 호환이다.

### 발견한 함정: 테스트 서버 재시작

수트가 서버를 세 번 재시작하는데, 이전에 잘린 테스트가 남긴 **고아 서버가
포트를 잡고 있으면 우리 서버는 죽고 readyz 는 고아가 응답해 통과한다.**
요청은 전부 옛 상태의 고아에게 가고 DB 만 리셋되어 "relation does not
exist" 500 이 난다 — 원인을 찾기 아주 어렵다. 포트를 정리하고 **응답한
것이 우리 프로세스인지** 확인한다 (SMTP 스텁에서 배운 것과 같은 함정).

## ADR-67. 원클릭 업데이트 — 서명 검증이 뿌리다

원격에서 코드를 받아 설치하는 기능은 서명 검증 없이 만들면 **원격 코드
실행의 문**이 된다. 업데이트 서버가 뚫리거나 DNS 가 조작되면 임의 코드가
들어온다 — 오래된 CMS 들이 실제로 겪은 사고 유형이고, 로드맵에서 이것을
플러그인 레지스트리보다 먼저 두었다. **이것 없이 레지스트리를 열면 배포
사고가 계약이 된다.**

### 신뢰 모델: 처음 설치할 때 키를 고정한다 (TOFU)

확장 매니페스트에 배포자의 Ed25519 공개키(`publisherKey`)가 들어 있고,
**처음 설치 — 운영자가 ZIP 을 직접 올리는 명시적 신뢰 행위 — 에서 그 키가
고정된다.** 이후의 원격 업데이트는:

1. 업데이트 매니페스트(JSON)를 https 로 받고
2. ZIP 을 내려받아
3. **지금 설치된 매니페스트의 키**로 ZIP 서명을 검증한다

업데이트 매니페스트나 새 ZIP 이 주장하는 키는 검증에 쓰지 않는다 — 그것을
믿으면 공격자가 자기 키를 함께 보내면 끝이다. 설치 후에는 **고정된 키를
되살린다**(repin): 새 매니페스트가 키를 바꿔치기해서 한 번의 침투가 영구
장악이 되는 것을 막는다. 키 교체는 운영자의 직접 업로드로만 된다.

중앙 인증기관을 두지 않았다. 레지스트리가 없는 지금 단계에서 CA 는 우리가
단일 장애점이 되는 것이고, TOFU 는 SSH 가 수십 년 검증한 모델이다.
레지스트리를 열 때 키 투명성 로그를 얹는 것은 그때의 결정이다.

### Ed25519 를 직접 쓴다

`node:crypto` 에 내장되어 있어 의존성이 없다. 인증 경로의 패키지는 공급망
위험이다 — TOTP(ADR-55)와 같은 판단. 매니페스트에는 raw 32바이트 키를
base64 로 넣고, 검증 시 SPKI DER 로 감싼다. 서명·검증 왕복과 변조 감지를
스모크의 첫 항목으로 뒀다.

### 막아 둔 것들

- **다운그레이드** — "새 버전"이 지금보다 높아야만 받는다. 낮은 버전을
  제시해 알려진 취약점이 있는 옛 버전을 되살리는 공격.
- **http 주소** — localhost 만 예외(테스트). 서명이 ZIP 변조는 막지만,
  평문 매니페스트를 "업데이트 없음"으로 조작해 **보안 패치를 숨기는 것**은
  서명으로 못 막는다. 전송 자체가 안전해야 한다.
- **크기 상한(50MB)·시간 제한(20초)·redirect 거부** — 악의적 서버가 우리를
  매달거나 내부 주소로 우회하는 것.
- **이름 불일치** — 매니페스트·ZIP 의 이름이 요청한 확장과 다르면 거부.
  다른 확장을 그 자리에 심으려는 시도다.
- **자동 적용 없음** — 확인과 적용을 분리했다. 새벽에 사이트가 저절로
  바뀌는 것을 원하는 운영자는 없다.

### 발견한 테스트 함정: "다른" ZIP 이 같은 바이트였다

변조 검증에서 `make_zip` 을 같은 인자로 다시 불러 "가짜 ZIP"을 만들었는데,
zip 의 mtime 은 2초 단위라 연속 생성이면 **바이트까지 동일**했다. 원본
서명이 그대로 통과했고, 검증이 아무것도 검증하지 않았다. 내용을 실제로
바꾼 ZIP 으로 고쳤다 — 부정 케이스는 **정말로 부정인지**부터 확인해야 한다.

## ADR-68. 회원 등급 — 혜택이지 권한이 아니다

역할(guest/member/manager/admin)과 별개다. 역할은 **권한**이고 등급은
**혜택**이다 — 섞으면 "VIP 라서 글을 지울 수 있다" 같은 사고가 난다.
(10단 숫자 레벨을 접은 ADR-25 와 이어지는 결정)

### 산정은 판매 리포트와 같은 정의를 쓴다

최근 3개월 **순매출** — 결제 완료 금액에서 완료된 반품 환불액을 뺀다
(ADR-51 과 동일). 반품을 빼지 않으면 **사서 반품하기를 반복해 등급을 올릴
수 있다.** 반품 시점이 기간 밖이어도 구매가 기간 안이면 그 반품을 뺀다 —
사서 기간이 지난 뒤 반품하는 우회도 막는다.

### 배정을 저장하고 주기 재계산한다

주문마다 실시간 계산하지 않는 이유:
1. 등급은 "이번 기간의 내 등급"으로 안내되는 값이다 — 주문 중에 바뀌면
   장바구니와 결제 화면의 할인이 달라져 혼란스럽다.
2. 기간 순매출 쿼리가 주문마다 돌기엔 무겁다.

재계산은 6시간 주기 자기 재예약 큐 잡(ADR-64 방식) + 관리자의 "지금 재계산".
재계산은 회원별 루프가 아니라 **한 문장의 INSERT ... ON CONFLICT** 다 —
회원 수만큼 쿼리를 내면 안 된다.

구매가 없는 회원도 기본 등급(min_amount = 0)에 배정한다. "등급 없음"과
"기본 등급"을 구분하지 않으면 마이페이지가 아무것도 안내할 수 없다.

### 할인 합산 규칙

등급 할인은 쿠폰과 **각각 subtotal 에서** 계산하고 합이 상품 금액을 넘으면
등급 쪽을 잘라낸다. 순차 적용(쿠폰 후 잔액에 등급율)은 적용 순서에 따라
금액이 달라져 "왜 이 금액인가"를 설명할 수 없다.

합산된 할인은 orders.discount 에 그대로 들어간다 — **환불 안분(ADR-44)과
판매 리포트(ADR-51)가 discount 를 기준으로 계산하므로 그 흐름이 전부 그대로
정합하다.** 내역 표시용으로 grade_discount·grade_name 스냅샷만 따로 남긴다
(등급이 나중에 바뀌어도 주문 내역은 그대로여야 한다).

### 견적과 주문이 같은 등급을 본다

pricing 은 회원 테이블을 모른다(포인트와 같은 관심사 분리). 라우트가
`gradeOf()` 로 읽어 견적과 주문 생성 **양쪽에** 넘긴다 — 한쪽만 넘기면
장바구니에서 본 금액과 결제 금액이 달라진다.

### 다음 등급까지 남은 금액을 보여준다

"₩57,000 더 구매하면 골드"가 이 기능의 존재 이유다. 등급만 보여주면 아무
행동도 유도하지 않는다. 산정에 쓰인 금액도 함께 준다 — "왜 이 등급인가"에
답할 수 없으면 문의가 된다.

## ADR-69. 쿠폰 고도화 — 조건은 신원을 전제한다

지금까지 쿠폰은 "코드를 아는 사람은 누구나, 전체 한도까지"였다. 실무에서
빠진 것은 전부 **"누구인가"를 전제하는 조건**이다.

### 1인당 한도는 주문 이력으로 센다

별도 카운터를 두지 않는다 — 카운터는 주문 취소 때 되돌리는 것을 잊는
순간부터 어긋나고, 그 어긋남은 조용하다. `취소 제외 주문 수`를 세면 취소
복원이 공짜로 따라온다(결제 실패로 취소된 주문이 쿠폰을 먹으면 안 된다).

### 첫 구매의 기준은 결제 이력이다

주문 이력으로 하면 **미결제 주문(장바구니에서 만들다 만 것)이 첫 구매
쿠폰을 막는다.** paid_at 이 있는 주문이 하나라도 있으면 첫 구매가 아니다.

### 회원 조건 쿠폰은 비회원을 로그인으로 안내한다

1인 제한·첫 구매·등급·발급형은 전부 신원을 전제한다. 비회원은 신원을 셀 수
없으므로 판정 자체가 불가능하다 — 조용히 통과시키면 조건이 무의미해지고,
조용히 거절하면 손님은 쿠폰이 고장난 줄 안다. "로그인 후 사용할 수 있는
쿠폰입니다"가 정답이다.

### 발급형(쿠폰함)은 코드 유출에 대한 답이다

코드형 쿠폰의 코드는 커뮤니티에 퍼진다 — 그 순간 대상 통제가 사라진다.
발급형은 쿠폰함에 지급받은 회원만 쓸 수 있고, 한 장이 한 번만 쓰인다
(`used_at IS NULL` 조건의 UPDATE — 복구 코드 소비와 같은 동시성 방어).

지급은 멱등하다(ON CONFLICT DO NOTHING) — "골드 전체 지급"을 두 번 누르면
두 장씩 가는 것이 아니라 빠진 사람만 채워진다. 같은 쿠폰의 재지급은 막는다:
재구매 유도로 다시 주고 싶으면 쿠폰을 새로 만드는 것이 맞다. 지급 이력이
섞이면 "이 쿠폰을 언제 받았나"에 답할 수 없다.

코드형 쿠폰에 대한 발급 API 는 거절한다 — 코드만 알면 누구나 쓰는 쿠폰을
"발급했다"고 믿는 통제는 실제로는 없는 통제다.

### 취소는 반환, 환불은 반환 안 함

주문 **취소**(결제 실패 등)면 발급형 쿠폰을 쿠폰함에 되돌린다 — 안 돌리면
"쿠폰을 먹었다"는 문의가 된다. **환불**에는 되돌리지 않는다 — 물건을 받아보고
반품하며 쿠폰까지 돌려받으면, 쿠폰으로 사는 것을 무한히 반복할 수 있다.

### 남긴 것

생일 쿠폰은 회원 프로필에 생일 필드가 없어 이번 범위에서 뺐다 — 필드 추가는
개인정보 수집 항목 변경이라 약관·동의 흐름과 함께 다뤄야 한다.

## ADR-70. 스토어프론트 라우팅과 기획전 — 링크 목록은 실제로 렌더되는 주소만

### 문제는 스모크가 아니라 사용자가 발견할 뻔했다

스타터로 설치한 사이트의 메뉴에 `/board/notice` 가 걸려 있었는데, 그 주소를
렌더하는 페이지가 없었다 — **설치 직후의 사이트가 메뉴를 누르면 404 였다.**
스모크 테스트가 이것을 놓친 이유가 더 나쁘다: 게시판 링크만 "그 경로는
게시판이니까"라며 검증을 **우회**하고 있었다. 링크 검증은 사용자가 누르는
것과 같은 방식이어야 한다 — 이제 `verify_menu_links` 가 메뉴의 모든 링크를
실제 렌더 API 로 열어본다. 예외 없음.

### 라우터 블록 — 페이지 하나가 하위 경로 전부를 받는다

고친 방법은 페이지를 게시판마다 만드는 것이 아니다. 페이지는 **가장 긴 slug
접두사**로 매칭되고 나머지 경로(pathTail)가 블록에 전달되므로:

- `board` 페이지(board 블록, props 없음) 하나가 `/board/*` 전부를 라우팅한다.
  pathTail 의 첫 조각이 게시판 slug, 나머지가 글 경로다. `/board` 루트는
  게시판 목록을 그린다. **게시판을 새로 만들어도 페이지를 만들 필요가 없다.**
- `shop` 페이지(storefront 블록) 하나가 `/shop/*` 를 받는다 — 목록·장바구니·
  기획전·상품 상세를 pathTail 로 분기한다. 기존 개별 블록(상품 목록·상세·
  장바구니)은 그대로 있고, storefront 는 그들에게 **위임**한다 — 세밀하게
  조립하고 싶은 운영자는 개별 블록을, 그냥 되기를 바라는 운영자는 라우터
  블록을 쓴다.

props 로 slug 를 고정한 블록(공지사항만 보여주는 페이지 등)은 지금까지처럼
동작한다 — 라우터는 props 가 비어 있을 때만 pathTail 을 해석한다.

### 기획전 — 분류는 소속, 기획전은 진열

분류(category)는 상품의 소속이고 하나뿐이다. 기획전(collection)은 **진열**이다
— "여름 특가"에 우산과 선풍기가 함께 있고, 같은 상품이 여러 기획전에 들어가고,
기간이 있고, 끝나면 내려간다. 이 구분을 뭉개고 분류로 기획전을 흉내 내면
상품의 소속이 행사 때마다 흔들린다.

- **끝난 기획전은 404 가 아니다.** 목록에서는 빠지되 직접 열면 "종료된
  기획전입니다"를 보여준다 — 공유된 링크를 타고 온 손님에게 404 는 사이트가
  고장난 것으로 보인다. 숨김은 404 다(운영자가 감춘 것이므로).
- 상품 지정은 관련 상품과 같은 규칙 — slug 한 줄에 하나, 없는 slug 는 400 으로
  알려준다. 조용히 버리면 오타를 영원히 못 찾는다.
- **생성·수정은 원자적이다.** 처음 구현은 기획전 행을 INSERT 한 뒤 상품을
  해석했다 — 상품 오타로 400 이 나면 반쪽짜리 기획전이 남고, 오타를 고쳐
  다시 저장하면 409("이미 사용 중인 주소")가 났다. 스모크가 잡았다. 해석을
  쓰기 **전에** 하고, 행과 항목을 한 트랜잭션으로 쓴다.

### 링크 목록은 실제로 렌더되는 주소만

연결 대상 선택기(ADR-65)에 `/shop/orders` 가 올라 있었는데, 그 주소를 그리는
화면이 없었다 — 선택기가 404 를 **권하고** 있었다. 제거했다. 규칙: 링크
목록에는 실제로 렌더되는 주소만 올린다. 기획전은 고정 화면(`/shop/event`)과
진행 중인 기획전 각각을 올린다 — 운영자가 "여름 특가"를 메뉴에 몇 번의
클릭으로 건다.

### 스모크가 DB 를 직접 고치면 캐시가 거짓말을 한다

기획전 스모크의 기간 변경을 처음에는 psql UPDATE 로 했다 — 페이지 캐시가
무효화되지 않아 화면 검증이 실패했다. 이것은 테스트의 결함이 아니라 **경고**다:
운영자는 관리 API 로 바꾸고, 관리 API 는 캐시를 지운다. 스모크도 같은 길을
가야 캐시 무효화까지 함께 검증된다. DB 직접 수정으로 우회하면 "고쳐도
통과"하는 스모크가 된다.

## ADR-71. 정기결제 — 카드는 PG 에, 해지는 한 클릭에

### 카드번호는 이 시스템을 지나가지 않는다

카드 등록은 PG 의 화면에서 일어나고, 우리는 그 결과로 받은 1회용 authKey 를
PG 에 제출해 **빌링키(토큰)** 를 받는다. 저장하는 것은 빌링키와 마스킹된
표시 라벨("테스트카드 ****1234")뿐이다 — 유출되어도 카드번호가 아니고, 우리
PG 계정 밖에서는 쓸 수 없다. 게이트웨이 계약에 `issueBillingKey` /
`chargeBillingKey` 를 선택 구현으로 추가했다 — 둘 다 구현한 게이트웨이만
정기결제를 지원한다.

### 청구액은 가입 시점에 고정된다

구독은 첫 주문의 총액(agreed_total)을 기억한다. 이후 회차의 주문 총액이
이것과 다르면 — 가격 인상, 배송비 변경, 무엇이든 — **결제하지 않고 멈춘 뒤
알린다.** 동의 없이 인상된 금액을 청구하는 것은 법 이전에 신뢰의 문제다.
같은 이유로 구독 청구에는 등급·쿠폰·포인트 할인을 적용하지 않는다 — 등급은
바뀌고 쿠폰은 소진되어, 2회차부터 금액이 조용히 달라진다.

### 회차마다 일반 주문이 생긴다

구독만의 특별한 돈 흐름을 만들지 않는다. 회차 청구 = 주문 생성 + 빌링키
결제이므로 매출 리포트·환불 안분·세금 증빙·재고가 기존 경로 그대로 정합하다.

### 해지는 항상, 즉시, 조건 없이

가입은 한 클릭인데 해지는 전화를 걸어야 하는 서비스를 만들지 않는다.
해지 API 에 확인 절차를 쌓지 않고, 두 번 눌러도 오류가 아니며, 관리자
화면의 구독은 수정 불가에 삭제(=해지)만 있다 — 금액·주기를 관리자가 고치는
순간 회원과의 합의가 깨지기 때문이다. 카드 삭제는 그 카드의 구독을 즉시
멈춘다 — 회원이 결제수단을 지웠는데 다음 회차가 청구되면 그것이 사고다.

### 실패한 회차가 멱등키를 태우면 구독이 영원히 죽는다

회차 주문의 멱등키는 `sub-<구독>-c<회차>` 다. 처음 구현은 실패한 회차 주문을
취소만 했다 — 그 취소된 주문이 회차 키를 차지한 채 남아, 재시도가 멱등성
때문에 **취소된 주문을 되돌려받았다.** 카드를 고쳐도, 가격을 되돌려도 그
구독은 영원히 재개되지 않는다. 스모크가 잡았다. 실패한 회차 주문은 취소하며
**멱등키를 회수한다**(NULL). PG 멱등키는 시도 단위(`-a<실패횟수>`)다 — PG 는
같은 키에 저장된 응답을 재생하므로, 회차 단위로 하면 첫 실패 응답이 재생되어
역시 영원히 실패한다. 토스 confirm 멱등키(ADR 결제 편)와 같은 병이 두 자리에서
재발한 것이다: **실패가 키를 오염시키게 두지 마라.**

### 밀린 회차를 몰아 청구하지 않는다

서버가 한 달 죽어 있었다고 네 번 치지 않는다. 한 번 청구하고 다음 예정일을
미래로 옮긴다 — 못 보낸 물건 값을 몰아 받는 것은 청구가 아니라 사고다.
실패는 하루 뒤 재시도, 3회 연속이면 멈추고 알린다. 성공은 실패 횟수를
리셋한다. 스윕은 재입고 알림과 같은 자기 재예약 큐 잡이다 — 워커 하나에서만
돌고, 플러그인이 꺼지면 함께 멈춘다.

## ADR-72. 개발 템플릿 — 빈 껍데기가 아니라 동작하는 예제

### create-brick-plugin 은 방명록을 만든다

`npm create brick-plugin my-plugin` 이 만드는 것은 빈 뼈대가 아니라 **동작하는
방명록**이다 — 라우트·블록·관리 화면·마이그레이션·개인정보 파기까지, Brick
플러그인의 계약 전부를 한 번씩 쓴다. 지우면서 배우는 것이 빈 파일을 채우는
것보다 빠르고, 예제가 계약을 다 쓰고 있어야 스모크가 계약 전체를 지킬 수 있다.

`smoke-create-plugin.sh` 은 외부 개발자의 경로를 그대로 밟는다: 모노레포 밖에
생성 → strict 컴파일 → README 절차 그대로 ZIP → 실제 서버에 업로드 설치 →
활성화 → 계약 전부를 사용자 입장에서 누른다. escapeHtml 은 `<b>태그</b>` 를
넣어 실제 렌더에서 검증하고, 파기는 **실제 탈퇴**로 검증한다(탈퇴 내역에
"방명록 1건 익명화"가 나와야 한다). 템플릿이 죽은 예제가 되는 순간 이 수트가
먼저 빨간불이 들어온다.

### 공유 의존성은 로더가 보증한다 — "우연히 되는 것"은 계약이 아니다

이 수트가 첫 실행에서 잡은 구멍: **ZIP 으로 설치된 플러그인은 node_modules 가
없다.** 배포본은 모든 의존성이 루트 node_modules 에 있어 우연히 해석되지만,
pnpm 모노레포에서는 `Cannot find package '@brick/plugin-sdk'` 로 활성화가
죽는다. 지금까지 ZIP 설치 스모크가 의존성 없는 플러그인만 써서 숨어 있었다.

로더가 활성화 때 명시적으로 보증한다: 플러그인 폴더에서 공유 의존성
(@brick/plugin-sdk · @brick/core · drizzle-orm · uuidv7)을 해석해 보고,
실패한 것만 **호스트가 쓰는 사본으로 심볼릭 링크**를 만든다. 같은 사본을
가리키는 것이 목적이기도 하다 — drizzle-orm 이 다른 사본이면 플러그인의
`sql` 객체를 서버가 알아보지 못한다(배포본 node_modules 를 루트에 두는 것과
같은 이유). API 자신은 plugin-sdk 에 의존하지 않으므로(플러그인의 계약이지
API 의 것이 아니다) 동봉 플러그인들의 컨텍스트를 해석 폴백으로 쓴다.

그래서 플러그인 의존성 규칙은 이렇다: **공유 4종은 번들하지 말 것**(로더가
보증한다 — 특히 drizzle 은 번들하면 안 된다), **그 외는 dist 에 번들할 것**
(서버는 절대 npm install 을 하지 않는다).

### Node 24: 모듈 해석기를 탐침으로 쓰지 마라

이 링크 보증의 첫 구현은 "이미 해석되는가"를 `createRequire().resolve()` 로
찔러보고, 실패하면 링크를 만들었다. macOS(Node 22)에서는 통과하고 **CI(Node
24)에서만 죽었다**: Node 24부터 모듈 해석기가 stat·파일 읽기 결과를 캐시하므로,
탐침이 남긴 부정 캐시 때문에 **링크를 만든 뒤에도 그 경로는 계속 "없음"** 이다.
증상은 기괴하다 — 링크는 정상이고 대상의 package.json 도 있는데
`Cannot find package '<...>/index.js'` 가 난다.

규칙: 파일시스템을 바꾸기 전에 모듈 해석기로 존재를 묻지 마라. 존재 확인도
검증도 **일반 fs(lstat/stat)** 로 한다. 해석기는 결과가 바뀌지 않을 경로에만
쓴다. 재현이 안 되는 CI 실패는 Node 버전부터 맞춰라 — `pnpm env use 24` 로
5분이면 로컬 재현이 된다.

### SDK 의 npm 공개는 남아 있다

모노레포 밖의 개발자가 `npm install` 로 타입을 받으려면 @brick/plugin-sdk 가
npm 에 있어야 한다. 공개(패키지 이름·버전 정책)는 첫 릴리스와 같은 사용자
결정 사항이라 임의로 하지 않았다 — 스모크는 로컬 링크로 공개 뒤의 설치와
같은 상태를 만들어 검증한다.

## ADR-73. OpenAPI — 코드가 곧 문서다

### 스펙 파일을 손으로 쓰지 않는다

손으로 쓴 API 문서는 라우트가 바뀌는 순간부터 거짓말을 시작한다.
`GET /api/openapi.json` 은 요청 시점에 **실제로 등록된 라우트**에서 생성된다:
코어는 Nest 컨트롤러 메타데이터(DiscoveryService)에서, 플러그인은 로더의
라우트 테이블에서. 그래서 플러그인을 켜면 그 라우트가 문서에 나타나고,
끄면 사라진다 — 문서가 항상 현재를 말한다. 스모크는 이 성질 자체를
검증한다(켜기 전 없음 → 켜면 있음 → 끄면 다시 없음).

### 스키마보다 정확성

요청/응답 본문 스키마는 담지 않는다. 플러그인 핸들러는 불투명하고, 코어에
데코레이터를 도배하는 것은 문서를 위해 코드를 무겁게 만드는 일이다.
경로·메서드·파라미터·인증 요구가 **정확한** 것이, 스키마가 **그럴듯한**
것보다 낫다. `/admin/` 경로에는 세션 인증 요구를 표시한다.

플러그인은 `registerRoute(method, path, handler, { summary })` 의 선택
인자로 사람용 한 줄을 붙일 수 있다 — 없어도 경로는 실린다. 계약을 바꾸지
않고(4번째 인자, 선택) 문서 품질을 올릴 길만 열어 둔다.

### 사람용 페이지도 자체 완결

`GET /api/docs` 는 그룹·필터가 있는 레퍼런스 페이지다. Swagger UI 를 CDN
에서 불러오지 않는다 — CSP 를 뚫어야 하고, 오프라인(내부망 설치)에서
깨진다. 페이지는 뼈대만 캐시되고 데이터는 매번 `/api/openapi.json` 을
다시 불러 그린다.

문서는 공개다. 경로 목록은 오픈소스 저장소에 이미 있는 정보이고, 인증이
필요한 라우트는 문서에 실려 있어도 인증 없이 열리지 않는다 — 숨겨서
지키는 보안은 보안이 아니다.

## ADR-74. 플러그인 레지스트리 — 레지스트리는 목록일 뿐, 신뢰는 서명이 결정한다

### 레지스트리는 정적 JSON 이다

중앙 서버를 만들지 않는다. 레지스트리는 어디에나 올릴 수 있는 정적 JSON
(기본값: 공식 레지스트리 `docs-site/registry.json`)이고, 관리자 설정
(`extensions.registry_url`)으로 바꿀 수 있다 — 회사 내부 레지스트리, 테마
전문 레지스트리가 전부 같은 형식이다. 항목은 이름·버전·**ADR-67 업데이트
매니페스트 주소**·배포자 공개키를 담는다.

### 설치와 업데이트가 같은 길을 쓴다

레지스트리 설치는 새 검증 경로를 만들지 않는다. 항목이 가리키는 것은 ADR-67
업데이트 매니페스트이고, 검증 순서도 같다: 이름 대조 → sha256 → **서명 검증**
→ 기존 설치기(zip-slip 방어 포함). 첫 설치의 키는 레지스트리에서 온다(TOFU —
운영자가 레지스트리를 고른 것이 신뢰의 시작점이다). 설치 순간 키와 업데이트
주소가 설치 기록에 **고정**되고, 이후에는 레지스트리가 항목의 키를 바꿔치기해도
업데이트는 고정된 키로 검증한다. 이미 설치된 확장을 레지스트리 설치로 덮는
것은 거부한다 — 그것은 업데이트이고, 업데이트는 고정 키의 길(apply)로만 간다.

### 스모크가 잡은 잠복 구멍: 활성화가 신뢰를 지우고 있었다

`activate()` 는 재부팅 복원을 위해 파일의 매니페스트로 DB 를 upsert 한다 —
그 upsert 가 설치 때 고정한 publisherKey·updates 를 **파일 값으로 덮고
있었다.** 유효하게 서명된 ZIP 이 자기 매니페스트에 다른 키를 적어 두는 것만으로
다음 업데이트의 검증 키를 갈아치울 수 있었다는 뜻이다. 같은 병이 apply 경로에도
있었다: 인스톨러 upsert 가 updates 를 지우고 repin 은 키만 되살려서, ZIP 에
updates 가 없으면 **이번 업데이트가 마지막 업데이트**가 됐다.

규칙으로 굳힌다: **신뢰 필드(publisherKey·updates)는 DB 의 기존 값이 파일을
이긴다.** 키·주소 교체는 운영자의 직접 업로드로만 된다. 스모크는 레지스트리
키 바꿔치기 → 업데이트 시도까지 실제로 밟아 이 규칙을 못박는다.

## ADR-75. 위험 작업 재인증 · 관리자 IP 제한 — 훔친 세션의 반경을 줄인다

### 재인증(sudo 모드)은 세션 단위다

세션 토큰이 탈취되어도 비밀번호까지는 없는 공격자가 있다. 회원 개인정보
열람(이메일 목록)과 대량 발송처럼 **세션 하나로 큰 피해가 나는** 작업은
비밀번호를 한 번 더 확인한 뒤 10분만 허용한다(`POST /api/me/security/reauth`).

승격은 사용자 단위가 아니라 **세션(토큰 해시) 단위**다 — 사용자 단위면 한
기기의 재인증이 탈취된 다른 세션까지 열어 준다. 스모크는 같은 계정의 두
세션으로 이것을 못박는다. 승격 상태는 메모리에만 둔다: 재시작하면 사라지지만
사라져서 생기는 일은 비밀번호를 한 번 더 묻는 것뿐이고, DB 에 남길수록
유출 걱정만 는다. 거부 응답은 `code: "reauth_required"` 를 담아 화면이
비밀번호 창을 띄운다.

### IP 제한은 자기잠금을 저장 시점에 막는다

고정 IP 사업장을 위한 선택 기능이다. 위험한 것은 기능 자체가 아니라
**운영자가 자기 IP 를 빼고 저장하는 순간**이다 — 그래서 저장 요청의 IP 가
목록에 없으면 400 으로 거부한다("저장하면 스스로 잠깁니다"). 그래도 잠기면
(사무실 IP 변경 등) 서버 소유자는 `BRICK_ADMIN_IP_LIMIT=off` 로 끈다 —
서버에 접속할 수 있는 사람은 어차피 DB 도 만질 수 있으므로 새 권한이 아니고,
재설치 없이 스스로를 구할 길은 있어야 한다.

IPv6 CIDR 은 받지 않는다 — 필요해질 때까지 반쪽 구현을 두지 않는다. 반쪽
구현은 "설정했는데 안 막히는" 보안 기능이 된다. IPv4-mapped IPv6
(::ffff:1.2.3.4)는 IPv4 로 취급한다 — 듀얼스택에서 이것을 안 하면 목록에
IPv4 를 적은 운영자가 잠긴다.

## ADR-76. 생일 쿠폰 — 연도는 받지 않는다

### 최소수집: 월·일이면 충분하다

생일 혜택에 필요한 것은 "몇 월 며칠"뿐이다. 연도까지 받으면 **나이**라는
별개의 개인정보를 함께 수집하는 것이 된다 — 목적에 필요한 최소만 받는다
(개인정보보호법 제16조). 그래서 users 에 birth_month · birth_day 두 정수만
있고, date 타입이 아니다.

가입할 때 받지 않는다. 회원이 혜택을 원할 때 마이페이지에서 스스로 입력하고
(본인 제공), 언제든 지울 수 있고(월·일 null 저장), 탈퇴하면 함께 파기된다 —
스모크가 세 경로를 전부 밟는다.

### 생일 쿠폰 = 발급형 + 자동 지급, 같은 쿠폰은 평생 1회

birthday_auto 를 켜면 발급형이 강제된다 — 코드형이면 "자동 지급"이 의미가
없다(코드를 아는 누구나 쓴다). 스윕이 오늘(사이트 시간대)이 생일인 회원의
쿠폰함에 지급하고, 지급은 쿠폰함 unique 로 **회원당 평생 1회**다. 매년
주려면 해마다 쿠폰을 새로 만든다 — ADR-69 의 재지급 규칙과 같은 이유다:
지급 이력이 섞이면 "언제 받았나"에 답할 수 없고, "2026 생일 쿠폰"이라는
이름 자체가 운영 기록이 된다.

스윕은 멱등하므로 6시간마다 돈다 — 자정에 한 번만 돌리는 정밀함은 서버가
그 시각에 꺼져 있으면 그날 생일자를 통째로 놓친다. 2월 29일 생일은 평년에
2월 28일에 지급한다 — 4년에 한 번만 혜택을 받는 회원을 만들지 않는다.

### 메일은 보내지 않는다

쿠폰함에 담기는 것은 발송이 아니다. 생일 축하 **메일**은 광고성 정보라
수신 동의·(광고) 표기 의무(정보통신망법 제50조)가 함께 온다 — 원하면
단체메일 기능(수신 동의자 대상, 규정 자동 준수)으로 따로 보낸다.
쿠폰 지급과 광고 발송을 한 기능에 묶으면 지급이 규제를 따라 멈춘다.

## ADR-77. 다국어 1단계 — 사이트의 언어이지 손님의 언어가 아니다

### locale 은 사이트 설정이다

`site.locale` 은 운영자가 정하는 **사이트의 언어**다. 손님별 언어 전환
(Accept-Language, 언어 선택 UI)은 다음 문제다 — 한국 커뮤니티는 한국어
사이트고, 영어권 운영자는 영어 사이트를 만든다. 사이트 하나에 언어 하나가
현실의 대부분을 덮는다.

### 카탈로그와 폴백 규칙: 조용한 반쪽 금지

메시지는 평평한 키의 카탈로그(ko 기본 + en)다. 찾는 순서는 요청 언어 →
ko → **키 자체**이고, 폴백이 일어나면 로그에 남는다. 번역이 반쪽이면
반쪽인 것이 보여야 고쳐진다 — 빈 문자열이나 조용한 한국어 섞임이 최악이다.
파라미터(`{path}`)가 없으면 지우지 않고 그대로 둔다 — 디버깅의 단서다.

### 세 갈래가 같은 규칙을 쓴다

- **코어 공개 화면**: 렌더러가 매 렌더마다 설정을 읽으므로 언어 변경이
  즉시 반영된다. 404 문구·`lang` 속성이 여기다.
- **테마**: 템플릿이 `{{ t.footer.company }}` 로 라벨을 받는다. **값(상호·
  대표자명)은 번역하지 않는다** — 번역 대상은 라벨이지 데이터가 아니다.
  운영자 소유의 커스텀 테마는 하드코딩을 유지해도 된다(그들의 선택).
- **플러그인**: `ctx.t(key, params)` 와 동봉 카탈로그(`locales/<locale>.json`).
  t 는 동기여야 해서(블록 렌더 어디서든 부른다) DB 를 직접 못 읽는다 —
  로더가 언어를 TTL 캐시하고, 설정 저장이 훅(`site.settings_changed`)으로
  캐시를 즉시 버린다. "언어를 바꿨는데 10초 동안 그대로"는 운영자에게
  "안 바뀐다"로 보이기 때문이다.

### 진행 (로드맵)

동봉 플러그인(게시판 92키 · 쇼핑몰 97키)과 웹 공개 페이지(로그인·가입·
비밀번호 — 카탈로그는 번들에, 언어만 공개 GET /api/i18n)까지 끝났다.
통화 표기(원)는 이관하지 않았다 — **통화는 언어가 아니라 상점의 통화다.**
영어 사이트도 원화로 팔면 "9,000원"이 맞다. 코어 관리 화면(셸·전체 코어 페이지 + 설정의 언어 선택 UI)도 끝났다 —
관리 카탈로그의 키는 리터럴 유니언 타입이라 **없는 키는 컴파일이 잡고**,
en 카탈로그는 `Record<keyof KO, string>` 이라 키 누락도 타입 오류다.
create-brick-plugin 템플릿은 처음부터 ctx.t 를 시연한다.

### 선언 라벨은 gettext 방식 — 원문이 곧 키다

플러그인의 관리 화면은 코드가 아니라 **선언**(AdminResource 의
title/label/help/placeholder/options)이다. 여기에 `ctx.t()` 를 쓰면 활성화
시점의 언어로 고정되어 언어 변경을 못 따라가고, 키를 도입하면 동봉 8개
플러그인의 선언 전부를 고쳐야 한다. 대신 gettext 의 원리를 빌린다 —
**한국어 원문이 곧 카탈로그 키**다. 플러그인은 `locales/en.json` 에
`"주문": "Orders"` 를 추가하면 되고, 선언 코드는 한 줄도 바뀌지 않는다.
로더가 서빙 시점(`GET admin/nav`·`admin/resources/:plugin/:name`)에
현재 언어로 치환한다. 번역이 없으면 원문이 그대로 나가는 자연 폴백이라
빠짐 로그는 내지 않는다 — 전 라벨이 원문 키여서 로그가 노이즈가 된다.
동봉 8개 플러그인의 관리 라벨 431개 전부 en 카탈로그를 갖췄다.

## ADR-78. 대시보드 카드 — 관리자 첫 화면은 "오늘의 사이트"다

### 문제

관리자 대시보드가 플러그인/테마 개수만 보여줬다. 그누보드를 쓰던 운영자가
매일 아침 확인하는 것은 오늘 방문자·오늘 주문·답변을 기다리는 문의인데,
그 숫자들은 전부 **플러그인 소유의 테이블**에 있어 코어가 알 수 없다.
운영자는 숫자 하나를 보러 화면을 네 번 옮겨 다녀야 했다.

### 결정: registerDashboardCard

플러그인이 `{ title, order?, link?, load }` 를 등록하면 코어가
`GET admin/dashboard` 에서 카드들을 모아 준다.

- **제목은 gettext** (ADR-77 의 관리 라벨과 같은 규칙) — 원문이 번역 키.
  `load` 가 만드는 동적 문구(sub)는 요청 시점에 실행되므로 ctx.t 를 쓴다.
- **카드 실패는 격리된다 — 시간 축까지.** 하나가 죽거나 3초를 넘기면 그
  카드만 오류로 표시한다. 플러그인 하나 때문에 대시보드 전체가 비거나
  멈추면 운영자는 아무것도 볼 수 없고, 값이 0 으로 보이는 것이 최악이라
  실패를 0 으로 숨기지 않는다. 코어 통계도 같은 규칙으로 격리된다
  (잘못된 BRICK_TIMEZONE 하나로 첫 화면이 500 이 되면 안 된다).
  카드 수집(정렬·번역·격리)은 레지스트리를 가진 로더의 일이다 —
  HTTP 계층에 흩어지면 두 번째 소비자가 규칙을 복제하게 된다.
- **"오늘"의 경계는 판매 리포트와 같은 사이트 시간대다** (ADR-51).
  카드와 리포트의 "오늘 주문"이 다르면 운영자는 어느 쪽도 믿지 않는다.
  그 정의(SITE_TZ)는 @brick/core 한 곳에만 있다 — 다섯 곳의 복사본이
  우연히 같기를 비는 대신. 술어는 상수 쪽을 변환하는 반개구간으로 쓴다
  (컬럼 캐스팅은 인덱스를 못 타 대시보드가 풀 스캔이 된다). 방문자
  집계(visit_day)도 같은 경계를 쓴다.
- 코어 통계(회원·발행 페이지)는 코어가 직접 낸다 — 코어 테이블을
  플러그인 계약 뒤로 숨길 이유가 없다. 단 "회원"의 정의는 members
  모듈과 같아야 한다 (탈퇴·휴면 제외) — 업무 규칙을 모듈마다 다른
  술어로 복제하면 화면끼리 숫자가 어긋난다.

동봉 플러그인이 넷을 등록한다: 오늘 방문자(brick-site) · 오늘 주문 +
입금대기(brick-shop) · 오늘 글 + 댓글(brick-board) · 답변 대기
문의(brick-helpdesk). create-brick-plugin 템플릿도 시연한다.
