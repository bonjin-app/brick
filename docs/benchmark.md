# 남들은 무엇을 갖추고 있나

Brick 은 **설치형 한국어 CMS** 를 표방한다. 그러면 이미 다른 것을 쓰고 있는 사람이
옮겨 올 때 기대하는 목록이 있다 — 그 목록은 우리가 정하는 것이 아니라 그누보드·
영카트·카페24·제로보드 계열·워드프레스가 20년 동안 정해 놓은 것이다. 이 문서는 그
목록을 적고, 우리에게 무엇이 없는지, 없는 것 중 무엇을 먼저 할지 정리한다.

조사 시점: 2026-09.

## 무엇으로 자리를 잡았나

**그누보드5 / 영카트5** — 한국 설치형의 사실상 표준. PHP 5 시절 구조 그대로지만
관리자 메뉴가 운영자의 일상을 빠짐없이 덮는다: 게시판그룹·권한·기능·디자인/양식·
포인트·여분필드가 게시판마다 따로 있고, 팝업레이어·인기검색어·접속자집계·SMS·
1:1문의·FAQ 가 코어에 들어 있다. 영카트는 여기에 상품·주문·쿠폰·추가배송비·
이벤트·배너를 얹는다. ([그누보드5 매뉴얼](https://sir.kr/manuals/g5/1) ·
[영카트5 매뉴얼](https://sir.kr/manuals/yc5/124))

**그누보드7** — 2026년 4월 오픈베타, 7월 정식. Laravel 12 + React 19 로 다시
설계했고 MIT 다. 우리와 겨냥하는 자리가 가장 가깝다: **JSON 레이아웃 엔진**(UI 를
코드가 아니라 JSON 선언으로 정의하고 모듈·플러그인이 프런트엔드 빌드 없이 화면을
주입한다), Role+Permission+Scope 3단계 권한, 다국어·**다중통화**, 활동 로그,
**알림 시스템(Definition × Template × Recipients, 메일·DB·브로드캐스트 다중 채널)**,
언어팩 ZIP/URL 설치, 본인인증 정책 중앙 관리. 기본 모듈은 게시판·쇼핑몰·페이지,
기본 플러그인에 이니시스·나이스·KCP·토스와 다음 우편번호가 들어 있다.
([저장소](https://github.com/gnuboard/g7) · [소개](https://sir.kr/g7))

**카페24** — 설치형이 아니라 임대형이지만, 한국 쇼핑몰 운영자의 기대치를 만든
쪽이다. 스마트디자인(HTML 템플릿 + 모듈 태그로 화면을 직접 고친다), 앱스토어,
관리자 대시보드가 오늘·어제의 주문·매출·품절을 먼저 보여주는 것, 모바일 관리자에서
무통장 입금확인까지 되는 것. ([스마트디자인 서포트](https://sdsupport.cafe24.com/manual/manual.html))

**제로보드 → XE → 라이믹스** — 확장을 **모듈·애드온·위젯·레이아웃·스킨** 다섯
종류로 나눈 계보. 모듈은 자기 URL 과 DB 를 갖는 독립 기능, 애드온은 요청 수명주기
중간에 끼어드는 코드 조각(게시판·페이지 단위로 켜고 끈다), 위젯은 화면 조각,
레이아웃은 머리·꼬리와 메뉴. ([Rhymix 매뉴얼](https://rhymix.org/manual/plugin/intro))

**워드프레스** — 전 세계 표준. 우리가 빌려야 할 것은 생태계가 아니라 **운영자
보호 장치**다: 리비전(글의 이전 버전이 남고 되돌릴 수 있다), 자동 저장, 예약 발행,
미디어 라이브러리, 역할(role), 자동 업데이트.

## 무엇을 먼저 할까

우선순위는 "없으면 사이트가 **조용히** 제 역할을 못 하는가"로 정한다. 우리가 계속
고쳐 온 것과 같은 기준이다.

1. ~~**알림이 메일 한 통로뿐이다.**~~ **(2026-09 완료)** 댓글·문의 답변·주문 상태·재입고를 알리는 길이
   전부 `mail.send` 하나다. 그런데 **SMTP 미설정은 기본값**이고, 대시보드가 스스로
   "메일이 발송되지 않습니다"라고 경고하는 그 상태가 설치 직후의 상태다. 즉 기본
   설치에서 **모든 알림이 조용히 사라진다** — 손님은 답이 없다고 느끼고 운영자는
   보냈다고 믿는다. 그누보드7 이 알림을 다중 채널(메일·DB·브로드캐스트)로 설계한
   이유가 이것이다. → 코어에 알림함을 두고, 메일로만 나가던 알림(댓글·문의
   답변·주문·재입고·정기결제)을 `ctx.notify` 한 통로로 모았다. 메일이 되면 둘 다
   가고, 안 되면 최소한 로그인한 사람은 사이트에서 본다.
2. ~~**예약 발행.**~~ **(2026-09 완료 — 페이지)** 공지·이벤트 공개 시각을 맞출 수
   없어 사람이 그 시각에 깨어 있어야 했다. `published_at` 은 이미 있었는데 "발행한
   순간" 으로만 쓰였다. 상태에 `scheduled` 를 더하고 30초마다 때가 된 것을 연다.
   게시판 글·상품 진열의 예약은 아직 없다(플러그인 계약이 함께 움직여야 한다).
3. ~~**이전 버전(리비전).**~~ **(2026-09 완료 — 페이지)** 덮어쓰면 되돌릴 길이
   없었다. 저장할 때마다 한 판을 남기고(한 페이지에 서른 판), 되돌리기도 하나의
   저장이라 되돌리기를 되돌릴 수 있다. 게시판 글은 아직 없다.
4. ~~**여분 필드.**~~ **(2026-09 완료 — 게시판)** 그누보드는 게시판마다 열 개의
   추가 입력칸을 주고(이름 `bo_N_subj`, 값 `wr_N`) 한국 사이트가 거기에 연락처·
   지역·학번을 담아 왔는데, **우리 이전 도구는 그것을 통째로 버리고 있었다** —
   글은 옮겨지고 그 옆의 값만 소리 없이 사라졌다. 관련 링크(`wr_link1/2`)도 같았다.
5. ~~**문자.**~~ **(2026-09 완료 — 주문 안내)** 한국 커머스에서 주문 안내의 기본
   통로다. 1번에서 만든 알림 통로 위에 채널로 얹었다: 코어는 발송기 하나가
   등록되어 있는지만 알고, 공급자는 플러그인이다(결제 게이트웨이와 같은 구조).
   **건당 요금이 나가므로 메일과 반대로 옵트인**이다 — 켜지 않으면 한 통도 나가지
   않는다. 알림톡(카카오)은 템플릿 사전심사가 필요해 따로 둔다.
6. **다중 통화.** 있으면 좋지만, 해외 판매를 하지 않는 사이트에는 없다고 망가지는
   것이 없다. 원화 하나를 제대로 하는 편이 낫다(원화는 소수점을 쓰지 않는다).

### Brick 이 앞서는 것 (확인한 것만)

- **서버가 HTML 을 그린다.** 그누보드7 은 React 화면이라 검색엔진용으로 "봇 탐지 →
  정적 HTML → 캐시" 를 따로 둔다. 우리는 처음부터 서버 렌더라 그 층이 필요 없다.
- **돈이 새지 않는지를 실제 HTTP 로 시험한다**: 결제 확인·부분환불 금액·이중 승인·결제
  중 취소된 주문 환불·정기결제 겹침(카드는 긁혔는데 주문은 취소되던 사고)·미결제 주문의
  재고 해제 — 스텁 PG 로 전부 돈다.
- **운영 안전장치**: 백업 검증(빈 덤프를 성공이라 하지 않는다)·점검 모드·중단된 작업 회수
  (재시작해도 메일 캠페인이 멈추지 않는다)·서버 여러 대에서 하나인 요청 제한·탈퇴 시
  개인정보 파기 전수 검사.
- **그누보드5·영카트5 데이터 이전** — 게시판·회원·주문·여분필드·추천 기록까지, 안 옮기는
  것은 이유와 함께 선언한다.
- **반품·교환·세금계산서·현금영수증·정기결제** 가 쇼핑몰에 들어 있다.

"이건 무엇으로 만들지"부터 고민해야 한다.
