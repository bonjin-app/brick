# 로드맵

목표는 하나입니다. **기존 PHP 게시판·쇼핑몰로 하던 일을 Brick에서 다 할 수 있게 하는 것.**

"더 좋은 기술"은 목표가 아닙니다. 기존 게시판으로 사이트를 운영하던 사람이 Brick으로
옮겨왔을 때 *없어서 못 하는 일*이 없어야 합니다. 그래서 이 문서는 자랑이 아니라
**격차 목록**입니다.

## M15 — 회원 생애주기 (법적 필수) ✅ 완료

**왜 최우선인가.** 회원 탈퇴가 없는 사이트는 한국에서 **운영할 수 없습니다.**
정보통신망법은 이용자가 언제든 동의를 철회할 수 있어야 한다고 정하고,
개인정보보호법 제21조는 목적 달성 후 지체 없는 파기를 요구합니다.
가입 시 약관·개인정보 수집 동의도 마찬가지입니다. 이건 기능이 아니라 **전제**입니다.

- **약관 동의** — 이용약관 · 개인정보 수집·이용 동의(필수), 마케팅 수신(선택).
  관리자가 본문을 편집하고, 개정 시 재동의를 받는다. 동의 이력을 남긴다
  (분쟁 시 "동의받았다"를 증명해야 하는 쪽은 사업자다).
- **만 14세 미만 가입 제한** — 법정대리인 동의 절차 없이는 가입을 막는다.
- **이메일 인증** — 가입 후 인증 메일, 미인증 상태의 권한 제한을 관리자가 선택.
- **회원 탈퇴** — 즉시 탈퇴. 개인정보는 파기하고, 전자상거래법상 보존 의무가 있는
  주문·결제 기록은 **작성자를 끊고 남긴다**(5년). 게시글은 남길지 지울지 선택.
- **내 정보 수정** — 비밀번호 변경(현재 비밀번호 확인), 닉네임, 연락처, 수신 동의.
- **휴면 계정** — 장기 미접속 계정 처리. 파기 전 사전 통지.

## M16 — 사이트 운영 기본기 ✅ 완료

게시판 사이트가 예외 없이 다 쓰는 것들입니다.

- ~~**1:1 문의**~~ ✅ — 비공개 문의 + 관리자 답변 + 대화 이어가기, 비회원 문의(조회
  비밀번호), 담당자 지정, 답변 메일 알림. 남의 문의는 **404** 로 응답한다 —
  403 은 "그 문의가 존재한다"를 알려주고 문의번호는 순차적이라 열거할 수 있다.
- ~~**FAQ**~~ ✅ — 분류 + 검색 + 조회수 + "도움이 되었나". `<details>` 로 만들어
  JS 없이 접히고 검색엔진은 답변을 다 읽는다.
- ~~**설문조사**~~ ✅ 복수 선택 · 기간 · 기타 의견. IP를 **해시로만** 저장해 중복
  투표를 막고(완벽하지 않음 — 공유기 아래는 한 표로 묶인다), 결과 공개 시점을
  고를 수 있다. 숨길 때는 득표 수를 응답에 넣지 않는다 (ADR-48).
- ~~**최신글 모아보기**~~ ✅ — 여러 게시판을 나란히. 게시판 수만큼 쿼리하지 않고
  윈도우 함수로 한 번에 가져온다(메인은 가장 많이 열리는 화면이다).
- ~~**회원 단체메일**~~ ✅ — 조건으로 회원을 골라 발송. 종류(공지/광고)를 고르면
  **수신자 조건·`(광고)` 표기·수신거부 링크가 자동으로 결정된다** — "광고를 동의
  없이 보내기"를 표현할 방법을 두지 않았다(ADR-50). 발송 직전에 동의를 다시
  확인해 그 사이 철회한 사람을 건너뛴다. 수신거부는 **로그인 없이** 링크 한 번.
  검증은 SMTP 스텁을 띄워 **받은 메일을 직접 읽는다** — 대상 쿼리만 보면
  제목의 `(광고)`가 빠져도 통과한다.
- ~~**robots.txt · sitemap.xml**~~ ✅ — 플러그인이 자기 URL을 제공하는 레지스트리
  방식(ADR-40). 조각으로 나눠 십만 건 규모에서도 메모리가 터지지 않는다.
  비밀글·비공개 게시판·임시 상품은 제외된다.

## M17 — 쇼핑몰 실무 ✅ 완료

~~지금 쇼핑몰은 "팔 수는 있지만 사후 처리를 못 하는" 상태입니다.~~
사후 처리(취소·반품·교환)가 들어갔습니다. 남은 것은 편의 기능과 표시 의무입니다.

- ~~**주문 취소 · 반품 · 교환**~~ ✅ 상품 단위 부분 처리, 할인 안분 환불,
  청약철회 7일(전자상거래법 제17조), 사유별 반송비 부담(불량은 사업자 — 고객에게
  청구하면 위법), 수거·입고 단계. 물건을 받기 전에는 환불되지 않는다 (ADR-44).
- ~~**위시리스트 · 최근 본 상품**~~ ✅ 비회원도 사용하고 로그인 시 이어받는다
  (ADR-46). 담아둔 뒤 품절되면 표시한다.
- ~~**지역별 배송비**~~ ✅ 우편번호 구간으로 판단한다 (ADR-47) — 주소 문자열로는
  "제주도청"과 "제주식당"을 구분할 수 없다. 무료배송이어도 지역비는 붙는다.
- ~~**사업자정보 표기**~~ ✅ 코어 설정 + 테마 자동 렌더. **사업자등록번호 체크섬을
  실제로 검증**한다 (ADR-45) — 잘못된 번호를 표시하는 것은 표시하지 않는 것과 같다.
- ~~**관련 상품 · 함께 구매**~~ ✅ — 수동 지정을 먼저 쓰고 남는 자리를 함께 구매로
  채운다 (ADR-53). 새 쇼핑몰에는 주문 이력이 없어 자동만으로는 몇 달간 아무것도
  안 보이고, 상품이 천 개면 전부 지정할 수 없다. **반품된 상품·미결제 주문·
  미공개 상품을 추천에서 뺀다** — 반품된 것을 "함께 구매하셨습니다"로 미는 것은
  반품 사유를 반복시키고, draft 노출은 정보 유출이다.
- ~~**판매 리포트**~~ ✅ — 기간별·상품별·분류별 + 직전 기간 대비 요약, 엑셀 CSV.
  **정의를 먼저 못박았다**(ADR-51): 결제일 기준 · 사이트 시간대 · 순매출은 받은
  돈에서 완료된 반품을 뺀 값. 기존 통계에 있던 두 버그를 고쳤다 — 부분 환불을
  빼지 않아 매출이 부풀었고, 주문일·UTC 기준이라 오전 9시 이전 결제가 전날로
  밀렸다.
- ~~**분류 계층 · 상품 분류 지정**~~ ✅ — 스키마에는 있었지만 **관리 화면에서 만들
  수 없었다**(ADR-52). 선택지가 테이블 행인 경우를 위해 관리 리소스에
  `optionsFrom` 을 더했다.

## M18 — 기존 사이트에서 옮겨오기 ✅ 완료

**채택의 실질적 관문.** 아무리 좋아도 10년 쌓인 게시글을 버릴 수는 없습니다.

- ~~MySQL 접속 정보를 받아~~ → **덤프 파일**로 읽는다 (ADR-42). 공유 호스팅은
  MySQL 외부 접속을 막으므로 원격 접속을 전제하면 "안 되는 사람"이 대부분이 된다.
- ~~비밀번호 보존~~ ✅ bcrypt(`$2y$`) · 구형 MD5 · sha256 을 그대로 저장하고
  첫 로그인 성공 시 argon2 로 승급한다 (ADR-43). 회원은 아무것도 하지 않는다.
- ~~레벨 매핑~~ ✅ 경계를 조정할 수 있고 리허설이 결과를 먼저 보여준다.
- ~~리허설 모드~~ ✅ 아무것도 쓰지 않고 보고한다. 옮기지 않는 것도 목록으로.
- ~~상품·주문 이전~~ ✅ 분류 계층 복원(ca_id 앞자리가 부모), 조합형 옵션을
  한 줄로 펼침, 주문 상태 매핑(알 수 없는 값은 입금대기 — 임의로 완료로 보면
  매출이 부풀려진다), 금액 불일치는 할인으로 흡수, **과거 주문이 재고를 줄이지 않음**.
- ~~게시글·상품 본문의 첨부 이미지 주소 변환~~ ✅ — /data/file·editor·item 을
  /uploads/… 로 자동 변환한다(기본 켬). 옛 사이트 절대주소도 oldBaseUrl 로
  잡고, 남의 CDN 이미지는 건드리지 않는다. 리버스 프록시파는 끌 수 있다.

## M19 — 세금 증빙 ✅ 완료

**미루면 쇼핑몰을 운영할 수 없습니다.** 여기까지가 "돈을 받을 수 있다"와
"돈을 받아도 된다"의 차이입니다.

부가가치세법 제32조의2·제46조: 최종소비자가 요청하면 **현금영수증을 발급해야
하고**, 미발급은 미발급액의 20% 가산세입니다. 사업자가 구매하면 세금계산서를
요구합니다. 카드 결제는 PG 가 처리하지만 **무통장 입금은 우리가 해야 합니다** —
기존 PHP 쇼핑몰의 상당수가 무통장 위주입니다.

- ~~**현금영수증**~~ ✅ — 게이트웨이로 추상화하고 **기본은 수동 발급**이다
  (ADR-54). PG 계약이 없는 사이트에서 "발급됨"으로 표시되고 실제로는 아무 일도
  없는 것이 최악이므로, `발급대기` 로 남겨 드러내고 **승인번호 없이 완료로
  바꿀 수 없게** 했다. **카드 주문은 거부한다** — 카드사가 이미 국세청에
  통보하므로 이중 신고가 된다.
- ~~**면세 상품**~~ ✅ — 도서·농수산물은 부가세가 없다. 없으면 서점이 잘못된
  증빙을 발급한다. 기존 쇼핑몰의 면세 설정을 이전하고, **주문 항목에 스냅샷**을
  남긴다 — 상품 설정이 바뀌어도 이미 신고한 금액이 흔들리면 안 된다.
- ~~**세금계산서**~~ ✅ — 요청 접수·발급·거부. 사업자등록번호 체크섬을 검증한다
  (함수를 코어로 옮겨 사업자정보 표시와 같은 규칙을 쓴다). 국세청 자동 연동은
  인증서가 필요해 아직 하지 않고, **요청을 잃어버리지 않는 것**부터 했다.
- ~~**부가세 신고 자료**~~ ✅ — 과세기간을 코드로 고른다("1기 확정이 언제부터"를
  찾아보게 하면 틀린 기간으로 신고한다). 판매 리포트와 **같은 정의**를 쓰고,
  증빙 없는 현금 매출을 따로 내보낸다 — 그것이 가산세의 원인이다.
- ~~**반품 시 증빙 취소**~~ ✅ — 반품 완료에 연결. 취소 실패는 사유를 남기지만
  **반품 처리를 막지 않는다** — 물건은 이미 돌려받았다.

## M20 — 결제 실무 ✅ 완료

지금은 "한 번 사고 한 번 결제"만 됩니다. 실제 쇼핑몰이 쓰는 형태가 빠져 있습니다.

- ~~**개인결제(주문서 없는 청구)**~~ ✅ — 결제하면 **주문을 만든다**(ADR-59).
  주문 없는 결제는 판매 리포트·부가세 자료에서 빠져 세금 신고에 구멍이 난다.
  링크 토큰은 32바이트 난수다 — 청구번호는 순차적이라 남의 청구서를 열 수 있다.
  결제는 일반 주문과 **같은 경로**를 쓴다(금액 위조 방어를 두 번 만들지 않는다).
- ~~**부분 취소를 PG 에 실제로 전달**~~ ✅ — 코드는 이미 맞았지만 **검증이
  없었다**. 무통장 게이트웨이가 인자를 무시하므로 어떤 금액을 보내도 통과했다.
  스텁 PG(ADR-58)를 세워 실제로 나가는 금액을 읽는다.
- ~~**에스크로 표시**~~ ✅ — 전자상거래법 제24조. 사업자정보에 자유 입력으로
  두고 테마가 자동 렌더한다 — 가입 기관과 형태가 사업자마다 달라 목록을
  고정하면 표시를 못 하는 사업자가 생긴다.
- ~~**정기결제**~~ ✅ — 카드는 PG 에, 우리는 빌링키(토큰)만 (ADR-71).
  청구액은 가입 시점에 고정 — 달라지면 결제하지 않고 멈춘 뒤 알린다.
  **해지는 항상, 즉시, 조건 없이.** 회차마다 일반 주문이 생겨 리포트·환불·
  세금 증빙이 그대로 정합하다. 실패는 하루 뒤 재시도, 3연속이면 중지+알림.
  실패한 회차 주문이 멱등키를 태워 구독이 영원히 죽는 버그를 스모크가 잡았다.

## M21 — 관리자 계정 보호 ✅ 완료

**관리자 계정이 뚫리면 사이트 전체를 잃습니다.** 회원 개인정보, 주문 내역,
결제 정보 접근 권한이 한 계정에 몰려 있습니다.

- ~~**2FA (TOTP)**~~ ✅ — 외부 패키지 없이 구현하고 **RFC 6238 표준 벡터를
  스모크에 넣었다**(어긋나면 인증 앱의 코드를 거절해 아무도 못 들어온다).
  설계의 절반은 **잠기지 않게** 하는 데 썼다(ADR-55): 코드 검증 전에는 켜지지
  않고, 복구 코드 10개를 주고, 강제 설정에서도 등록 경로는 열려 있다.
  비밀번호만으로는 세션이 나가지 않는다 — 5분 사는 도전 토큰만 준다.
- ~~**세션 관리**~~ ✅ — 접속 중인 기기 목록·원격 로그아웃 (ADR-56).
  IP 는 **해시로만** 저장하고 User-Agent 는 사람이 읽는 이름으로 바꿔 준다.
  "다른 기기 모두 끊기"는 지금 세션을 남긴다 — 자기까지 끊으면 다시 로그인하는
  사이에 공격자가 먼저 들어올 수 있다.
- ~~**감사 로그 필터 보강**~~ ✅ — 행위자(부분 일치)와 기간 (ADR-57).
  와일드카드 주입을 막고, 기간은 사이트 시간대로 자른다.
- ~~**관리자 IP 제한**~~ ✅ — 선택 (ADR-75). 자기 IP 를 뺀 목록은 저장을
  거부한다("저장하면 스스로 잠깁니다"). 잠기면 BRICK_ADMIN_IP_LIMIT=off.
- ~~**위험한 작업 재인증**~~ ✅ — 회원 개인정보 열람·대량 발송 전에
  비밀번호를 다시 묻는다(10분 승격, **세션 단위** — ADR-75).

## M22 — 유입과 재방문 ✅

여기부터는 법적 의무가 아니라 **매출을 만드는 것**입니다.

- ~~**통합검색**~~ ✅ — 기존 검색은 **페이지만** 찾았고, `total` 이 그 페이지의
  행 수여서 **페이지네이션이 동작하지 않았다**(500건이 맞아도 20을 돌려줬다).
  공급자 레지스트리로 게시글·상품을 모으고(ADR-60), 권한을 공급자가 거른다 —
  검색은 권한 검사를 우회하는 가장 흔한 경로다.
- ~~**인기 검색어 · 검색 로그**~~ ✅ — 결과 0건 목록이 핵심이다(ADR-61).
  같은 사람의 반복을 한 번으로 세고, 인기 검색어에 **빈손 비율**을 붙인다 —
  인기 있는데 결과가 없는 것이 가장 먼저 손볼 것이다. 치환 규칙으로 "아이폰15
  ↔ iPhone 15" 를 연결하고, 0건 목록에서 규칙 폼으로 바로 이어진다.
- ~~**사이트 스타터**~~ ✅ — 설치할 때 유형(커뮤니티/쇼핑몰/회사)을 고르면
  홈·페이지·게시판·메뉴가 통째로 만들어진다(ADR-66). **설치가 끝나면 이미
  돌아가는 사이트**가 있다 — 빈 화면 앞에서 멈추는 것이 가장 큰 이탈이었다.
  만들어지는 것은 전부 일반 페이지·메뉴라 특별 취급이 없다.
- ~~**연결 대상 선택기**~~ ✅ — 메뉴가 "주소 직접 입력"이라 slug 를 외워
  타이핑해야 했고, 오타가 나도 저장되고 눌러야 404 를 봤다(ADR-65).
  `registerLinkTarget` 으로 페이지·게시판·쇼핑몰 화면을 모아 **몇 번의 클릭으로
  연결**되게 했다. home → `/` 변환, 임시 저장·비공개 표시 포함.
- ~~**이벤트 · 기획전**~~ ✅ — 분류는 소속, 기획전은 **진열**이다(여럿 가능,
  기간 있음, 끝나면 내려감) (ADR-70). 끝난 기획전은 404 가 아니라 "종료"
  안내 — 공유 링크로 온 손님에게 404 는 고장으로 보인다. 이 작업이 스타터
  메뉴의 `/board/notice` 404 를 드러냈다: 페이지 하나가 하위 경로 전부를
  라우팅하는 **라우터 블록**(board·storefront)으로 고치고, 스모크가 모든
  메뉴 링크를 실제 렌더로 검증하게 했다.
- ~~**쿠폰 고도화**~~ ✅ — 1인당 한도(취소 제외 주문 이력으로 센다 — 카운터는
  어긋난다), 첫 구매 전용(결제 이력 기준), 등급 전용, **발급형 쿠폰함**(코드가
  퍼져도 지급받은 회원만 · 취소는 반환, 환불은 미반환) (ADR-69).
  ~~생일 쿠폰~~ ✅ — 생일은 **월·일만** 받는다(연도는 나이라는 별개 정보 —
  최소수집, ADR-76). 회원이 스스로 입력·삭제하고 탈퇴 시 파기. 같은 쿠폰은
  평생 1회 — 매년 주려면 해마다 새로 만든다. 평년의 2/29 생일은 2/28 지급.
- ~~**회원 등급**~~ ✅ — 최근 3개월 **순매출**(반품 차감 — 사서 반품하기 우회
  차단)로 자동 배정, 등급별 상시 할인 (ADR-68). 할인은 discount 에 합산되어
  환불 안분·리포트가 그대로 정합하다. "₩57,000 더 구매하면 골드"까지.
- ~~**재입고 알림**~~ ✅ — 품절 상품을 찾아온 손님에게 할 것을 준다(ADR-63).
  **옵션 단위**로 받는다 — "M 사이즈만 품절"이 대부분이고, 그때 상품은 여전히
  판매중이라 품절 화면이 안 뜨므로 살 수 있는 상품에도 폼을 보여준다.
  재입고 감지는 **스윕**이다: 재고가 오르는 지점(반품·취소·관리자 수정·이전
  도구)마다 붙이면 반드시 하나를 빠뜨리고, 빠뜨린 경로의 대기자는 영원히
  못 받는데 아무도 눈치채지 못한다.
  스팸 도구가 되지 않게(1회 소진·로그인 없는 해지·주소 가림) 그리고 **광고가
  되지 않게**(다른 상품을 넣을 자리를 두지 않았다) 만들었다.

## M24 — 기본 스킨 그대로도 사이트로 보이게 ✅ 완료 (2026-09-01)

설치형 CMS 의 기본 스킨은 대개 "일단 돌아가는" 수준이라, 운영자가 첫날부터
CSS 를 고쳐야 합니다. 그 시간이 사이트를 만드는 시간을 잡아먹습니다.

- ~~**라이트·다크 두 벌**~~ ✅ (ADR-79) — `dark-` 토큰 한 벌을 더 두면 다크가
  따라온다. 손님이 헤더에서 전환하고 그 선택이 기억된다. `color-scheme` 도
  함께 전환해 체크박스·스크롤바까지 따라온다. 블록 CSS 의 하드코딩 색 200곳을
  토큰으로 옮겼고, 로그인·마이페이지는 `/api/themes/tokens.css` 로 같은
  팔레트를 받는다 — 화면을 옮겨도 사이트가 바뀌지 않는다.
- ~~**컴포넌트 프리미티브**~~ ✅ — 버튼·카드·배지·알림·표·페이지네이션·빈
  상태를 테마가 소유한다. 블록이 각자 그리면 사이트가 조각보가 된다.
- ~~**랜딩 재료**~~ ✅ — 히어로·특징 카드·행동 유도 배너·FAQ·알림·구분선을
  코어 블록으로. 스타터 세 유형의 홈·소개·이용안내를 이 재료로 다시 짰다.
- ~~**화면이 제 이름을 갖는다**~~ ✅ (ADR-80) — `ctx.setSeo({ title,
  description, ownHeading })`. 글 상세의 문서 제목이 "게시판"이던 것을 고쳤다.
  장바구니·주문서처럼 자기 h1 을 그리지 않는 화면은 테마가 제목을 그려 준다.
- ~~**헤더 유틸을 플러그인에 연다**~~ ✅ (ADR-82) — `registerHeaderAction`.
  쇼핑몰을 켜면 헤더에 장바구니가 생긴다(그전에는 주소를 외워야 했다).
- ~~**고쳤는데 안 바뀐다를 없앤다**~~ ✅ (ADR-81) — 테마 스탬프(버전 + 파일
  mtime)가 브라우저 캐시버스터와 서버 렌더 캐시 키에 함께 들어간다.

## 1.0 완성형의 정의

"완성"은 기능 개수가 아니라 **이 네 문장이 참이 되는 것**입니다.

1. **설치하면 바로 사이트다.** 유형을 고르면 돌아가는 사이트가 나온다. ✅ (스타터)
2. **운영에 법적 구멍이 없다.** 약관·탈퇴·청약철회·증빙·광고 규정을 시스템이
   지킨다 — 운영자가 실수로도 위법할 수 없게. ✅ (M15~M21)
3. **업데이트가 무섭지 않다.** 확장은 ZIP 업로드 또는 **원클릭 원격
   업데이트**(서명 검증)로 갱신되고 마이그레이션이 자동이다. ✅
4. **남이 만들 수 있다.** 계약 문서 ✅ · 개발 템플릿 ✅ (ADR-72) ·
   OpenAPI ✅ (ADR-73) · 레지스트리 ✅ (ADR-74). 첫 릴리스는 v0.1.0
   (알파, 2026-09-01)으로 나갔다. 남은 것: SDK npm 공개.

- [x] **블록을 키보드로는 고를 수 없었다** — 페이지 편집기의 선택지 열여덟 개가 전부 `<div onClick>`. 메뉴의 연결 대상도 같았고, 페이지 목록은 **행 클릭이 유일한 진입로**라 키보드만으로는 페이지를 열 수조차 없었다. 후기 **별점은 `<b>` 다섯 개**여서 별점을 매길 수 없었다(별점은 후기 필수 항목이다). `check-admin-keyboard.mjs` 가 이 계열을 본다
- [x] **뉴욕에서 주문을 보면 하루 전 날짜였다** — 주문 이력이 `toLocaleString()` (로케일도 시간대도 없음), 목록·쿠폰함은 언어만 따르고 시간대는 보는 사람의 것이었다. 서버 렌더는 사이트 시간대이므로 같은 주문이 화면마다 달랐다
- [x] **워크플로가 세 커밋 동안 한 줄도 돌지 않았다** — 단계 이름을 `name: "오늘"을 …` 로 적어 YAML 이 파싱되지 않았다. 잡이 하나도 만들어지지 않으면 화면에 원인이 나오지 않는다. 게다가 CI 확인 스크립트가 conclusion 을 안 봐서 실패를 초록으로 읽고 있었다 — 확인하고 있다고 믿으면서 아무것도 확인하지 않는 것이 더 나쁘다
- [x] **개발 서버가 프로덕션 빌드 한 번에 깨졌다** — `pnpm dev` 와 `pnpm build` 가 같은 `.next` 를 쓴다. 남는 메시지는 `Cannot find module './777.js'` 뿐이라 원인을 짐작하기 어렵다. 개발은 `.next-dev` 를 쓴다
- [x] **비회원 주문으로 아무 주소에나 메일을 보낼 수 있었다** — 주문서는 아무 이메일이나 받고 접수 즉시 그 주소로 안내가 나간다. 캡차가 켜진 기본 설정에서 10/10 성공·메일 10통을 재현했다. 받는 사람에게는 괴롭힘, 보내는 도메인에는 평판 손상, 운영자에게는 주문 목록 오염이다. 주문서에는 **캡차 대신 IP 한도**(시간당 20건, 비회원만) — 손님이 돈을 내려는 자리 앞에 퍼즐을 놓으면 진짜 손님을 잃는다. 재입고·1:1 문의에 이어 세 번째라 `check-mail-abuse.mjs` 로 막았다
- [x] **0.74MB 그림 한 장이 메모리 150MB 를 먹었다** — 업로드는 용량으로만 막고 있었는데, 단색 PNG 는 0.74MB 로 16000×16000(256메가픽셀)이 된다. 처리에 778ms·150MB(실측). sharp 기본 픽셀 상한이 268메가픽셀이라 사실상 열려 있었다. 5천만으로 낮추니 같은 파일이 4ms·0MB 고 정상 사진(6MP)은 그대로 줄어든다
- [x] **메일이 안 나가는 사이트가 자기는 잘 되는 줄 알았다** — SMTP 미설정이면 주문 안내(입금 계좌!)·비밀번호 재설정·이메일 인증이 콘솔로만 간다. MailProvider 계약에는 처음부터 `enabled`("설정 여부 확인용")가 있었는데 묻는 화면이 없어서, 뉴스레터만 큰 소리로 거부하고 거래 메일은 말없이 버려졌다. 대시보드가 무엇이 안 가는지 이름을 대고 알린다
- [x] **프로덕션인데 메일 링크가 전부 `localhost` 였다** — `BRICK_SITE_URL` 을 안 바꾸면 비밀번호 재설정·이메일 인증·비회원 주문 조회 링크가 받는 사람 컴퓨터를 가리킨다. 재현했다: 경고 0건에 재설정 링크가 `http://localhost:3000/reset-password?token=…`. 기존 검사는 http/https 만 보면서 localhost 를 **일부러 제외**하고 있었다 — 개발 편의를 위한 예외가 정확히 "설정을 잊은 상태"를 덮고 있었다. 같은 계열로 `BRICK_TRUST_PROXY` 도: 프록시 뒤에서 끄면 모든 손님이 한 IP 로 보여 IP 한도가 한 바구니가 되고 IP 차단이 듣지 않는다. 부팅 시점에는 알 수 없으므로 요청 헤더로 판단한다(믿지는 않는다 — 말만 해준다)
- [x] **"유지보수가 부른다"고 써 놓고 아무도 부르지 않았다** — 서비스마다 정리 함수가 있고 주석도 나란히 달려 있었는데 호출부가 없었다. 400일 된 행을 심고 띄웠더니 검색어("희귀질환 치료")와 이메일 인증 토큰이 그대로 남았다. 스키마가 스스로 "질병·법률 문의라 민감하다"고 적어 두고 IP 는 해시로 저장하면서, 정작 검색어는 영원히 남았다. 나머지 셋은 유지보수가 같은 정책을 **다시 구현**해 두 곳에 적혀 있었다. 보관 기간은 데이터의 주인이 갖고 유지보수는 일정만 갖는다(ADR-111)
- [x] **한국어 화면에 `request file too large`** — 업로드 한도에 걸리면 멀티파트 원문이 그대로 나갔고 화면은 그 message 를 그대로 보여줬다. 한도가 얼마인지도 말하지 않는다. 휴대폰 사진이 12MB 인 시대에 가장 자주 만나는 오류다. 전역 필터에서 한국어로 바꾸고 한도를 숫자로 말한다(설정값을 읽어서 — 안내가 실제 설정과 다르면 없느니만 못하다). 업로드 실패가 성공과 같은 초록으로 뜨던 것도 함께 고쳤다
- [x] **백업 복원 경로가 검증되지 않았다** — `docs/operations.md` 가 `dump`/`restore` 를 안내하는데 어떤 수트도 왕복시키지 않았다. 덤프를 뜨고 복원해 내용이 돌아오는지 아무도 확인한 적이 없고, 운영자는 정말 필요한 순간에 알게 된다. `smoke-backup.sh` 가 왕복시킨다: 지운 회원·페이지가 돌아오는가, **덤프 뒤에 만든 것은 사라지는가**(복원의 의미를 오해하지 않도록), 복원 뒤 로그인·목록이 되는가. 문서가 시키는 대로 **앱이 돌고 있는 채로** 복원해 본다. 검증에는 서버와 주 버전이 맞는 `pg_dump` 가 필요해 CI 에 postgresql-client 17 을 설치한다 — 러너 기본 클라이언트는 서비스 컨테이너(17)보다 낮아 `server version mismatch` 로 거부한다. 문서에는 "그 시점으로 되돌아간다"는 경고와 버전 불일치 대처를 덧붙였다. 수트가 정말 복원을 지키는지도 확인했다 — 임시 브랜치에서 `pg_restore` 호출을 빼자 일곱 개가 실패했다(로컬 맥에는 `pg_dump` 가 없어 이 역검증도 CI 에서 돌렸다)
- [x] **비밀번호를 틀리면 로그인 화면에 `invalid credentials`** — 화면은 서버가 준 message 를 그대로 보여주고 한국어 대체 문구는 message 가 **아예 없을 때만** 쓰인다. 손님이 가장 자주 보는 오류 화면이 영어였다. 같은 자리에서 열여덟 곳을 더 찾았다: 관리 저장이 401 이면 `Unauthorized`(메시지를 비우면 Nest 가 넣는 기본값), 페이지 주소가 겹치면 `slug "..." already exists`, 설치 화면은 `siteName, adminEmail, adminPassword(8+) required`, 확장 zip 검증은 구조 설명이 통째로 영어였다. `check-error-messages.mjs` 가 막는다 — **같은 파일의 상수까지 따라간다**(첫 판은 그것을 놓쳤고, 마침 내가 로그인 문구를 상수로 옮긴 참이었다)
- [x] **오류를 눈으로만 알려주고 있었다** — 로그인에 실패하면 버튼 아래 빨간 글씨가 나타나는데, 브라우저로 확인해 보니 라이브 영역이 **하나도 없었다**(`live: []`). 스크린리더 사용자에게는 버튼을 눌렀는데 아무 일도 일어나지 않은 화면이다. 가입 화면만 `role="alert"` 를 갖고 있었고 열한 곳이 남아 있었다 — 관리자 로그인·재인증·메뉴·설정·선언 화면·비밀번호 재설정. 서버가 그리는 쪽에서도 후기·문의 폼 둘을 더 찾았다(검사를 플러그인 HTML 까지 넓히자마자 나왔다). 메뉴 화면은 성공/실패를 **문구 앞 두 글자**로 판별하고 있어서 번역을 고치면 색이 뒤집혔다 — 상태로 바꿨다
- [x] **저장된 비밀번호가 채워지지 않았다** — 로그인 칸에 `name` 도 `autocomplete` 도 없었다(브라우저 DOM 으로 확인). 비밀번호 관리자와 iOS 키체인은 이 단서로 칸을 알아보므로, 손님은 폰에서 매번 손으로 쳤다. 주문서에는 이미 제대로 넣어 두고 있었는데(name·tel·postal-code·street-address) **모든 손님이 지나는 로그인·가입만** 빠져 있었다. 검사를 만들자마자 마이페이지·비밀번호 찾기·설치 화면에서 아홉 곳을 더 찾았다. 설치 화면의 **데이터베이스** 비밀번호는 내 계정이 아니므로 `off` — 빠뜨린 것과 정한 것을 구별하는 것이 이 검사의 요지다. 주문서에는 같은 태그에 `autocomplete` 가 두 번 적힌 곳이 넷 있었다(브라우저는 첫 번째만 쓴다)
- [x] **로그인하면 읽던 자리를 잃었다** — 로그인 화면은 `?next=` 를 지원하는데 그것을 보내는 화면이 **하나뿐**이었다(1:1 문의). 게시판의 비밀글·답글, 쿠폰함, 마이페이지는 맨 `/login` 이라 로그인 뒤 홈으로 떨어졌고, 손님은 글을 다시 찾아 들어가야 했다. 테마가 직접 넣은 링크까지 생각하면 진입로를 하나씩 고쳐서는 끝이 없어서, `?next=` 가 없으면 **같은 출처의 referrer** 로 돌려보낸다. 브라우저로 확인했다: `/shop` 에서 로그인 → `/shop` 복귀, `?next=//evil.example/x` → 홈(오픈 리다이렉트 차단), 로그인·가입 계열 경로는 제자리를 맴돌지 않도록 제외
- [x] **운영자가 만든 페이지는 새로고침 한 번에 사라졌다** — 게시판은 손님이 쓰던 글을 초안으로 지켜 주는데(자동 저장·복구 안내), 블록을 열몇 개 쌓아 만든 랜딩 페이지와 한참 고친 상품 설명은 아무 보호가 없었다. 같은 원칙이 한쪽에만 있었다. 저장하지 않은 편집이 있으면 창을 닫을 때 브라우저가 묻고, **"닫기"·"취소" 버튼**도 묻는다 — 화면 안에서만 움직이는 그쪽이 오히려 더 흔한 손실 경로다. 아무것도 안 친 채 나가는 사람은 붙잡지 않는다
- [x] **광고 메일이 메일 앱에게는 수신거부 방법을 말하지 않았다** — 본문에는 링크가 붙는데(정보통신망법 제50조 제4항) `List-Unsubscribe` 헤더가 없었다. Gmail·Apple Mail·네이버가 메일 위에 **"수신거부" 버튼**을 띄우는 근거는 본문이 아니라 그 헤더다. 버튼이 없으면 사람들은 대신 **"스팸 신고"** 를 누르고, 그것이 쌓이면 발신 도메인의 평판이 떨어져 광고만이 아니라 **입금 계좌가 담긴 주문 안내**까지 스팸함으로 간다. 헤더와 함께 원클릭(RFC 8058)을 선언하고, 선언한 이상 그 주소가 **POST 를 받도록** 라우트를 더했다 — 선언만 하고 받지 않으면 버튼이 실패해서 없느니만 못하다. 공지·거래 메일에는 붙이지 않는다. SMTP 싱크가 헤더를 파싱해 놓고 버리고 있어서, 메일이 "무엇을 말하는지"만 보고 "어떻게 취급되는지"는 아무도 보지 못했다
- [x] **훔친 세션 하나로 계정이 넘어갔다** — 이메일 주소 변경에 현재 비밀번호를 묻지 않았다. 재현했다: 세션 쿠키만으로 주소를 공격자의 것으로 바꾸고(`{"sent":true}`), 확인 링크는 그 새 주소로 가고, 원래 주인에게는 아무것도 가지 않았다. 그 뒤 원래 주소로는 로그인이 **401** 이다. 재인증(ADR-75)은 회원 목록 열람과 대량 발송에만 걸려 있었고 정작 계정 자체를 넘기는 자리에는 없었다. 셋을 함께 넣었다: 변경 요청에 재인증, 확정 시 **옛 주소로 알림**, 모든 세션 무효화(비밀번호 변경과 같은 처리). 같은 주소 재인증은 위험한 작업이 아니므로 그대로 둔다
- [x] **소셜 연결이 비밀번호를 지우지 못하는 뒷문이었다** — `?link=1` 은 세션만 있으면 됐다(302). 훔친 세션으로 공격자가 자기 소셜 계정을 붙여 놓으면, 피해자가 비밀번호를 바꿔도 계속 들어온다 — 비밀번호 재설정으로는 지워지지 않는다. 게다가 **조용히** 일어나 주인은 알 길이 없었다. 이메일 주소 변경과 같은 등급이라 같은 보호를 걸었다(재인증 + 계정 주소로 알림). 해제는 그대로 둔다 — 접근 수단을 없애는 일이고 마지막 수단은 이미 거부한다. 소셜 연결 API 를 쓰는 **화면은 아직 없다**
- [x] **코드가 그대로인데 CI 가 빨개졌다** — 판매 리포트 수트가 결제 시각을 `2026-09-15` 로 못박고 그 하루만 조회해 금액을 단언했다. 적을 때는 먼 미래라 안전했는데, **그날이 오자** 수트가 그날 만든 다른 주문들과 같은 버킷에 섞여 순매출이 어긋났다(기대 20000, 실제 56000). 지난 날로 옮기고, `check-smoke-dates.mjs` 가 **하루짜리 창**만 골라 본다 — 범위의 끝(`to=2026-12-31`)은 미래여도 해롭지 않으므로 보지 않는다
- [x] **소셜 연결 API 를 쓰는 화면이 없었다** — 연결·해제·목록이 다 구현돼 있고 스모크도 전수로 돌리는데, 회원이 닿을 수 있는 화면이 없었다. 그래서 자기 계정에 소셜 계정이 붙어 있어도 볼 수도 뗄 수도 없었다 — 훔친 세션으로 심어진 뒷문이라면 더더욱 그렇다. 바로 앞에서 넣은 연결 알림 메일이 "내 정보에서 해제하세요" 라고 안내하는데 **그 화면이 없었다.** 마이페이지에 "연결된 로그인 수단" 을 만들었다(목록·해제·비밀번호 확인 후 연결). 곁들여 마이페이지의 알림 배너에 `role` 이 없어 실패가 스크린리더에 전달되지 않던 것도 고쳤다 — `check-error-announce.mjs` 가 `{(notice || error) && …}` 모양을 못 보고 있었다(여는 중괄호 바로 뒤의 변수만 봤다)
- [x] **손님마다 다른 화면에 캐시 정책이 없었다** — 서버 렌더 HTML 과 API 응답 어디에도 `cache-control` 이 없었다. 그런 200 응답은 중간 캐시가 자기 판단으로 담는다. 설치 안내는 앞에 Nginx·Caddy 를 두라고 하고 그 앞에 CDN 을 얹는 사이트가 많다 — 그러면 한 손님의 주문 화면이 다른 손님에게 그대로 나간다. 렌더 라우트의 주석은 "로그인 사용자는 캐시를 우회해야 한다"고 적어 두었는데, 그것은 **우리가 API 를 부를 때**의 이야기였고 아래로 내보내는 응답은 아무 말도 하지 않고 있었다. 공유 캐시에는 `private`, 세션을 들고 온 요청에는 `no-store`. 자기 정책을 정한 응답(정적 자산 immutable·사이트맵)은 건드리지 않는다 — 정책을 아는 쪽이 하나여야 한다
- [x] **보안 문서가 옛 숫자를 말하고 있었다** — "가입 스팸: IP별 5회/시간" 이라고 적혀 있는데 코드는 **같은 이메일 3회 · 같은 IP 20회** 였다. 주석에는 왜 바꿨는지까지 있었다(IP 하나에 좁게 걸면 NAT 뒤 사무실·학교에서 여섯 번째 사람이 막힌다). 코드가 옳고 문서만 옛 설계에 머물러 있었다 — 운영자가 숫자를 믿고 판단하는 자리다. 문서를 고치고 **동작**을 스모크로 못박았다: 다섯 명이 연달아 가입해도 막히지 않고, 같은 이메일 네 번째는 막히고, 대량 생성은 결국 막힌다. 처음 쓴 단언은 캡차를 풀지 않아 전부 400 이었고 그래서 엉뚱하게 통과했다
- [x] **단언은 전부 통과인데 CI 만 빨개졌다** — 보안 수트가 85개 통과·0개 실패를 찍고 종료코드 1 로 끝났다. 정리(trap)에서 이미 죽은 프로세스를 맨손으로 `kill` 했고, 트랩 본문도 `set -e` 아래에서 돌기 때문에 그 실패가 그대로 스크립트를 1 로 끝냈다. 같은 모양이 열여섯 수트에 있었다(지금은 서버가 살아 있어 우연히 통과할 뿐이었다). 전부 `|| true` 로 막고, `check-smoke-hygiene.mjs` 가 미래 날짜와 함께 이 계열을 본다 — 원인을 찾는 데 드는 시간이 고치는 시간의 몇 배다
- [x] **입금할 계좌를 다시 볼 곳이 없었다** — 브라우저로 비회원 구매를 끝까지 밟다 찾았다. 주문 완료 화면은 계좌를 보여 주는데, 그 화면을 닫으면 다시 볼 곳이 없었다. 무통장 입금은 보통 나중에 한다 — 은행 앱을 열고, 밤에, 다음 날. 그때 손님이 보는 주문 상세에는 **"입금대기" 라고만** 적혀 있었다. 계좌는 메일에만 있는데 주문서의 이메일 칸은 **선택**이고, SMTP 가 없으면 그 메일조차 나가지 않는다. 입금대기인 무통장 주문의 상세에 계좌를 보여준다 — 이미 낸 주문에는 보여주지 않는다(한 번 더 내야 하나 싶게 만든다)
- [x] **운영자가 고른 말과 오류가 쓰는 말이 달랐다** — 폰으로 주문을 처리하다 찾았다. 결제완료에서 배송중으로 바로 바꾸면 `"paid" 상태에서 "shipped" 로 변경할 수 없습니다` 가 떴다. 화면에서는 "결제완료"·"배송중" 을 골랐는데 오류만 내부 코드로 말하고, **다음에 무엇을 할 수 있는지**(상품준비중을 거쳐야 한다) 말하지 않았다. 게다가 그 **저장 실패가 초록색**으로, `role` 도 없이 떴다 — 미디어·메뉴에서 고친 결함이 **스물네 개 리소스가 모두 쓰는 화면**에 남아 있었다. 고치는 김에 코어 `josa()` 의 **ㄹ 받침 예외**를 채웠다(환불으로 → 환불로). 주석에 "필요해지면 그때 규칙과 함께 더한다" 고 적어 둔 자리였고, 릴리스 도구는 이미 그 규칙을 구현해 두고 "코어의 josa() 와 같은 규칙" 이라 적어 두었다 — 실제로는 갈라져 있었다
- [x] **나중에 붙인 송장이 조용히 지나갔다** — 폰으로 발송 처리를 하다 찾았다. 한국 쇼핑몰의 실제 운영은 오전에 택배사에 넘기고 발송 처리, **송장은 저녁에 일괄 등록**이다. 관리 화면도 "발송 처리" 와 "송장번호 입력 + 발송" 을 따로 두고 그 흐름을 인정한다. 그런데 나중에 붙인 송장은 아무것도 알리지 않았다 — 손님이 받은 발송 메일에는 송장이 없고, 손님은 주문 조회를 새로고침하거나 문의한다. 이미 발송된 주문에 송장이 **새로** 붙으면 알린다(같은 값을 다시 저장하는 것은 알림이 아니다 — 목록을 통째로 다시 붙여넣는 일이 흔하다). 일괄 경로의 조회에 `tracking_no` 가 빠져 있어 중복 발송이 될 뻔한 것도 함께 고쳤다
- [x] **청약철회 신청 폼의 칸에 이름이 없었다** — 손님으로 반품 신청을 밟다 찾았다. 사유·상세 사유·수량 칸에 이름이 없어 스크린리더에는 "콤보 상자"·"편집"·"스핀 버튼" 으로만 읽혔다. 제목(h4)은 크게 적혀 있었지만 칸과 이어져 있지 않았다. 청약철회는 전자상거래법이 보장하는 권리다. **화면 감사 도구가 이것을 오래 놓치고 있었다** — 닫힌 `<details>` 안의 요소는 크기가 0 이라 모든 검사가 건너뛴다("보이지 않으니 검사할 것도 없다" 였는데, 손님이 열면 보이는 화면이다). 도구가 접힌 details 를 펴 두고 보게 했다. 그 도구가 바로 로그인 화면의 이름 없는 링크도 찾아냈다 — 사이트 이름이 오기 전에는 글자가 공백 하나뿐이라 25px 짜리 이름 없는 표적이었고, 그것이 로그인 화면에서 사이트로 돌아가는 유일한 길이다
- [x] **회원이 포인트를 한 점도 쓸 수 없었다** — 회원으로 장바구니부터 주문까지 밟다 찾았다. 서버는 처음부터 포인트로 결제할 수 있었고(견적·주문 모두 `pointUsed` 를 받는다), `pointsAvailable` 이라는 필드가 **"포인트 플러그인이 활성화되어 있으면 주문서에 포인트 사용 UI 를 띄운다"** 는 주석과 함께 있었다. 그런데 그 필드를 읽는 화면이 아무 데도 없었다 — 세 곳에서 내보내기만 했다. 회원은 포인트를 쌓기만 하고 쇼핑에는 쓸 수 없었다(쪽지에서만 쓸 수 있었다). 주문서에 칸을 달고, 장바구니 응답이 쓸 수 있는지와 잔액을 함께 준다. 합계는 **서버 견적을 그대로** 쓴다 — 상한·등급 할인·쿠폰이 얽혀 있어서 같은 규칙을 두 곳에 두면 갈라진다
- [x] **같은 권한 판단이 세 곳에 따로 적혀 있었다** — "서버가 내보내는데 아무도 읽지 않는 필드" 를 훑다 찾았다. 집행(`assertCanModify`)은 비회원 글을 **비밀번호로** 허용하고 화면도 버튼을 보여준 뒤 비밀번호를 묻는데, API 응답의 `canModify` 만 비회원 글에 `false` 라고 말했다. 읽는 화면이 없어서 아무도 몰랐다 — 누가 그것을 믿고 화면을 만들면 비회원이 자기 글을 고칠 버튼을 잃는다. `canModifyPost()` 하나가 셋을 다 정한다
- [x] **약관을 개정해도 기존 회원에게 묻지 못했다** — 개정·목록(`agreements/pending`)·수락 API 가 다 있고, 서버는 프로필 응답에 `pendingAgreements` 개수까지 실어 보내며 "동의해야 계속 이용할 수 있다" 고 말한다(`acceptPending`). 그런데 그것을 읽는 화면이 없었다 — 웹에서 약관을 다루는 화면은 **가입 화면 하나뿐**이었다. 마이페이지 맨 위에 재동의 섹션을 만들었다(개정 본문·체크·동의, 체크 전에는 버튼이 잠긴다). 오늘 이 계열이 세 번째라 `check-reachable-screens.mjs` 로 못박았다 — 소셜 연결 해제·포인트 사용·약관 재동의, 셋 다 API 와 스모크는 있고 화면만 없었다
- [x] **2단계 인증을 켜면 사이트에서 잠겼다** — 서버는 TOTP 를 직접 구현하고(RFC 6238 벡터까지 검증) 복구 코드·도전 토큰·세션 기록·감사 로그에 116개짜리 스모크까지 갖추고 있었다. 그런데 **그것을 쓰는 화면이 하나도 없었다.** 관리 설정에는 "관리자에게 2단계 인증 요구" 체크박스가 있어서, 켜는 순간 `AdminGuard` 가 2FA 없는 관리자의 관리 작업을 전부 막는다 — 그 안에는 **그 설정을 되돌리는 것**도 들어 있으니, 등록할 화면이 없는 채로 켜면 DB 를 직접 만지지 않는 한 나올 수 없다. 로그인은 더 조용히 망가진다: 2FA 가 켜진 계정에 서버는 세션 없이 200 + `twoFactorRequired` 를 주는데, 로그인 화면은 `res.ok` 만 보고 홈으로 보냈다 — 로그인한 줄 알고 갔더니 로그아웃 상태다. `TwoFactorService` 주석은 "강제 설정이 켜져 있어도 등록 경로는 열어 둔다"며 이 잠금을 대비해 두었는데, 화면이 없다는 이유로 그 대비가 무의미했다. 마이페이지에 2단계 인증 섹션(등록·복구 코드·재발급·해제)을 만들고 로그인 두 화면에 코드 단계를 더했다. QR 라이브러리는 넣지 않는다 — `totp.ts` 가 "인증 경로의 의존성 하나는 공급망 위험 하나" 라며 외부 패키지를 배제한 자리다. 대신 키를 4자씩 끊어 보여주고 `otpauth://` 링크를 준다(폰에서는 눌러서 바로 등록된다). 서버에도 자기잠금 방지를 넣었다 — IP 허용 목록·차단 목록에는 이미 있고 이것만 없었다
- [x] **사업자정보를 입력할 자리가 없었다** — 전자상거래법 제13조는 상호·대표자·사업자등록번호·통신판매업 신고번호·주소·전화번호를 소비자가 쉽게 알 수 있도록 표시하라고 정한다. 서버는 그것을 진지하게 구현해 두었다: 국세청 체크섬 검증(`000-00-00000` 같은 칸 채우기까지 거른다), 조항을 인용한 경고(제13조·개인정보보호법 제31조), 공개 API, 테마 푸터 렌더, 전용 스모크, 그리고 `docs/business-info.md` 는 **"관리자 → 설정 → 사업자정보에서 입력합니다"** 라고 길까지 안내한다. **그 화면만 없었다.** 그래서 모든 브릭 사이트의 푸터가 빈 채였고, 쇼핑몰은 합법적으로 열 수 없었다 — 문서가 가리키는 곳에 아무것도 없으니 운영자는 자기가 못 찾는 줄 안다. 설정 화면에 섹션을 만들었다. 라벨은 **서버가 준 것**(`labels`)을 쓴다 — 검증 실패 문구가 같은 이름을 쓰므로 화면에 따로 적으면 "상호를 입력하세요" 라는데 화면에는 다른 이름이 적히는 일이 생긴다. 빠진 필수 항목은 이름을 대서 알리고(`commerceReady`·`missing`), 저장 뒤 서버가 주는 법 경고(`warnings`)를 그대로 보여준다 — 그 경고들은 그동안 아무에게도 닿지 않았다
- [x] **손님이 현금영수증을 신청할 자리가 없었다** — 부가가치세법 제32조의2 는 최종소비자가 요청하면 현금영수증을 발급하라고 정한다. 서버는 발급·취소·재발급·금액 분해·반품 시 증빙 취소까지 갖추고 있었고, `GET /tax/info` 에는 **"화면이 폼을 만들고 손님에게 설명하는 데 쓴다"** 는 주석까지 달려 있었다. 그 화면이 없었다 — 요청할 곳이 없으면 그 권리는 없는 것과 같다. 주문 상세에 신청 섹션을 만들었다. 신청 가능 여부는 **서버가 판단해서 준다**(`cashReceipt`) — 규칙을 화면에 다시 적으면, 못 하는 주문에 폼을 내밀어 누른 뒤에 거절하거나 할 수 있는데 안 내밀게 된다. 발급된 뒤에는 폼 대신 결과를 보여주고, 번호는 가려서 준다(주민등록번호일 수 있다). 만들다 보니 더 나쁜 것이 나왔다: **비회원은 아예 신청할 수 없었다.** 청약철회는 처음부터 주문 토큰으로 되는데 현금영수증만 회원으로 막혀 있었고, 정작 현금영수증이 꼭 필요한 주문이 그 **무통장 + 비회원** 주문이다. 같은 규칙으로 맞췄다. 그리고 지난 라운드에 만든 `check-reachable-screens.mjs` 가 **헐거웠다는 것도 이때 드러났다** — 플러그인은 서버와 화면이 한 저장소에 있어서 서버가 등록한 경로 문자열에 걸렸고, 주문서의 포인트 UI 를 통째로 지워도 초록이었다. 이제 화면을 그리는 파일만 본다
- [x] **주문을 눌러도 목록이 다시 나왔다** — 현금영수증 화면을 확인하다 찾았다. 쇼핑몰 페이지를 만들지 않고 **선언 화면**(`shop/orders`)만 쓰는 사이트 — 이미 굴러가던 사이트에 쇼핑몰 플러그인을 나중에 켠 경우가 그렇다 — 에서는 주문 상세가 **아예 열리지 않았다.** 주문번호는 두 길로 들어오는데(`/shop` 라우터가 props 로 주는 길, 선언 화면의 pathTail) 두 번째를 읽지 않았다. 게다가 목록의 링크는 자기 경로에 `/orders` 를 한 번 더 붙여 `/shop/orders/orders/…` 라는 없는 주소를 가리켰고, 그 주소는 404 가 아니라 **목록을 다시** 보여줬다 — 손님은 눌렀는데 아무 일도 안 일어난 것으로 본다. 상세에 달려 있던 것이 전부 닿지 않았다: 입금 계좌, 청약철회 신청, 방금 만든 현금영수증. 주문번호를 두 길 모두에서 읽고, 목록 주소는 "지금 경로에서 주문번호를 뗀 것" 하나로 정한다. 선언 화면으로 들어온 상세는 문서 제목도 스스로 정한다 — 안 하면 상세인데 제목이 "주문 내역" 이다
- [x] **청약철회를 신청하고 나면 어떻게 됐는지 알 수 없었다** — 신청은 되는데(전자상거래법 제17조, 비회원 포함) 그 뒤가 없었다. 새로고침하면 신청 폼만 다시 나오고 낸 요청은 화면에서 사라진다 — 승인됐는지 거절됐는지 환불이 얼마인지 알 길이 없어서 결국 전화한다. `GET /my/returns` 도 `POST /returns/:id/cancel` 도 부르는 화면이 없었고, 번역 파일에는 **그 화면을 위한 키가 이미 다 있었다**(`ret.myRequests` · `ret.emptyRequests` · `ret.colNo` · `ret.cancelRequest` …) — 문구까지 써 두고 화면만 없었던 것이다. 주문 상세가 이 주문의 요청을 접수번호·종류·사유·상태·환불액으로 보여주고, 처리 시작 전이면 물릴 수 있다. 여기서도 **비회원만 막혀 있었다** — 신청은 주문 토큰으로 되는데 철회만 회원을 요구해서, 잘못 누른 비회원은 되돌릴 방법이 없었다(현금영수증과 같은 모양이 이틀 사이 세 번째다). 곁들여 다시 그릴 때 안내가 사라지던 것도 고쳤다: 접수번호와 철회 완료를 화면에 써 놓고 목록을 다시 그리면 그 말이 같이 지워져, 스크린리더에는 아무 일도 없었던 화면이 된다
- [x] **비회원에게 조회용 비밀번호를 받아 놓고 조회할 곳이 없었다** — 1:1 문의는 비회원도 남길 수 있고, 폼은 이름·이메일과 함께 **"조회용 비밀번호"** 를 받는다. 접수하면 문의번호를 알려 준다. 그런데 그 다음 화면은 **"문의 내역을 보려면 로그인해주세요"** 였다 — 받아 적은 번호와 비밀번호를 넣을 칸이 어디에도 없었다. 서버에는 `GET /tickets/by-no/:ticketNo?pw=` 가 처음부터 있었고 주석에 "비회원이 메일 링크로 들어오는 경로" 라고까지 적혀 있었는데, 메일 링크 말고는 들어올 길이 없었던 것이다(그리고 SMTP 를 설정하지 않은 사이트에서는 그 메일도 안 간다). 조회 폼을 만들고, 연 뒤에는 추가 문의도 쓸 수 있게 했다 — 답변 칸은 이미 보이는데 비밀번호를 같이 보내지 않아 누르면 403 이었다
- [x] **제주 손님은 화면에 없는 3,000원을 더 냈다** — 지역별 배송비(제주·도서산간)는 서버가 **주문할 때 우편번호를 보고** 붙인다. 그런데 주문서의 견적 요청에는 **우편번호가 빠져 있었다.** 그래서 화면에는 25,000원이 뜨고 실제 주문은 28,000원으로 만들어졌다 — 재현했다. `/shipping-zone` 라우트는 "주문서가 금액을 미리 보여주는 데 쓴다"는 주석과 함께 있었는데 부르는 화면이 없었고, 스모크는 "표시만 하고 안 받으면 손해"라며 **반대 방향**만 지키고 있었다(덜 보여주고 더 받는 것도 같은 문제다). 견적에 우편번호를 함께 보내고, 지역비를 **별도 줄로** 보여준다 — 총액 숫자만 조용히 늘면 무엇이 붙었는지 모른 채 주문하거나 그 자리에서 이탈한다. 고치다 보니 `requote` 가 **포인트 설정 안에** 들어 있었다: 포인트 플러그인이 꺼진 사이트에서는 우편번호를 넣어도 합계를 아예 다시 계산하지 않았다. 밖으로 빼서 쿠폰 칸도 같이 물렸다
- [x] **재입고 알림을 끊을 방법이 없었다** — 재입고 메일은 "신청하지 않으셨다면 아래 링크를 눌러 알림을 해지해주세요" 라며 `/shop/restock/cancel/<토큰>` 을 보낸다. 스토어프론트에 그 경로를 받는 자리가 없어서 **"상품을 찾을 수 없습니다"** 가 떴다(재현했다). 목록 API 도 같은 주소를 `cancelPath` 로 돌려주고 있었고, 그 목록을 보여주는 화면도 없었다. 광고가 아니라고 적어 두었어도, 한 번 신청하면 끊을 수 없는 알림은 받는 사람에게 끊을 수 없는 메일이다 — 수신거부 헤더를 붙인 것과 같은 이유로 고친다. 해지 화면은 **열자마자 해지한다**: 메일에서 "해지"를 누른 사람에게 버튼을 한 번 더 내밀면 그 자리에서 포기하고, 그러면 메일은 계속 간다. 로그인도 요구하지 않는다(비회원도 신청할 수 있고, 서버의 해지 함수 주석이 이미 같은 말을 한다). 회원에게는 신청 내역 화면을 함께 준다. 역검증에서 첫 단언이 헐거웠다 — 클래스 이름으로 찾았더니 **CSS 에도 그 이름이 있어서** 화면이 없어도 통과했다. 분기에서만 나오는 속성으로 바꿨다
- [x] **위시리스트에 담을 수가 없었다** — 목록·삭제 화면이 있고 회원 메뉴에도 링크가 있는데, **담는 버튼이 어느 화면에도 없었다.** `POST /wishlist` 를 부르는 곳이 0곳이라 위시리스트는 영원히 "담아둔 상품이 없습니다" 였다. `GET /wishlist/check` 는 "목록 화면이 여러 상품을 한 번에 물어본다" 는 주석까지 달고 아무도 부르지 않았다. 상품 화면에 하트를 달았다 — 품절 상품에도 둔다(지금 못 사는 물건이야말로 담아 둔다). 비회원도 담을 수 있다(서버가 게스트 토큰을 발급한다) — 로그인부터 요구하면 대부분 거기서 끝난다. 그리고 `POST /wishlist/merge` 도 부르는 곳이 없어서, 비회원으로 담고 로그인하면 **담은 것이 사라진 것처럼** 보였다: 위시리스트 화면이 열릴 때 합친다. 곁들여 로그인한 뒤에도 "로그인하면 다른 기기에서도 보입니다" 안내가 남던 것도 고쳤다 — 게스트 토큰을 비회원 주문 조회에 계속 쓰느라 지우지 않는데, 그 존재를 로그인 여부로 착각하고 있었다. 역검증에서 단언 하나가 또 헐거웠다: 경로를 **주석에도** 적어 두어서 부르는 자리를 지워도 통과했다
- [x] **다크로 보는 운영자에게는 저장 버튼이 빈 칸이었다** — 새로 만든 화면들에 대비 감사 도구를 돌리다 찾았다. 관리 화면의 `.btn-primary` 가 글자색을 `#fff` 로 박아 두고 있었는데, `--color-primary` 는 **칠하는 색**이고 그 위에 올릴 글자색은 테마가 `--color-on-primary` 로 따로 선언한다. storefront 테마의 다크 팔레트는 primary 가 밝은 색(#f2f3f6)이라 흰 글자가 사라진다 — 측정값 1.11:1(필요 4.5). 관리 화면의 **모든 저장 버튼**이 그랬다. 테마는 그 경우를 대비해 `--color-on-primary`(#14161b)를 같이 선언해 두는데 아무도 읽지 않았다. `check-on-primary.mjs` 가 막는다: primary 를 배경으로 칠하는 규칙이 글자색을 정한다면 그 값은 리터럴이 아니라 `--color-on-primary` 여야 한다(배경만 다시 칠하는 hover 규칙은 보지 않는다)
- [x] **운영자가 자기 사이트의 약관을 고칠 수 없었다** — 기본 약관의 첫 줄은 **"※ 이 문서는 초안입니다. 실제로 수집하는 항목에 맞게 반드시 고쳐 쓰세요"** 다. 그런데 고칠 화면이 없었다 — `GET/POST /api/admin/agreements` 가 감사 로그까지 갖추고 있었지만 부르는 곳이 어디에도 없어서, 운영자는 curl 없이는 이용약관도 개인정보처리방침도 바꿀 수 없었다. 모든 브릭 사이트가 초안을 내걸고 있었다는 뜻이고, 바로 앞 라운드에서 만든 **재동의 화면도 아무도 띄울 수 없었다**(개정할 방법이 없으니까). 관리 화면에 약관을 넣었다: 지금 쓰이는 버전·동의한 회원 수·시행일을 보여주고, 고르면 **현재 본문을 채워 준다**(빈 칸에서 다시 쓰라고 하면 아무도 고치지 않는다). "수정" 이 아니라 **"개정 발행"** 이라고 말한다 — 서버가 기존 버전을 고치지 않고 새 버전을 만들기 때문이고, 그 이유(누가 어느 버전에 동의했는지가 증거다)를 화면에도 적었다. 필수/선택과 시행일도 화면에서 정한다 — 광고성 정보 수신을 필수로 만들면 위법이라는 것도 그 자리에서 말한다. 브라우저로 끝까지 확인했다: 2차 개정을 발행하자 회원의 마이페이지에 재동의가 떴다
- [x] **회원에게 단체메일을 보낼 방법이 없었다** — `docs/mailing.md` 는 "관리자 → 회원 → 단체메일" 이라고 안내하고, 106개짜리 스모크가 (광고) 강제 표기·동의자만 발송·발송 직전 동의 재확인·수신거부 헤더까지 지키는데, **그것을 쓰는 화면이 없었다.** 운영자는 curl 없이는 한 통도 보낼 수 없었다. 관리 화면을 만들면서 서버가 이미 정해 둔 것을 그대로 따랐다: 종류 목록이 내려주는 **법적 근거 문구**(정보통신망법 제50조)를 그 자리에 보여주고, 보내기 전에 **대상 수**를 세어 보여주며(서버 주석: "수만 명에게 잘못 보내는 것은 되돌릴 수 없다"), 광고에서 동의하지 않아 빠진 인원도 함께 보여준다 — "대상이 왜 이렇게 적은가" 에 답이 된다. 발송은 **재인증**을 요구한다(ADR-75, 서버가 403 으로 막는다). 만들다 보니 내 화면이 함정을 하나 만들고 있었다: 발송이 실패하면(SMTP 미설정이 가장 흔하다) 캠페인은 이미 만들어져 있는데 목록에 보이지 않아, 다시 누르면 같은 내용이 하나씩 쌓였다 — 나중에 SMTP 를 고치면 같은 메일이 여러 통 나간다. 만들어 둔 것을 재사용하고, 실패해도 목록을 다시 읽는다. CI 가 표 접기와 오류 안내를 잡아 줬다(폰에서 카드로 접히지 않았고, 실패 건수 표시가 검사에 걸렸다 — 뒤엣것은 지난 발송의 기록이라 읽어주지 않는 이유를 적었다)
- [x] **64MB 덤프를 받는다고 해 놓고 2MB에서 막았다** — 그누보드 이전은 덤프(SQL 텍스트)를 JSON 으로 받는다. 컨트롤러는 `MAX_DUMP_BYTES = 64MB` 로 검사하고 문서도 "(64MB 이하)" 라고 안내하는데, Fastify 본문 한도가 **2MB** 였다. 3.43MB 덤프를 올리면 컨트롤러에 닿기도 전에 영어로 `Request body is too large` 가 돌아온다 — 실제 그누보드 덤프는 거의 이보다 크므로, 문서가 안내하는 업로드 경로는 **되는 일이 없었다.** 한도를 경로마다 나눴다: 보통 JSON 은 그대로 2MB, 이전 경로만 64MB. Fastify 의 기본 JSON 파서는 갈아끼우지 않는다(그것이 프로토타입 오염을 막아 준다) — 본문을 읽기 전에 Content-Length 로 거른다. 그 예외를 이전 경로에만 주는 것도 스모크로 못박았다: 다른 API 에 같은 본문을 보내면 여전히 413 이고, 이제 그 거절도 한국어로 말한다
- [x] **문서가 안내하는 "관리자 → 이전" 이 없었다** — `docs/migrate-gnuboard.md` 는 "관리자 → **이전** 에서 덤프를 올리고 **분석**을 누릅니다" 라고 한 절을 통째로 안내하고, README 는 그누보드 이전을 기본 동봉 기능으로 내세운다. API 도 155개짜리 스모크도 CLI 도 있는데 **관리 화면만 없어서**, 문서를 따라온 운영자는 없는 메뉴를 찾는다. 화면을 만들었다: 덤프를 고르고 → **분석(아무것도 쓰지 않는다)** → 무엇이 옮겨지는지 본 뒤에야 실행 버튼이 나온다. 옮겨지지 않는 것(쪽지·설문 등)과 그 이유를 **먼저** 보여준다 — 옮기고 나서 "왜 없지" 를 찾게 하면 그때는 늦다. 글 테이블이 덤프에 없는 게시판은 기본으로 선택하지 않는다(껍데기만 옮기면 빈 게시판이 늘 뿐이다). 브라우저로 샘플 덤프를 끝까지 돌렸다: 회원 6명·게시판 1개·글 6개·댓글 2개·영카트 상품 4개가 실제로 들어왔다. 바로 앞 라운드에서 본문 한도를 고치지 않았다면 이 화면은 만들자마자 3MB 짜리 덤프에서 막혔을 것이다. CI 가 회귀 하나를 잡아 줬다 — 본문 한도 훅이 **멀티파트 업로드까지** 가로채서, 큰 사진을 올린 손님이 업로드 한도 대신 JSON 한도를 듣고 있었다
- [x] **"50명이 기다리는 상품을 먼저 채우세요" 인데 그 50명을 볼 자리가 없었다** — `docs/restock.md` 는 운영자 절에 "관리자 → 쇼핑몰 → (API `GET /admin/restock-demand`)" 라고 적고 있었다. **괄호 안이 그대로 말해 준다** — 화면이 없어서 API 이름을 문서에 적어 둔 것이다. 같은 문단은 그 목록을 "재입고 우선순위를 정하는 근거" 라고 부른다. `AdminResource` 를 읽기 전용으로 선언해 화면을 얻었다 — 코어 관리 화면이 표를 그리므로 새 React 코드가 없다. 만들거나 고칠 것이 없는 목록이라 생성·수정·삭제를 전부 닫았다. 문서의 괄호도 걷어냈다
- [x] **영어 사이트의 주문서에 "무통장입금" 이 떴다** — 선언 문자열(원문이 곧 번역 키)은 관리 리소스만 검사하고 있었다. 그래서 **손님이 읽는 두 곳**이 새고 있었다: 마이페이지의 회원 메뉴에 "재입고 알림 · 내 포인트 · 내 스크랩" 이 한국어로 떴고, 주문서의 결제수단 이름은 **번역을 거치지도 않고** 원문을 그대로 내보내고 있었다(`displayName` 을 그대로 반환). 빠진 번역을 채우고 결제수단 이름을 카탈로그에 태웠다. 스모크가 두 곳을 전수로 본다 — 한국어가 하나라도 남으면 이름을 대고 실패한다. 이 라운드는 내가 만든 회귀에서 시작했다: 바로 앞에서 선언한 재입고 대기 리소스의 라벨 다섯 개를 영어로 옮기지 않았고, **기존 스모크가 그것을 즉시 잡았다**(CI 가 빨개졌다). 그 검사가 리소스만 보고 있다는 것을 그때 알았다
- [x] **메일이 보내는 링크를 코어만 검사하고 있었다** — 워크플로에는 "메일이 보내는 링크에 화면이 있다" 가 있는데 `apps/api` 만 훑는다. 플러그인은 보지 않아서 재입고 해지 링크가 죽은 채로 지나갔다. `check-mail-links.mjs` 가 플러그인의 메일 링크를 뽑아 **고정 구간이 화면에 닿는지** 본다: 첫 구간은 선언 화면이, 둘째 구간이 고정 문자열이면 선언 화면이나 라우터 분기(`seg[0] === "…"`)가 받아야 한다 — 둘 다 없으면 상품 slug 로 해석되어 "상품을 찾을 수 없습니다" 가 된다. 주소를 **지역 변수에 담아 쓰는** 경우까지 따라간다(주문 메일이 그렇게 쓴다 — 비회원에게는 그 링크가 주문을 볼 유일한 수단이다). 되돌려서 확인했다: 재입고 분기와 선언 화면을 함께 지우면 그 링크가 빨개진다
- [x] **운영자 역할은 관리 화면에서 아무것도 찾을 수 없었다** — 플러그인 관리 라우트는 디스패처가 **manager 까지 통과시킨다**(그렇게 설계했고 주석도 그렇게 적혀 있다). 그런데 사이드바를 만드는 목록(`/api/admin/nav`)과 화면을 그리는 선언(`/api/admin/resources/…`)만 admin 으로 닫혀 있었다. 그래서 운영자는 **권한은 있는데 길이 없었다**: 사이드바에 플러그인 리소스가 하나도 안 뜨고, 주소를 외워 들어가도 화면이 "오류" 로 떴다(데이터 라우트는 열려 있는데 선언을 못 읽어서). 그 상태에서 사이드바는 관리자 전용 링크(페이지·미디어·회원·설정·감사 …)를 그대로 보여줘서, 누르는 족족 403 이었다. 둘 다 `ManagerGuard` 로 열고(2단계 인증 강제와 IP 제한은 그대로 적용된다), 사이드바는 역할에 맞는 것만 그린다. 대시보드도 운영자에게는 "⚠ 불러오지 못했습니다" 대신 무엇을 할 수 있는지 말한다. 열어 준 것은 플러그인 화면뿐이라는 것도 스모크가 지킨다 — 코어 회원·설정·감사는 여전히 403 이다
- [x] **목록을 열어 줬더니 목록이 거짓말을 했다** — 바로 앞 라운드에서 운영자에게 관리 목록을 열어 주자, 그 목록에 **관리자만 쓸 수 있는 화면**이 섞여 들어갔다: 토스페이먼츠 설정(시크릿 키)은 라우트가 관리자만 받는데 사이드바에는 떠서, 누르면 403 이었다. 고친 문제를 작은 규모로 되돌린 셈이다. `AdminResource.adminOnly` 를 계약에 더해 리소스가 스스로 선언하게 했다 — 목록에서 가리고, 주소를 쳐도 선언 조회가 403 이다. 그 선언은 **보여줄지만** 정한다: 권한은 여전히 라우트가 지키고, 문서에도 그렇게 적었다(선언만 믿고 핸들러 검사를 빼면 안 된다)
- [x] **로그인한 손님이 폰으로 열면 화면이 가로로 밀렸다** — 동봉 테마 다섯 중 **셋**(기본·회사·부티크)에서 문서가 가로로 스크롤됐다: 375px 에서 381·385·475px, 320px 에서는 더 벌어졌다. 헤더 우측의 이름이 자기 칸보다 넓은데 줄지 않는 것이 원인이다 — flex 항목의 기본 `min-width: auto` 때문에 내용 너비 밑으로 줄지 않아서, 테마가 적어 둔 `max-width: 34vw` 와 말줄임이 아무 일도 하지 못했다. 헤더에 장바구니 같은 플러그인 링크가 붙으면 더 심해진다(부티크는 100px 이 삐져나왔다). `min-width: 0` 을 열어 주니 말줄임이 제 일을 한다 — 다섯 테마 × 320·375·768·1280px 에서 넘침이 전부 0 이 됐다. 부티크는 두 가지가 더 있었다: 좁은 화면에서 헤더 링크를 하나만 남기는 규칙(다른 세 테마가 이미 쓰는 것)이 빠져 있었고, 접힌 검색칸이 78px 를 늘 잡고 있어서 이름이 23px 로 눌렸다 — 화면 감사가 "작은 터치 23x40" 으로 잡았다. 마이페이지로 가는 유일한 링크다

- [x] **영어로 쓰는 사이트에서는 장바구니가 폰 화면 밖으로 나갔다** — 사이트 언어를 en 으로 두고 375px 로 열면 장바구니 표가 391px 로 벌어져 문서가 가로로 밀렸다. 밀려난 자리에 **수량 칸과 삭제 버튼**이 있다. 한국어에서는 우연히 들어맞아("상품/단가/수량/합계"가 "Product/Price/Qty/Total" 보다 좁다) 보이지 않던 문제다 — 상품 이름이 길어지면 어느 언어에서나 밀린다. 관리 화면은 이미 같은 일을 두 번 겪고 `.brick-x-table` 로 막아 두었는데 **손님 화면에는 그 짝이 없었다.** SDK 에 `STACK_TABLE_CSS` 를 내고(테마가 아니라 플러그인이 가진다 — 테마에 두면 이 규칙이 없는 제3의 테마에서 깨진다) 장바구니·주문 내역·취소반품 신청·재입고 신청·스크랩·포인트 내역·1:1 문의 내역 일곱 표를 카드로 접었다. 게시판 목록과 쪽지함은 이미 자기 방식으로 좁은 화면을 그리고 있어 그대로 뒀다. 수량 칸에 이름이 없던 것(`aria-label`)도 화면 감사가 같이 잡아 고쳤다. `check-guest-tables.mjs` 로 잠갔다 — 머리글이 있는 표는 접히거나, 그 표의 클래스가 미디어쿼리에 나타나야 한다
- [x] **영어로 쓰는 사이트에서 1:1 문의 화면은 통째로 한국어였다** — brick-helpdesk 의 손님 화면은 `t()` 를 **일곱 번**밖에 쓰지 않았다(게시판 159 · 쇼핑몰 358). FAQ 검색·평가, 문의 목록·작성 폼·상세, 비회원 조회까지 문구가 코드에 박혀 있어서, 관리 화면과 메일은 영어인데 손님이 문의하려고 누르는 순간 한국어가 나왔다. 같은 모양을 훑었더니 **게시판은 절반만** 옮겨져 있었다: 목록·상세는 번역되는데 에디터(링크 입력·이미지 업로드)와 댓글·추천·스크랩·삭제의 `prompt`·`alert`·상태 문구 스물셋이 한국어였다 — 읽기만 할 때는 영어, 쓰기 시작하면 한국어인 화면이다. 팝업(brick-site)도 "자세히 보기·닫기·N일 동안 보지 않기" 셋이 남아 있었다. 셋 다 카탈로그로 옮겼다(helpdesk 48키 · board 25키 · site 3키). 옮기면서 알게 된 것: **모듈 최상단의 템플릿 리터럴 상수는 `bindI18n` 보다 먼저 굳는다** — `BOARD_SCRIPT`·`HELP_SCRIPT`·`POPUP_SCRIPT` 를 함수로 바꿔야 번역이 실린다(쇼핑몰이 이미 함수로 쓰고 있던 이유다). 브라우저로 en·ko 양쪽을 확인했다. `check-screen-i18n.mjs` 로 잠갔다 — 화면 파일의 템플릿 리터럴에 한글이 남아 있으면 잡는다(보간과 주석은 지우고 본다)
- [x] **대비 감사가 59건을 지어내고 있었다** — 손님 화면 열여섯 개를 라이트·다크로 돌렸더니 헤더·내비게이션·필터가 통째로 1.06~1.9 로 나왔다. 이전 세션에서 한 번 본 뒤 재현되지 않아 손대지 않았던 그 보고서다(56건). 이번에는 재현됐고 원인도 잡혔다: 도구가 iframe 을 **띄운 뒤** `data-theme` 를 바꾸는데, 그러면 배경색은 새 테마로 바뀌지만 **글자색이 이전 테마 값에 머문다** — 변수(`--color-text-soft`)는 분명히 바뀌었는데 `var()` 로 물린 `color` 가 다시 계산되지 않는다(크로미움에서 확인: 변수 #4a4f59, 배경 #101216, 글자색은 rgb(74,79,89) 그대로). 밝은 글자가 밝은 배경 위에 있는 것처럼 읽힌 것이다. 진짜 화면에서 토글을 눌러 보면 멀쩡하다(6.9:1) — **도구만 틀렸다.** 사이트는 첫 페인트 전에 `localStorage("brick-theme")` 를 읽으므로, 같은 출처인 iframe 에 그 값을 **미리** 넣어 두고 불러오게 고쳤다. 더해서, 요청한 모드로 실제 그려졌는지 확인하고 아니면 측정하지 않고 그 사실을 보고한다 — 조용히 다른 모드를 재면 보고서 전체가 거짓이 된다. 같은 화면에서 59 → **0건**(건너뜀 4). 역검증: 테마 토큰 하나를 일부러 안 보이는 색으로 바꾸니 16건을 잡고, 부트 스크립트가 없는 문서에서는 "화면 모드가 적용되지 않았습니다" 로 걸린다. 곁들여 화면 감사가 잡은 FAQ 의 "예/아니오" 버튼(38x26)을 40px 로 키웠다
- [x] **카드로 결제할 수 있는 쇼핑몰이 아니었다** — 게이트웨이 계약도, 토스 플러그인도, 금액 위조·중복 승인 방어도, 부분 환불도, 정기결제 빌링키도 다 있었다. PG 스텁으로 도는 스모크가 그 경로를 전부 지키고 있었다. 그런데 **손님이 카드를 고를 자리가 없었다.** 세 군데가 끊겨 있었다: (1) 주문서에 "무통장입금" 이 글자로 박혀 있고 `/payment-methods` 는 **부르는 곳이 하나도 없는** 라우트였다, (2) 주문 생성이 `PAYMENT_METHODS = ["bank_transfer"]` 배열로 검사해서 — 바로 옆 주석은 "PG 연동은 별도 플러그인이 추가한다" 인데 더하는 곳이 없어서 — 카드를 보내면 "지원하지 않는 결제수단입니다: toss" 로 거절했다, (3) CSP 의 `script-src` 가 고정이라 결제창 SDK 를 부를 방법이 없었다. 셋을 이었다(ADR-112): 주문에 실을 수 있는 수단은 **등록된 게이트웨이**로 판단하고, 그 자리에서 승인이 필요한 수단은 `checkout.script` 로 클라이언트 단계를 **선언해야만** 주문서에 나온다(선언이 없으면 고를 수는 있는데 승인으로 갈 길이 없다 — 손님은 결제했다고 믿고 사업자는 못 받은 주문을 배송한다), `script-src` 는 매니페스트로 열되 **호스트를 못박은 https 출처만** 받는다(`https:` 나 와일드카드를 받으면 CSP 의 목적이 사라진다). 토스 플러그인에 결제창 호출과 복귀값 번역(`readReturn`)을 넣었다. PG 스텁으로 브라우저에서 밟았다: 주문서에 두 줄이 뜨고, 카드를 고르면 주문이 만들어져 결제창으로 넘어가고, 돌아오면 `/payments/confirm` 으로 마쳐 주문이 `paid` 가 된다(스텁 로그에 승인 27,000 과 멱등키). 곁들여: 결제창에 뜰 주문명(`머그컵 (샘플)`)을 주문 응답에 넣었고 — 주문번호만 보내면 손님은 결제창에서 무엇을 사는지 알 수 없다 — 입금 계좌는 무통장입금일 때만 준다
- [x] **결제창에서 취소하면 유령 주문만 남았다** — 카드로 주문하면 주문이 먼저 만들어지고 결제창으로 넘어간다. 거기서 취소하거나 실패하면 주문은 `pending` 으로 남는데 **다시 결제할 자리가 없었다.** 손님이 할 수 있는 일은 다시 주문하는 것뿐이고, 앞의 주문은 미결제로 남아 사업자가 떠안는다. 주문 상세에 "결제하기" 를 놓고 같은 계약(`window.brickPay[provider]`)으로 결제창을 다시 연다. 낼 수 있는 주문인지는 **서버가 판단한다**(`payable`) — 아직 결제대기이고, 그 결제수단의 게이트웨이가 준비돼 있으며, 클라이언트 단계를 선언했을 때만이다. 규칙을 화면에도 두면 갈라져서 못 내는 주문에 버튼을 내밀게 된다(현금영수증에서 같은 판단을 이미 서버에 뒀다). 돌아오면 상세를 **다시 받아 그린다** — 상태·이력·현금영수증 신청 가능 여부가 전부 결제 여부에 딸려 있어서, 화면을 손으로 고치면 어긋난다. 주문서의 취소 안내도 이제 그 주문으로 데려간다(없던 길을 약속하지 않으려고 "다시 주문하세요" 라고만 적어 뒀던 문구다)
- [x] **정기결제는 카드를 등록할 화면이 없어 통째로 닿지 않았다** — 손님용 라우트가 **열 개** 있었다: 카드 등록 준비·발급·목록·삭제, 정기배송 가입·목록·회차 이력·해지·재개. 화면은 **하나도 없었다.** 회원은 카드를 등록할 수 없고, 카드가 없으니 정기배송에 가입할 수도 없다 — 관리 화면의 "정기배송" 목록은 만들어질 수 없는 구독을 기다리고 있었고, 상품 선언에는 `sub_interval` 칸까지 있다. 뿌리인 **결제 카드 화면**(`/shop/cards`, 회원 메뉴)을 만들었다: 등록된 카드 목록·삭제·등록. 게이트웨이 계약에 카드 등록 단계를 더했다(`registerCard({customerKey, returnUrl})` + `readCardReturn(query)`) — 결제 단계와 같은 모양이다. **카드번호는 PG 의 등록 창에서만** 입력되고 우리가 받는 것은 1회용 `authKey` 뿐이며, 빌링키 발급은 서버가 그 키로 PG 에 직접 요청한다(화면에도 그렇게 적었다). `listBillingProviders` 는 이제 **클라이언트 단계를 선언한 게이트웨이만** 내놓는다 — 서버 쪽 둘(발급·청구)만 있으면 목록에는 뜨는데 눌러도 아무 일이 없다(`isReady` 와 같은 원칙).
